# AI 前端技能清单

按优先级从高到低排列。

---

## 1. SSE / Stream 流式渲染

大模型生成内容是逐 token 输出的，不是一次性返回完整结果。前端用 SSE（Server-Sent Events）接收服务端持续推送的数据流，然后逐字渲染到界面上，形成"打字机"效果。

实现上通常不用浏览器原生的 EventSource，因为它有两个硬伤：只支持 GET 请求（不能传复杂的 JSON 参数）、不能自定义 Header（比如传 token 鉴权）。所以实际项目里一般用 Fetch API + ReadableStream 手动解析数据流。

手动解析要处理的最大坑是**粘包半包**：TCP 是流式传输，你收到的每一个 chunk 不一定刚好是一帧完整的 SSE 消息——可能一个 chunk 里包含多帧，也可能一帧被拆到了两个 chunk 里。解决方案是自己维护一个 buffer，每次收到新数据追加进去，然后按 `\n\n` 分隔符切分出完整的帧，切不完整的部分留在 buffer 里等下一个 chunk。除此之外还有断线重连（网络断了怎么自动恢复）、超时降级（模型太久没返回怎么提示用户）、连接中断（用户点了"停止生成"怎么立刻中止流）。

面试会追问：为什么不用 WebSocket？答案——大模型场景是服务端单向推流，客户端只需要接收，不需要双向通信。SSE 更轻量、基于 HTTP、容易接入网关和鉴权体系。

## 2. 多轮对话上下文管理

LLM 每次调用是无状态的，不知道上一轮说了什么。多轮对话的本质是：把历史消息按照角色排列好，每次请求时把历史带上发给模型，让它"记住"前面的内容。

**上下文窗口管理**：每个模型有最大 Token 上限，对话长了会超出窗口。常见的解决方式——滑动窗口（只保留最近 N 轮）、摘要压缩（把较早的对话压缩成一段摘要）、关键信息提取（只保留重要的几轮，其余丢弃）。

**多会话隔离**：用户可能同时开着多个对话。每个会话的上下文独立存储、切换时不能串。你 IOT 项目里基于 LangGraph 做的上下文隔离，解决的就是"会话状态污染"——A 会话的消息不会出现在 B 会话里。

**持久化与恢复**：对话历史存到后端或本地，刷新页面后能恢复之前的对话。

## 3. Function Calling / 工具调用

给 LLM 定义一套"工具"——每件工具用 JSON Schema 描述它的名称、功能、参数。当用户的问题需要外部数据或执行操作时，模型不直接回答，而是返回一个"我要调用某某工具"的指令，并附上参数。前端拿到这个指令后实际执行调用（比如查数据库、调天气 API），然后把结果回传给模型，模型再基于结果生成最终的回答。

前端要处理几个关键状态：每个工具调用的状态展示（调用中 loading → 成功展示结果 → 失败展示错误 → 超时提示重试）、多个工具并行调用还是串行调用的编排、调用结果在前端的渲染形式（纯文本 vs 表格 vs 图表 vs 地图，取决于工具返回的数据类型）。

还有个容易被问到的点：**工具描述的稳定性**。工具 Schema 写得不好，模型可能选错工具、传错参数、甚至不调用工具直接编造答案。Schema 设计得像写接口文档一样严谨。

## 4. MCP（Model Context Protocol）

MCP 是 Anthropic 提出的一套标准化协议，本质上就是把 Function Calling 规范化——让不同的大模型、不同的应用都能用同一种方式连接外部工具和数据源。可以理解为"AI 时代的 API 标准"。

三个核心概念：
- **Tools（工具）**：模型可以调用的能力，比如"搜索文件"、"发送邮件"。每个 Tool 有名称、描述和 JSON Schema 定义的参数
- **Resources（资源）**：提供上下文的数据，比如文件内容、数据库记录、API 文档。像 GET 请求，只读
- **Prompts（提示模板）**：预定义的 Prompt 模板，用户可以快速选择使用

运作方式：MCP Server 对外暴露 Tools、Resources、Prompts → MCP Client 连接 Server 获取这些列表 → 把 Tool 列表转成 Function Calling 的 Schema 发给大模型 → 大模型决定调用哪个 Tool → Client 执行调用 → 结果返回给大模型。

前端关注的点：怎么通过 MCP Client 获取工具列表、怎么在前端展示这些工具、工具调用过程中每个步骤的状态怎么渲染、流式响应怎么处理。

## 5. Agent 架构

Agent 不只是"对话机器人"。它是一套能自主思考、规划、执行多步操作的系统。四个核心组件：

- **大脑（LLM）**：负责推理和决策，理解用户意图、判断下一步该做什么
- **工具（Tools）**：能实际执行操作的能力，通过 Function Calling / MCP 调用
- **记忆（Memory）**：短期记忆（当前会话的上下文）、长期记忆（用户偏好、历史记录、知识库）
- **规划（Planning）**：把复杂任务拆解成多个子任务，按顺序或并行执行

核心执行模式是 **ReAct**（Reasoning + Acting）：模型先思考（Thought）→ 决定执行什么动作（Action）→ 观察执行结果（Observation）→ 根据结果再思考下一步 → 循环直到任务完成。比如用户说"帮我找杭州 25K 以上的 AI 前端岗位"，Agent 会先搜索岗位 → 看到搜索结果后判断数量太多 → 再加薪资过滤条件 → 拿到最终结果后生成推荐。这不是一问一答，是模型自主多步推理。

**多 Agent 协作**：一个主 Agent 拆解任务，分发给多个子 Agent 各自执行，最后汇总。比如求职助手场景——搜索 Agent 爬岗位、解析 Agent 提取 JD 要求、匹配 Agent 对比简历、建议 Agent 输出优化方案——四个 Agent 各干各的，最后拼成一份完整报告。

## 6. RAG（检索增强生成）

LLM 的知识截止于训练日期，而且会编造不存在的事实（幻觉）。RAG 的核心思路是：回答问题之前先去外部知识库检索相关资料，把检索到的内容当作"参考资料"一起发给模型，让它基于参考资料回答问题，而不是凭空编造。

全链路七个环节：
1. **文档加载**：支持 PDF、Word、Markdown、网页等各种格式
2. **文本分块**：把长文档切成小段（Chunk），块太大检索不精准，太小丢失上下文。分块策略是关键决策点
3. **向量化（Embedding）**：把每个 Chunk 转成一个高维向量，语义相近的文本向量距离也近
4. **向量存储**：存入向量数据库（Milvus / Chroma / FAISS / Pinecone），支持快速相似度搜索
5. **检索**：用户提问时，把问题也向量化，到库里找最相似的 Top-K 个 Chunk。高级做法会用混合检索（关键词 BM25 + 语义向量）+ 重排序（Rerank）
6. **生成**：把检索到的 Chunk 拼进 Prompt，发给 LLM 生成最终答案
7. **引用溯源**：答案里的关键信息标注来自哪个文档的哪一段

前端在 RAG 里的角色：文档上传 UI（拖拽上传、解析进度、分块预览）、知识库管理界面、检索结果高亮展示、答案引用溯源的渲染（"这段回答来自《xxx 文档》第 3 页"）。

## 7. Agent 交互 UI

这是 AI 前端跟传统前端最大的体验差异。传统前端是"用户操作 → 页面响应"，AI 前端是"用户触发 → Agent 后台多步执行 → 实时推送中间状态 → 最终展示结果"。用户在等的过程中需要看到 Agent 在干什么，否则体验就是"卡住了"。

四个核心 UI 模式：

**思考链展示**：Agent 推理时每一步在想什么，实时展示出来。类似 ChatGPT 的 Thinking——用户能看到"正在分析问题… → 决定搜索岗位… → 找到 15 条结果… → 正在按薪资过滤…"。这一步的文案可以是模型生成的，也可以是前端根据 Agent 的执行阶段自动拼接的。

**工具调用状态**：Agent 调工具不是一瞬间完成的。每个工具调用有一个状态机——空闲 → 调用中（loading 动画 + 工具名称 + 参数预览）→ 成功（展示结果摘要）→ 失败（错误信息 + 重试按钮）→ 超时（提示 + 降级方案）。多个工具并行调用时要展示并行状态，串行调用时展示执行顺序。

**进度指示**：用户需要知道"Agent 还在干活"以及"大概还要多久"。可以是简单的一排跳动圆点，也可以是基于步骤数的进度条（"第 2/4 步"）。

**中断控制**：用户可以随时点"停止"。这个操作要同时中止前端的流式接收和后端的 Agent 执行。技术上用 AbortController 实现。

## 8. Prompt Engineering 系统化

不只是"写一段话让 AI 干活"，而是一套系统化的方法论：

- **System Prompt 角色设定**：定义模型的角色（"你是一个技术面试官"）、行为边界（"只回答技术问题，不聊其他"）、输出格式（"用 Markdown 格式回答"）
- **思维链（Chain of Thought）**：让模型在给答案之前先写出推理过程，"先分析这道题的考点，再给出答案"
- **少样本学习（Few-shot）**：在 Prompt 里给几个示例，让模型理解你想要的输出格式和风格。比如给两个"问题→分析→答案"的范例，第三个它就会照这个结构来
- **结构化输出**：要求模型返回 JSON 或特定格式的内容，用 JSON Schema 约束输出结构，结合 Pydantic 校验保证格式正确
- **动态 Prompt 组装**：根据用户状态、上下文、历史记录动态拼装 Prompt 模板，而不是每次都用同一段话

面试会问的不是"你用过 Prompt Engineering 吗"，而是"你是怎么设计 Prompt 的，有没有一套方法论"。你在 IOT 项目里针对设备运营场景设计的定制化 Prompt 策略，包装一下就是这个问题的答案。

## 9. Token 与成本控制

每次 LLM 调用按 Token 计费。input 和 output 的 Token 分开算，价格不同，output 通常更贵。

需要关注的：长对话的 Token 累积（每轮都把历史带上，Token 随对话增长）、上下文截断策略（什么时候该裁剪历史）、Prompt Caching（相同的 System Prompt 或前缀可以缓存，省 input Token 的钱）、模型选型（便宜的模型做简单任务，贵的模型做复杂推理）。

面试常被问："用户量上来后，Token 成本怎么控制？"——答案方向：缓存重复的 System Prompt、做上下文窗口管理不做无脑全量携带、根据任务复杂度动态选择模型。

## 10. Embedding / 语义搜索

把文本转成高维向量。语义相近的文本向量距离近，语义不相关的向量距离远。

跟传统关键词搜索的区别：搜"前端开发"能匹配到"Web 前端工程师"、"React 开发"、"用户界面开发"等语义相近但字面不同的词——因为它们在向量空间里距离近。

前端视角主要是调搜索接口、展示搜索结果、对命中词做高亮。不需要自己写 Embedding 逻辑或管理向量数据库，但要理解向量搜索和传统搜索的差异，能跟后端讨论搜索结果的排序和展示策略。

## 11. 流式结构化输出

普通流式输出是纯文本，相对好处理。但如果你让模型流式返回 JSON，问题就来了——流式过程中 JSON 一直是残缺的，`{"name": "王鹏伟", "skills": ["R` 这样的片段你没法 parse。

解决方案：每个 chunk 到达时缓存起来，尝试 parse，parse 失败就继续等，直到能解析成完整的 JSON 对象。也可以降级处理——先在前端展示已解析出来的字段，剩下的显示加载中。

面试高频追问："流式输出中怎么处理不完整的 JSON？"——你需要回答 buffer 缓存 + 渐进式解析 + 降级兜底的完整策略。

## 12. 端侧 AI / 浏览器推理

Chrome 最新版本内置了小模型（Gemini Nano），可以直接在浏览器里跑推理，不需要调云端 API。优势是低延迟、离线可用、数据不离开用户设备。WebNN、WebGPU 做硬件加速。

目前还是早期阶段，能跑的场景有限（文本摘要、情绪分类等简单任务），大模型没法本地跑。但面试里可能会被问到"对端侧 AI 有什么了解"，能说出 Chrome 内置模型 + WebNN 加速就够了。

---

## 13. 多模态交互

用户的输入不只是文字——可能是语音、图片、文件、甚至视频。前端负责这些非文本媒体的捕获和上传，以及模型返回的多模态结果渲染。

- **语音输入**：Web Speech API 做语音识别，把语音转成文字发给模型
- **图片理解**：用户上传截图，模型分析图片内容。前端负责图片压缩、预览、结合文字提问一起发送
- **文件处理**：文档上传做知识库、代码文件让模型分析、Excel 做数据问答
