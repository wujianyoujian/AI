# 一、前端基础

## 1. 浏览器渲染机制

**Q: 从输入 URL 到页面渲染的完整过程？**

- **网络阶段：** DNS 解析 → TCP 连接（TLS 握手）→ HTTP 请求 → 服务器响应
- **解析阶段：** HTML 解析（DOM 树）→ CSS 解析（CSSOM 树）→ 遇到 `<script>` 阻塞解析（除非 async/defer）
- **渲染阶段：** DOM + CSSOM → Render Tree → Layout（回流）→ Paint（重绘）→ Composite（合成层）
- **关键优化点：** 减少阻塞资源、避免强制同步布局、利用 GPU 合成层

**Q: 回流和重绘的区别？什么操作会触发回流？**

- **回流（Reflow）：** 改变元素几何属性（宽高、位置），触发重新布局。成本高。
- **重绘（Repaint）：** 只改变外观（颜色、阴影），不改变布局。成本较低。
- **触发回流的操作：** offsetTop/Left 读取、display: none、添加/删除 DOM、改变字体大小、resize 窗口
- **优化：** 用 class 批量修改样式、DocumentFragment 批量插入、transform 代替 left/top（跳过 Layout）

**Q: 合成层是什么？哪些属性会创建合成层？**

- 合成层由 GPU 独立绘制，不触发回流和重绘
- 触发条件：3D transform、video/canvas/iframe 元素、will-change、opacity 动画、filter
- 陷阱：过多合成层导致内存暴涨（层爆炸），需要合理控制

## 2. Event Loop

**Q: 详细解释 Event Loop 机制？**

- JS 是单线程，通过事件循环实现异步
- **调用栈：** 同步代码执行的地方
- **任务队列分两种：**
  - **宏任务（MacroTask）：** script 整体、setTimeout、setInterval、I/O、UI 渲染、postMessage
  - **微任务（MicroTask）：** Promise.then/catch/finally、MutationObserver、queueMicrotask
- **执行顺序：** 执行一个宏任务 → 清空所有微任务 → 检查是否需要渲染 → 下一个宏任务
- **关键：** 微任务在当前宏任务结束后立即全部执行，渲染可能在宏任务之间也可能在之后（浏览器 16.6ms 一帧）

**Q: 这道经典题输出什么？**

```js
console.log(1)
setTimeout(() => console.log(2), 0)
Promise.resolve().then(() => console.log(3))
console.log(4)
```

> 1 → 4 → 3 → 2。当前宏任务执行 1 和 4，微任务队列执行 3，下一个宏任务执行 2。

## 3. Promise 与 async/await

**Q: Promise 的三种状态？all、allSettled、race、any 的区别？**

- 三种状态：pending → fulfilled / rejected（不可逆）
- `Promise.all`：全部成功才成功，一个失败就失败
- `Promise.allSettled`：等全部完成，不管成功失败，返回每项结果
- `Promise.race`：返回最先完成的结果（不管成功失败）
- `Promise.any`：返回第一个成功的结果，全部失败才失败（ES2021）

**Q: async/await 的原理？和 Promise 的关系？**

- async 函数返回 Promise；await 暂停函数执行直到 Promise 完成
- 本质是 Generator + Promise 的语法糖
- await 后面的代码相当于 `.then()` 里的回调（微任务）
- **错误处理：** try/catch 包裹 await，或 .catch() 链式调用

**Q: 多个 await 串行 vs Promise.all 并行？**

```js
// 串行 — 各等各的
const a = await fetchA()
const b = await fetchB()  // B 等 A 完成才开始

// 并行 — 同时发起
const [a, b] = await Promise.all([fetchA(), fetchB()])
```

## 4. TypeScript

**Q: TypeScript 中 type 和 interface 的区别？**

- interface：可被合并声明（declaration merging）、更适合描述对象形状、extends 继承
- type：可定义联合类型、交叉类型、元组、不能重复声明、功能更强大
- **选型：** 对外 API/组件 Props 用 interface（可扩展），内部工具类型用 type

**Q: 泛型怎么用？写一个泛型工具类型？**

```ts
// 实际场景：提取 API 响应中的 data 字段类型
type ApiResponse<T> = { code: number; data: T; message: string }
type UserListRes = ApiResponse<{ users: User[]; total: number }>

// Pick / Omit / Partial / Required 等内置工具类型的原理
type MyPick<T, K extends keyof T> = { [P in K]: T[P] }
```

# 二、React 深度

## 5. React Fiber 架构

**Q: React Fiber 是什么？解决了什么问题？**

- React 16 重构的协调引擎，解决 Stack Reconciler 的同步递归不可中断问题
- **核心改进：** 可中断的异步渲染、优先级调度、双缓冲（current ↔ workInProgress 两棵树交替）
- **工作过程：** Render 阶段（可中断，构建 Fiber 树）→ Commit 阶段（不可中断，更新 DOM）
- **实际收益：** 大列表更新时不会阻塞用户输入，动画更流畅

**Q: React 的 Diff 算法三个假设？**

1. 只对同级元素比较，不跨层级
2. 不同类型的元素产生不同的树（div → span 会整个替换）
3. key 属性标识元素是否变化，优化列表渲染

**Q: key 的作用？为什么不能用 index？**

- key 帮助 React 识别哪些元素变了、添加了、删除了
- 用 index：如果列表重新排序，key 不变导致错误复用 DOM、状态错乱
- **最佳实践：** 用稳定的唯一 ID

## 6. Hooks 原理

**Q: useState 的原理？为什么不能在条件语句中调用？**

- React 通过**调用顺序**维护 Hook 链表（Fiber.memoizedState 单向链表）
- 每次渲染按相同顺序读取 Hook → 必须保持调用顺序稳定
- 放条件语句里 → 顺序变化 → 状态错位

**Q: useEffect 和 useLayoutEffect 的区别？**

- useEffect：渲染提交到屏幕后**异步**执行，不阻塞渲染，用于数据请求、订阅
- useLayoutEffect：DOM 更新后、浏览器绘制前**同步**执行，会阻塞渲染，用于 DOM 测量、避免闪烁

**Q: useMemo 和 useCallback 的区别和使用场景？**

- useMemo：缓存计算结果，依赖不变不重新计算
- useCallback：缓存函数引用，避免子组件不必要的重渲染
- **不要滥用：** 简单计算不需要缓存，配合 React.memo 使用才有意义

**Q: 自定义 Hook 解决过什么实际问题？**

> 比如做了一个 usePolling Hook：轮询查询任务状态直到完成或超时，支持指数退避、组件卸载自动取消、返回 loading/data/error 三态。把轮询逻辑从业务组件中抽离，10+ 个页面复用。

## 7. 状态管理

**Q: Zustand 和 Redux 的对比？你为什么选 Zustand？**

- Zustand：极简 API（create 一个函数搞定）、不需要 Provider 包裹、原生支持 selector 精确渲染、TypeScript 友好、包体积极小（<1KB）
- Redux：概念多（store/reducer/action/middleware）、需要 Provider、样板代码多、但生态成熟
- **选型理由：** 中后台项目不需要 Redux 的中间件生态和时间旅行调试，Zustand 够用且开发效率高

## 7b. React 面试主线（23 题口述版）

> 按一条主线组织：Fiber 总纲 → 渲染链路 → Hooks → 并发 → 状态管理 → 新特性 → 路由 → 性能与工程化。每题先给**口述版**（面试直接背，2-4 句），再给**要点**。

### 1. Fiber 是什么

**口述版：** Fiber 是 React 16 引入的新的协调引擎数据结构。它既是**最小的工作单元**——一次渲染中的一个节点，可以单独开始、暂停、恢复；也是**链表对象**——通过 child、sibling、return 三个指针串成树，天然支持中断后从任意节点继续。每个 fiber 上挂着 stateNode、Hook 链表、updateQueue、lanes、flags、alternate——**它是一个组件一次渲染的完整账本**。双缓冲（current 树和 workInProgress 树互指）保证中断不污染 UI。

- 解决 Stack Reconciler 同步递归不可中断的问题
- 三个指针：child（向下）/ sibling（横向）/ return（向上）
- 挂载内容：stateNode、memoizedState（Hook 链表）、updateQueue、lanes、flags（Placement/Update/Deletion）、alternate

### 2. createElement

**口述版：** createElement 是创建 React 元素（ReactElement）的函数，**JSX 是它的语法糖**，编译后就是 createElement 调用。它返回一个描述 UI 的普通对象（type、props、key、ref、children），**不碰 DOM**。ReactElement 不可变，render 阶段才把它转成可变的 Fiber。整条链：**JSX → createElement → ReactElement → Fiber → DOM**。

- React 17 新 JSX transform（react/jsx-runtime）后，日常写 JSX 不再需要 import React
- cloneElement：复制已有元素并改 props（封装组件透传 props 时用）
- $$typeof 符号标记防 XSS

### 3. render / commit 阶段 & mutation 阶段

**口述版：** React 渲染分两个阶段。**render 阶段**（reconcile/diff）是纯计算、不碰 DOM、**可中断**，产出 effectList，标记哪些节点要增删改；**commit 阶段**真正操作 DOM、**不可中断**，一口气执行完。commit 内部又分三个子阶段：**before mutation**（DOM 未动）、**mutation**（真正动 DOM：插入/更新/删除）、**layout**（DOM 已定：ref 赋值、useLayoutEffect 执行）。**mutation 是 commit 的子阶段，不是并列概念**。删除节点时 mutation 阶段会先 detach ref（ref.current = null）再移除 DOM，防止内存泄漏。

- 为什么 commit 不可中断：改真实 DOM，中断会造成 DOM 与 Fiber 树不一致
- useRef 的 DOM 赋值发生在 layout 阶段 → 所以 useEffect 能访问到 ref.current

### 4. Diff 算法

**口述版：** Diff 是 render 阶段对比新旧虚拟 DOM、**找出最小更新量**的过程。基于**三个假设**把 O(n³) 降到 **O(n)**：① 只做同层比较不跨层；② 类型不同直接替换整个子树；③ 同层列表用 key 标识复用。多节点 diff 分**三轮**：从头开始比较（key 相同就复用）、从尾开始比较、剩余节点用 map 找复用并判断移动（lastPlacedIndex）。结果标记在 fiber 的 flags 上，commit 阶段才执行。**key 要稳定唯一，不能是 index**（index 会导致头部增删时全部重建 + 状态错乱）。

- diff 是启发式算法，不保证最优，但符合 UI 变化模式
- 与 Vue 对比：Vue 双端 diff，React 单端三轮，思想一致（同层 + key）

### 5. 合成事件（SyntheticEvent）

**口述版：** React 没有把事件直接绑定到每个 DOM 元素上，而是封装了**跨浏览器统一的事件系统**。所有事件**委托到根容器**上统一监听，派发时**沿 Fiber 树模拟捕获和冒泡**，并包装成统一的事件对象（SyntheticEvent）。React 17 之前委托在 document 上，17 之后移到**根容器**——原因是多版本共存互不干扰、避免与页面其他 document 监听冲突。**执行顺序：原生捕获 → React 捕获 → React 冒泡 → 原生冒泡**。合成事件的 stopPropagation **挡不住原生冒泡**（原生事件早已冒泡到根容器）。React 16 有事件池（异步访问 e.target 拿不到，要 e.persist()），**17 已移除**。

- 为什么用合成事件：跨浏览器兼容 + 委托性能 + 跨端统一（SSR/RN）+ 配合调度器批量更新
- 通过 e.nativeEvent 拿底层原生事件对象

### 6. useState 原理

**口述版：** useState 的状态存在 **fiber 的 memoizedState 链表**上，返回 `[hook.memoizedState, dispatch]`。dispatch 在 mount 时创建一次、**引用恒定**。每次调用 dispatch：把 update 塞进 **queue.pending 环形链表**，先**急迫计算**一次新值，用 **Object.is** 和当前值比较——相同则 **bail out 跳过渲染**，不同则**调度重新渲染**。render 阶段重新执行组件函数时，遍历 pending 队列把每个 action 依次算到旧值上，算出**最新状态写回 memoizedState** 并返回。它本质是 **useReducer 的语法糖**。

- **dispatch = 排队 + 调度；执行 = render 阶段**（这就是"异步感"和闭包陷阱的根源）
- 函数式更新（c => c+1）依次累加；传值后者覆盖
- 为什么不能条件调用 Hook：按调用顺序和链表节点一一对应，条件调用会错位

### 7. React 18 自动批处理（Automatic Batching）

**口述版：** 批处理 = **一次事件/回调里多次 setState 合并成一次渲染**。React 17 之前**只在 React 事件处理函数里批量**（靠 isBatching 上下文标记），setTimeout、Promise、原生事件里不批量。React 18 把批量能力**下沉到调度器层面**：setState 永远只做两件事——把 update 塞进队列 + 调用 scheduleUpdateOnFiber 进统一调度器，调度器合并所有待处理更新（Lane 合并）再一次性渲染。**所以从哪调用都自动批量**。要立即拿新值用函数式更新，要同步提交 DOM 用 flushSync（逃生舱，别滥用）。

- 17 = 标记法（上下文包裹），18 = 调度法（统一入口），这是架构升级
- 批处理和并发是同一调度器的两面：合并更新 + 按优先级执行

### 8. useEffect / useLayoutEffect 原理

**口述版：** 两者都存在 **fiber 的 memoizedState 链表的 hook 对象**上，内容是 **effect 对象**（create 回调、destroy 清理、deps、tag 标记），所有 effect 串成**环形链表挂在 fiber.updateQueue** 上。render 阶段负责**收集和比对 deps**（Object.is），commit 阶段按时机执行。**useLayoutEffect 在 commit 的 layout 阶段同步执行（绘制前，不会闪烁）**，useEffect 在**浏览器绘制之后异步执行**（不阻塞）。deps 变了**先 destroy 旧的、再 create 新的**。注意：**useEffect 返回 undefined**，`[state, dispatch]` 是 useState 的返回值。

- layout = 绘制前同步（同 componentDidMount 时机，能读 DOM 布局）
- passive = 绘制后异步（不阻塞首屏）
- deps 不传 = 每次渲染都执行（配合 setState 易死循环）

### 9. useRef 原理

**口述版：** useRef 的本质是**在 fiber 的 memoizedState 上存一个 `{ current: 值 }` 对象**，mount 时创建一次，之后每次渲染返回**同一个引用**，所以能跨渲染保存数据。改 current **不触发渲染**——它是逃离渲染体系的后门。当 JSX 元素挂了 ref 属性时，**commit 的 layout 阶段（commitAttachRef）把 DOM 节点赋给 ref.current**，所以 useEffect 里能安全访问；卸载时 mutation 阶段（commitDetachRef）把 current 置 null 防内存泄漏。

- ref = 副作用数据（不驱动 UI），state = 视图数据（驱动 UI）
- 函数组件 ref 指向 DOM，类组件指向实例
- useRef 是 Hook（复用同一对象），createRef 每次渲染新建（只用于类组件）

### 10. useMemo / useCallback

**口述版：** 两者都是**依赖数组驱动的缓存**，存在 memoizedState 上。useMemo 缓存**计算结果**（值），useCallback 缓存**函数引用**——**useCallback(fn, deps) 本质是 useMemo(() => fn, deps)**。每次渲染用 Object.is 逐个比对 deps：相同就复用缓存，不同才重新计算。价值是**引用稳定性**：配合 React.memo 防止子组件重渲染、放进 useEffect 依赖数组避免反复触发。代价是 deps 比较 + 内存开销，**滥用反而更慢**。判断标准：计算真的很重才 useMemo，函数真的常传给 memo 子组件才 useCallback。

- 传对象/数组给 memo 子组件时用 useMemo（每次渲染都是新引用）
- useMemo 不是持久仓库（React 不保证缓存存活），持久数据用 useRef

### 11. useReducer vs useState

**口述版：** **useState 是 useReducer 的语法糖**（源码里 useState 就是 useReducer(basicStateReducer)），两者底层机制完全相同（memoizedState 链表 + 批量更新 + Object.is bail out）。区别在**组织方式**：useState 适合**单个简单值**直接覆盖；useReducer 适合**多个关联字段**、更新逻辑有固定规则（状态机）、逻辑需要复用和测试（reducer 是纯函数）、深层组件树传 dispatch（引用恒定，不破坏 memo）。**简单用 useState，复杂用 useReducer**——useReducer 样板代码多，简单场景用它反而啰嗦。

- dispatch 引用恒定：可安全放依赖数组、直接传 memo 子组件
- 第三个参数 init 函数做惰性初始化

### 12. 并发与时间切片

**口述版：** React 18 的并发不是同时执行，而是**让渲染可中断、可抢占、可恢复**。JS 单线程，所以是**伪并发，本质是可中断渲染**。实现靠三个前提：**Fiber 链表**（可暂停恢复）+ **双缓冲树**（workInProgress 不污染 current）+ **Lane 优先级**（可抢占）。**时间切片是它的实现手段**：调度器用 **MessageChannel 宏任务**把渲染拆成 **5ms 一片**，每片执行完让出主线程，浏览器趁机响应输入和绘制。配合 startTransition / useDeferredValue 让低优先级渲染让位给高优先级输入。**commit 阶段不能并发**——改真实 DOM 必须一口气同步完成。

- 并发特性：startTransition（低优先级更新）、useDeferredValue（延迟值）、Suspense
- Scheduler 用 MessageChannel 而不用 setTimeout：嵌套 setTimeout 被 clamp 到 4ms；不用 requestIdleCallback：兼容性和时机不可控
- 与 Vue 对比：Vue 响应式粒度细不需要时间切片，React 粗粒度 + 可中断，是设计取舍

### 13. Lane 优先级（可抢占）

**口述版：** Lane 用**二进制位**给每个更新贴优先级标签，一位代表一种优先级，**低位 = 高优先级**。合并用 `|`、判断交集用 `&`、取最高优先级用 `& -lanes`，全是 **O(1) 位运算**。**抢占的实现**：渲染循环每处理一个 fiber 就检查一次 getNextLanes，发现更高 lane 插队就**中断当前渲染**——workInProgress 树和遍历进度保留，**从断点恢复**。**使用差异**：点击事件 setState 是 SyncLane（最高，立即渲染）、输入是 InputContinuousLane、普通 setState 是 DefaultLane、startTransition/useDeferredValue 是 TransitionLane（可被打断、可推迟）。

- 中断不是杀进程：workInProgress 树 + 已遍历 fiber 指针都保留；状态真变了才丢弃重算
- 一个变量 pendingLanes 记录所有排队任务，一次位运算知道下一个该做谁

### 14. Redux 核心原理（单向数据流）

**口述版：** Redux 核心是**单一 store + 纯函数 reducer + 单向数据流**：UI 只能通过 dispatch(action) 发起变更 → reducer 纯函数算出新状态（**不可变更新**）→ store 通知订阅者 → UI 重新渲染。**数据永远单方向流，绝不反向修改**。createStore 30 行就能实现骨架：getState（读状态）、dispatch（调 reducer 算新状态 + 通知订阅者）、subscribe（注册监听，返回取消函数）。三个铁律：**reducer 必须纯函数**（可预测、可测试、时间旅行）、**必须不可变更新**（返回新引用，React 靠引用比较感知变化）、**reducer 必须同步**（异步靠 thunk/saga 中间件——thunk 原理是让 dispatch 能接收函数）。React 连接靠 **Provider + useSelector（基于 useSyncExternalStore）**。

- 单向数据流的价值：状态变更可追踪、可预测、可调试
- dispatch 内同步执行 reducer；副作用放中间件，完成后 dispatch 同步 action

### 15. Redux vs Zustand

**口述版：** Redux 是**单一 store + action/reducer + 不可变更新**的规范架构，强在**可预测性和生态**（devtools、saga、reselect）；Zustand 是**无 reducer、无 Provider、按 selector 细粒度订阅**的轻量库，强在**代码量和性能**。两者底层都是 useSyncExternalStore，差在**订阅粒度**：Zustand 对每个 selector 做输出比较，**没选中的字段变化不重渲染，优化是白送的**；Redux 的 useSelector 默认引用比较，返回新对象要手动 useShallow/reselect 优化。选型：大团队复杂状态、需要规范和时间旅行调试选 Redux；中小项目、性能敏感、想在 React 外使用状态（store 是普通对象，可在定时器/路由守卫里用）选 Zustand。

- Zustand 无 Provider 原理：store 是模块级普通对象（getState/setState/subscribe），hook 直接订阅
- 两者可以共存（新项目 Zustand 起步，复杂了引入 RTK）

### 16. React 19 新特性

**口述版：** React 19 的核心是**让异步更新和表单开发变简单**。四大重点：① **Actions 体系**——useActionState（表单提交状态 + isPending）、useFormStatus（子组件读父表单提交状态，自动禁用按钮）、useOptimistic（乐观更新，先变后验）、form action + async transition；② **ref 直接作为 prop**，forwardRef 退役；③ **use()** 渲染期间读 Promise 或 Context；④ **文档元数据** title/meta/link 直接写在组件里自动提升到 head。配套 **React Compiler**（编译期自动 memo，告别手动 useMemo/useCallback）。废弃：forwardRef、函数组件 defaultProps、ReactDOM.render。

- 记忆：Actions 三件套 = useActionState（提交状态）+ useFormStatus（按钮禁用）+ useOptimistic（先变后验）
- React Compiler 是独立编译器（Babel 插件），配 React 19 效果最好；官方建议先写普通代码，优化交给编译器

### 17. use() Hook

**口述版：** use() 是**渲染期间读取资源**的 Hook：读 Promise（配合 Suspense 挂起等待）或 Context（替代 useContext）。和普通 Hook 最大区别：它是**读取而不是注册**，所以可以在条件语句、循环里调用，**打破 Hook 顶层调用规则**。底层原理：**use(promise) 在 Promise 未完成时抛出一个 Promise**，Suspense 捕获它渲染 fallback，resolve 后重渲染。注意：**错误交给 Error Boundary 而不是 try/catch**；**use 不会缓存数据**，必须保证每次渲染传同一个 Promise 引用（用 useMemo 缓存），否则永远挂起死循环。**它是 async 组件不存在的理由**。

- 注册类 Hook 靠调用顺序（占链表位置），use 靠传入引用（不占位置）
- 数据获取库（TanStack Query、SWR）都用这个机制接入

### 18. 受控组件 vs 非受控组件

**口述版：** 核心区别是**值归谁管**。受控组件值由 **React state 控制**：value + onChange，每次输入经过 React，可以校验、转换、联动，代价是**每次输入都触发渲染**。非受控组件值由 **DOM 自己维护**：defaultValue 初始化 + ref 读取，**不触发渲染**、代码少，但拿不到实时值。**默认用受控**（可维护性），大表单、文件上传（只能非受控）、性能敏感用非受控。**React Hook Form 快的秘密就是非受控 + ref 注册**。value 和 defaultValue 不能混用：value = 受控，defaultValue = 非受控。

- 受控组件价值：值在 state 里，校验/转换/联动/提交都简单
- 半受控组件：外部传 value 走受控，不传用内部 state 兜底（AntD Input 的做法）

### 19. 虚拟列表原理

**口述版：** 虚拟列表**只渲染可视区域内的列表项**。三件套：① 一个**空容器撑出滚动条**（高度 = 数据量 × 行高，滚动行为真实）；② 根据 **scrollTop 算出可视区范围**（startIndex = scrollTop / itemHeight，endIndex = startIndex + 可视条数）；③ **只渲染范围内的项并用 translateY 定位**到正确位置。三个进阶点：**overscan** 上下多渲染几项防快速滚动白屏；**transform 定位走 GPU 合成层**避免重排；**动态行高**要预估 + 测量 + 缓存。10 万条数据只渲染 20 个 DOM 节点。手写 30 行就能实现。

- onScroll 高频触发：requestAnimationFrame 节流 + passive: true
- 与无限滚动关系：无限滚动解决加载，虚拟列表解决渲染数量，通常组合使用
- 数据 < 1000 时不需要虚拟列表（优化本身是成本）

### 20. React 性能优化

**口述版：** 原则：**先测量再优化**（DevTools Profiler + why-did-you-render），90% 的优化在优化不存在的性能问题。三条主线：**① 减少渲染次数**——React.memo（props 浅比较）+ useCallback/useMemo 稳定引用 + **状态下沉/上移**（state 在哪渲染范围就到哪，最高性价比）+ key 稳定；**② 降低渲染成本**——虚拟列表 + React.lazy 代码分割 + 组件拆分；**③ 减少主线程阻塞**——startTransition/useDeferredValue 让低优先级渲染让位 + 大计算扔 Web Worker。判断力：组件渲染快、频率低、树小就**别优化**，优化本身是复杂度。

- Context 的坑：value 要 useMemo 包住，高频变化状态别放 Context（用 Zustand）
- 面试话术：说场景 → 说手段 → 说原理（引用稳定/只渲染可视区/并发让位）→ 说收益（Profiler 验证）

### 21. 路由懒加载 + useNavigate / useParams / useLocation

**口述版：** 路由懒加载 = **React.lazy + Suspense + 动态 import()**：Webpack 遇到动态 import 自动拆 chunk，访问到该路由才加载对应代码。注意：lazy 组件**必须默认导出**、加 **Error Boundary** 处理 chunk 加载失败、hover 链接时**预加载**下一页面。三个 hooks：**useNavigate** 是编程式导航——表单提交后跳转、按钮点击跳转、navigate(-1) 后退、replace 替换历史、state 传参；**useParams** 读路径参数（/user/:id 拿 id，注意是字符串要 Number 转换）；**useLocation** 读当前 location——query 用 URLSearchParams、读 navigate 传的 state、useEffect 依赖 location 做埋点和滚动复位。记忆：**navigate 写，params/location 读；Link 声明式，navigate 命令式**。

- 记忆链：navigate('/user/123', { state }) → useLocation 读 state，useParams 读 id
- Link 渲染成 a 标签（可右键新标签、SEO 友好），逻辑跳转用 navigate

### 22. BrowserRouter vs HashRouter

**口述版：** 两者都是**不刷新页面换 URL 并更新视图**，手段不同。**BrowserRouter 用 HTML5 History API**：pushState/replaceState 不刷新改 URL 但**不会触发任何事件**，要手动通知 React 更新状态；popstate 只在浏览器**前进后退**时触发。URL 美观但**要服务端配置 fallback**（Nginx try_files / historyApiFallback），否则**刷新 404**。**HashRouter 用 location.hash + hashchange**：改 hash 自动触发事件，**零服务端配置**、兼容老浏览器，但 URL 带 #、SEO 差。正式项目选 BrowserRouter + 服务端配置，纯静态部署选 HashRouter。

- 为什么 pushState 不触发 popstate：popstate 只在前进后退（或 back/forward）时触发
- 微前端（qiankun）子应用：HashRouter 最省心；BrowserRouter 要加 basename

### 23. Vite 中 Vue / React 是谁转译的

**口述版：** Vite 本身**只负责启动、模块解析和依赖预构建**，具体转译靠**插件**。Vue 由 **@vitejs/plugin-vue** 编译，底层是 **@vue/compiler-sfc**：template 编译成 render 函数、script 交给 esbuild、style 提取成 CSS。React 由 **@vitejs/plugin-react** 转译，底层是 **Babel**（转 JSX + 注入 fast refresh）；想更快换 **@vitejs/plugin-react-swc**（SWC 是 Rust 写的）。开发时 **esbuild** 做依赖预构建和按需转译（**不检查类型**，类型靠 tsc），生产用 **Rollup** 打包。Vite 快是因为**开发时不打包**：浏览器原生 ESM 按需加载，只转译被请求的那个文件。

- .vue 是自定义格式 esbuild 不认识，必须插件；JSX 是 esbuild 原生支持
- 为什么 React 用 Babel 不用 esbuild：fast refresh 注入 + Babel 插件生态；要更快换 SWC

### 24. Context API 性能问题与优化

**口述版：** Context 的核心性能问题是**广播式订阅**：Provider 的 value 一变，**所有消费者组件（以及子树）全部重渲染，无论用没用变化的数据**，而且 **React.memo 拦不住**——memo 只比较 props，Context 更新通过 fiber 的依赖标记直达，不经过 props 比较。优化三板斧：**① 按领域拆分 Context**（user/theme/locale 分开，缩小广播范围）；**② value 用 useMemo 稳定引用**（不包 useMemo 等于每次渲染都换引用，所有消费者必重渲染，这是必做项）；**③ 高频变化的状态移出 Context**（表单输入、实时数据用 Zustand 细粒度订阅）。选型记忆：**低频用 Context，高频用 Zustand。**

- 消费者重渲染会带崩整个子树 → 消费组件要"轻"，重逻辑放 memo 子组件
- 判断标准：变化频率高 + 消费面广 → 不适合 Context
- React 19 的 use(Context) 没解决性能问题（机制相同）

### 25. Context 原理

**口述版：** Context 是**跨层级共享数据的广播订阅机制**：createContext 创建 context 对象（**内部存值 + 提供 Provider/Consumer**）；**Provider 负责写值，useContext 负责读值 + 在 fiber 上登记订阅**。更新传播不走 props：Provider 的 value 变化 → Object.is 比较 → **propagateContextChange 向下遍历**，找到所有登记过该 context 的 fiber（**fiber.dependencies 链表**）→ 直接打更新标记 → 重新渲染。**这就是 memo 拦不住的原因**（两条不同链路：memo 是 props 过滤器，Context 是依赖标记直达）。context 对象存**两个值**（_currentValue 和 _currentValue2）：因为双缓冲下 current 树和 workInProgress 树可能读到不同版本的值，各存一份保证并发一致性。

- 消费者读的是"渲染路径上最近的 Provider 写过的值"（没有则拿默认值）
- commit 阶段 checkIfContextChanged 校验两棵树的值，确定真的变了才渲染
- Context 更新同样走 Lane 优先级体系

### 26. 手写简版 useState（闭包 + 链表）

**口述版：** useState 的状态存在**链表节点**上，对应 fiber 的 memoizedState。挂载时创建节点，更新时**按调用顺序复用节点、不重建**。setState 通过**闭包捕获住自己对应的节点**，所以引用恒定、永远改对地方，支持函数式更新（基于节点上的最新值计算）。每次渲染从链表头按顺序遍历——**这就是 Hook 不能条件调用的原因**：条件调用会让链表遍历顺序错位，后面的 Hook 全拿错状态。

- 闭包捕获节点 = dispatch 引用恒定的原理
- 链表复用节点 = 状态能跨渲染保存的原理
- rerender 时指针回到链表头，从头按顺序遍历

### 27. 手写简版 useEffect（依赖对比）

**口述版：** useEffect 在同一个链表上，节点存 `{ deps, cleanup }`。每次渲染用 **Object.is 逐个比较 deps**：**首次执行**（无 prevDeps）、**不传 deps**（每次渲染都执行）、**deps 有元素变化**，三者任一触发执行。执行顺序永远是**先 destroy 旧的 cleanup、再 create 新的**。组件卸载时 React 会额外调用所有 cleanup。

- 浅比较（Object.is）不是深比较
- deps 不传 = 每次都执行（配合 setState 易死循环）
- cleanup 机制 = 副作用不泄漏的保证

### 28. 手写 useFetch（取消请求、loading、error）

**口述版：** useFetch 的核心是**四件套**：**AbortController** 提供取消能力、**isCancelled 标记防竞态**、**cleanup 里 abort + 置标记**、**AbortError 主动忽略**。依赖 url，url 变化重新请求。**防竞态是关键**：快速切换 url 时旧请求可能比新请求后返回（竞态），只有**最后一次请求**的结果允许 setState，否则会渲染错误数据。

- 主动讲竞态问题 = 面试加分点（多数人漏）
- AbortError 是主动取消的报错，必须忽略（不是真错误）
- 返回 { data, loading, error } 三态，配合 Suspense/loading UI

### 29. 简版 VDOM + Diff

**口述版：** 简版 VDOM 三步：**h 函数创建 VNode**（type/props/children）、**createElement 递归转真实 DOM**、**diff 做同层比较**。diff 规则：都没有 → 新增；旧有新增无 → 删除；文本变化 → 改 textContent；**类型不同 → 整体替换**（不深入比较子树，这是 React 的核心假设）；**类型相同 → 更新 props + 递归 children**。真实 React 在此基础上加了 key 复用和 lastPlacedIndex 移动判断。

- 直接体现 React 三个 diff 假设（同层 / 类型 / key）
- 递归 + 类型判断就是 diff 的全部骨架
- 面试手写时先写骨架再补 key，比直接写完整版稳

### 30. 简版事件委托

**口述版：** 事件委托三件套：**委托到根容器统一监听**（减少监听器、动态元素免绑定）、**合成事件对象统一接口**（target/preventDefault/stopPropagation）、**模拟捕获（根到目标）和冒泡（目标到根）两阶段**。真实 React 的区别：收集路径沿 **fiber 树**而不是 DOM 树——所以合成事件的 **stopPropagation 拦不住原生冒泡**（原生事件早已冒到根容器）。

- 与 5 号合成事件原理题联动（同一套知识）
- 委托的好处：内存少 + 动态元素天然生效
- 两阶段顺序：先捕获再冒泡（和原生一致）

### 31. React 底层细节加分清单（20 条）

> 每个细节都是"读过源码/踩过坑"的体现，面试时主动抛出来能拉开差距。每条标注联动题号，复习时对照。

**一、事件系统**

**细节 1：React 的 onChange 是假的（自己实现的）**
原生 change 是**失焦才触发**，React 的 onChange **输入即触发**（合成事件模拟，统一各浏览器行为）。
🔗 联动：5 号合成事件

**细节 2：事件委托是"插件体系"分发的**
SimpleEventPlugin（click 等通用）、ChangeEventPlugin（模拟 change）、EnterLeaveEventPlugin（mouseenter/leave）等插件各负责一类事件的合成与派发。
🔗 联动：5 号

**细节 3：事件派发沿 Fiber 树，不走 DOM 树（Portal 的体现）**
Portal 里的子组件事件**冒泡到 React 树上的祖先**而非 DOM 树祖先——收集路径走 fiber 的 return 指针。这也是"合成 stopPropagation 拦不住原生冒泡"的根源。
🔗 联动：5 号、30 号

**细节 4：委托挂 root，事件函数存 fiber 上**
委托只解决监听器数量；处理函数存在 fiber 节点上，派发时从目标 fiber 沿 return 向上收集再执行——这就是动态元素天然生效 + 执行顺序按 fiber 树的原理。
🔗 联动：5 号

**二、渲染与 Fiber**

**细节 5：render 阶段是 beginWork / completeWork 两阶段遍历**
**beginWork（递推）**从上往下创建/复用子 fiber，**completeWork（归）**从下往上收尾（处理 props、标记 flags）。遍历指针是显式的而不是 JS 调用栈——所以能中断。
🔗 联动：1 号 Fiber、3 号 render/commit

**细节 6：fiber.updateQueue 一个字段两种用途**
class 组件存**更新队列**（setState update 链表）；function 组件存 **effect 环形链表**（useEffect 的 effect 对象）。同一字段按组件类型复用。
🔗 联动：6 号 useState、8 号 useEffect

**细节 7：双缓冲切换 = alternate 指针互换**
commit 后 `root.current = root.current.alternate`，两棵树的 fiber **互相复用**而非重建——这是"每次渲染大量复用对象、只有变化部分重建"的性能来源。
🔗 联动：1 号 Fiber

**细节 8：bail out 有两种（分层记忆）**
**fiber 级**：`fiber.lanes & renderLanes === 0` → 整棵子树跳过（靠 childLanes 快速判断）；**组件级**：组件函数执行后返回相同的 ReactElement（Object.is）→ 跳过该组件。
🔗 联动：4 号 Diff、6 号 useState

**细节 9：组件函数执行了 ≠ DOM 变了**
同类型组件默认不深比较 props（除非 memo），直接执行函数，靠返回元素对比 + Diff 决定是否更新 DOM。
🔗 联动：20 号性能优化

**三、状态更新**

**细节 10：eagerState 急迫计算（"相同值不渲染"的完整实现）**
dispatch 时**立即**用当前 state + action 算一次新值，Object.is 相同 → **直接 bail out，连调度都不做**。
🔗 联动：6 号 useState

**细节 11：baseQueue + pendingQueue（交叉更新处理）**
函数式更新（c => c+1）能累加，因为 update 队列分 baseQueue（上次遗留）和 pendingQueue（新来的），render 时**按序依次计算**；传值则后者覆盖。
🔗 联动：6 号、7 号批处理

**细节 12：render 期间可以 setState（但只允许一次）**
组件函数执行中 setState 会触发同一次 render 的重算（render phase update），React 允许但限制次数，超限报错。
🔗 联动：6 号

**四、Hooks**

**细节 13：Hook 对象结构因 Hook 而异**
useState 存 `{ memoizedState: 值, queue }`；useEffect 存 effect 对象（create/destroy/deps/tag）；useMemo 存 `[value, deps]`；useRef 存 `{ current }`。
🔗 联动：6/8/9/10 号

**细节 14：为什么 Hook 不能脱离组件调用？**
Hook 靠 **ReactCurrentDispatcher**（全局 dispatcher 引用）分发到 mount/update 实现；组件渲染之外 dispatcher 是空的 → 报 "Invalid hook call"。
🔗 联动：6 号

**细节 15：effect 的 tag 标记（执行时机开关）**
tag 决定执行阶段：`Passive`（绘制后）、`Layout`（layout 阶段）、`HasEffect`（deps 变了要执行）。commit 按 tag 筛选执行。
🔗 联动：8 号 useEffect/useLayoutEffect

**五、调度与并发**

**细节 16：workLoopSync vs workLoopConcurrent**
同步模式（legacy ReactDOM.render）一次跑完不检查；并发模式（createRoot）**每处理一个 fiber 检查 shouldYield**（时间片）和 getNextLanes（抢占）。这就是"为什么 createRoot 才有并发"。
🔗 联动：12 号并发

**细节 17：5ms 时间片 + shouldYield 检查点**
让位发生在**每个 fiber 处理完后的检查点**（不是任意位置），shouldYield 用 performance.now() 比较。
🔗 联动：12 号

**细节 18：Lane 位运算三个 O(1)**
合并 `|`、交集 `&`、取最高优先级 `& -lanes`（最低位 1 = 最高优先级）。为什么低位是高优先级：一步位运算取出，快。
🔗 联动：13 号 Lane

**细节 19：Scheduler 用 MessageChannel 的完整原因**
① setTimeout 嵌套 5 层以上被 clamp 到 4ms（不可控）；② requestIdleCallback 兼容性和触发时机不可控；③ MessageChannel 是宏任务、无延迟、每帧可靠让出主线程。
🔗 联动：12 号

**六、安全与边界**

**细节 20：$$typeof 防 XSS（JSON 注入攻击）**
ReactElement 的 `$$typeof: Symbol.for('react.element')` 是防注入校验：JSON 无法序列化 Symbol，服务端返回的伪造元素（如 {type:'script'}）没有这个标记 → React 拒绝渲染。
🔗 联动：2 号 createElement

# 三、Vue 与微前端

## 8. Vue 核心

**Q: Vue 3 Composition API 相比 Options API 的优势？**

- 逻辑复用：composables 替代 mixins（this 来源清晰、命名冲突可避免）
- 代码组织：相关逻辑聚合在一起，而非分散在 data/methods/computed 各块
- TypeScript 支持：组合式 API 天然适合类型推导

**Q: Vue 3 的响应式原理？和 Vue 2 的区别？**

- Vue 2：Object.defineProperty 劫持属性，无法检测新增/删除属性（需 $set）、数组索引修改
- Vue 3：Proxy 代理整个对象，支持数组、Map/Set、新增属性自动响应

**Q: Vue 迁移到 React 你经历了什么？怎么说服团队？**

> IOT 平台存量是 Vue 2（Element UI），新业务统一用 React（历史原因：团队 React 储备更强，Ant Design Pro 在中后台场景的开箱即用程度高于 Element Plus）。迁移策略不是一次性重写——通过 qiankun 让 Vue 和 React 子应用共存，新功能用 React 写，存量 Vue 模块在需要大改时逐步迁移。关键是渐进式，不阻塞业务迭代。

## 9. qiankun 微前端

**Q: qiankun 的核心原理？**

- 基于 single-spa，提供开箱即用的子应用加载、沙箱隔离、样式隔离
- **JS 沙箱：** 快照沙箱（SnapshotSandbox，单实例）和代理沙箱（ProxySandbox，多实例），通过 Proxy 劫持 window 操作
- **CSS 隔离：** strictStyleIsolation（Shadow DOM）和 experimentalStyleIsolation（CSS 前缀作用域）
- **生命周期：** bootstrap → mount → unmount，子应用需导出这三个方法

**Q: qiankun 的 JS 沙箱怎么工作的？**

- **ProxySandbox（默认）：** 为每个子应用创建 fakeWindow（Proxy），子应用对 window 的读写操作被拦截在 fakeWindow 上，不污染真正的 window。子应用卸载时 fakeWindow 随之销毁。
- **关键：** 激活子应用时将 fakeWindow 设为当前，代码中的全局变量操作实际落在隔离的 Proxy 上

**Q: 主子应用通信怎么做的？**

> 通过 qiankun 的 initGlobalState 定义全局状态池，主子应用都可以通过 onGlobalStateChange 监听和 setGlobalState 修改。我们约定只传必要的共享数据（用户信息、当前租户、主题配置），避免全局状态膨胀。复杂通信场景用自定义事件或共享 API 层，不依赖全局状态。

## 10. 构建工具

**Q: Webpack 和 Vite 的核心区别？**

- Webpack：Bundle 模式，先打包再启动，大项目冷启动慢。基于 JS 模块解析，需要各种 loader/plugin

# 五、跨端开发

## 12. 小程序与插件

**Q: 支付宝小程序和 H5 的核心差异？**

- **运行环境：** 小程序是双线程架构（渲染层 WebView + 逻辑层 JSCore），H5 是单线程
- **能力限制：** 小程序没有真实的 DOM/BOM API，不能直接操作 DOM；大部分 API 是异步的
- **包限制：** 小程序有包大小限制，需要分包加载、资源懒加载
- **JSAPI 能力：** 小程序可以调用更多原生能力（扫码、支付、蓝牙等），H5 内嵌 WebView 只能通过 JSBridge

**Q: 小程序插件怎么开发的？和普通小程序有什么区别？**

> 支付宝小程序插件是独立的功能组件，可以被其他小程序引用。和普通小程序的区别：插件有自己的独立上下文，不能直接访问宿主小程序的页面栈和数据。通信通过插件 API 暴露的接口。我们开发的插件面向商户，提供支付能力封装，30+ 商户接入使用。

**Q: 小程序包体积优化怎么做的？**

> 分包加载（主包只放核心页面）、图片资源上 CDN 不打包、公共组件抽离到独立分包、无用依赖清理。通过分析工具（支付宝 IDE 的包体积分析）找大文件，图标用 iconfont 代替图片。

## 13. WebView 与 JSBridge

**Q: WebView 白屏怎么排查和解决？**

- **排查：** 检查网络请求是否成功、JS 是否有阻断性报错、WebView 是否加载完成、原生侧是否正常初始化
- **兜底方案：** WebView 加载超时（如 5 秒）→ 自动切换为原生错误页 + 重试按钮；原生侧监听 WebView 加载状态，异常时重新加载
- **优化：** 预加载 WebView 实例（WebView 池）、静态资源离线包、骨架屏

**Q: 你设计的 JSBridge 协议规范包含哪些能力？**

> 三大设计原则：
> 1. **Promise 化封装：** 所有原生调用返回 Promise，统一异步处理
> 2. **版本兼容：** 协议带版本号，原生侧按版本号路由到对应实现，老版本 API 保持向后兼容
> 3. **降级策略：** 原生 Bridge 不可用时（如旧版 App），降级为 URL Scheme 方案或提示用户升级
>
> 具体实现：call(method, params) → Promise，内部通过 callbackId 关联请求和响应。支持同步调用（特定场景，如获取设备 ID）和异步调用（大部分场景）。

**Q: iOS 和 Android WebView 遇到过哪些兼容坑？**

- iOS WKWebView 本地文件跨域：Ajax 被 CORS 拦截，需原生配置或改用 http://localhost
- iOS 100vh 问题：地址栏占用视口空间，用 dvh 或 JS 动态设置
- Android 字体缩放：系统字体设置影响 WebView 内字体大小，CSS 用固定 px
- position: fixed + 软键盘 Android：键盘弹出导致 fixed 元素错位
- iOS 输入框被键盘遮挡：键盘不触发 resize，需监听 focusin 手动滚动

# 六、IOT 项目深挖

## 14. 微前端架构整体设计

**Q: 你们微前端架构的整体设计是什么样的？一句话说清楚。**

> 基座（主应用）+ N 个子应用，基座负责路由分发、全局状态、统一登录鉴权；子应用通过 qiankun 注册接入，各自独立开发、独立部署。技术栈不限——Vue 存量模块和 React 新模块共存运行。

**Q: 为什么选择 qiankun 而不是 Module Federation 或 iframe？**

> | 方案 | 优点 | 缺点 |
> |------|------|------|
> | qiankun | 技术栈无关、沙箱隔离完善、社区活跃 | 需要改造子应用（导出生命周期） |
> | Module Federation | 原生 Webpack 支持、运行时共享依赖 | 技术栈绑定（需同一构建体系） |
> | iframe | 隔离最彻底 | 通信成本高、URL 不同步、性能差、弹窗只能 iframe 内部 |
>
> 我们场景是 Vue + React 混用，qiankun 是最优解。

**Q: 子应用接入规范包含哪些内容？**

> 1. 必须导出 bootstrap/mount/unmount 生命周期
> 2. 必须配置 webpack publicPath 为子应用部署路径
> 3. 打包格式为 umd，注入到 window
> 4. CSS 命名规范：BEM + 子应用前缀，配合 experimentalStyleIsolation
> 5. 共享依赖声明：React、ReactDOM、Ant Design 等由基座提供（externals），避免重复加载
> 6. 路由前缀：每个子应用有独立的 base path

**Q: 主子应用共享依赖怎么管理？版本冲突怎么办？**

> 基座通过 webpack externals 暴露 React、ReactDOM、Ant Design 等公共依赖。子应用在 webpack externals 中声明使用基座提供的版本。版本冲突通过 qiankun 的 `excludeAssetFilter` 排除子应用打包的公共依赖。
>
> 如果两个子应用需要不兼容的依赖版本（如 Ant Design 4 vs 5），通过基座的 webpack alias 处理版本映射。实际策略是：推进统一升级，不加长期兼容多个主版本的逻辑以免复杂度失控。

## 15. Formily 低代码表单引擎

**Q: 为什么选 Formily 而不是其他方案？**

> 对比过三种方案：
> 1. **纯手写表单：** 可定制但不通用，中后台 80% 的表单是重复劳动
> 2. **FormRender（阿里开源）：** 基于 JSON Schema，简单场景够用，复杂联动支持弱
> 3. **Formily：** Schema + 响应式联动，支持复杂逻辑编排，有可视化设计器，组件扩展性好
>
> 我们的场景有大量设备配置表单，字段之间联动复杂（A 选"海报投放"→ 显示 BCD 字段 → B 选"定时"后显示时间选择器），Formily 的 reactions 机制天然适合这种场景。

**Q: Formily 的字段联动响应式依赖模型怎么设计的？**

> Formily 基于 observable 响应式系统，字段值变化自动触发 reactions。核心机制：
> 1. 声明式联动规则：在 Schema 中定义 x-reactions，描述"当某字段变化时做什么"
> 2. 依赖自动收集：reaction 中访问的字段值会被自动追踪为依赖
> 3. 联动类型：字段显隐（x-display）、状态（x-pattern：可编辑/只读/禁用）、数据源（x-data）、校验规则（x-validator）
>
> 循环依赖检测：在设置联动规则时构建字段依赖图，拓扑排序检测环。发现环 → 告警并拒绝该规则。运行时也设置了递归深度上限（5 层）作为兜底。

**Q: 20+ 物料组件的设计规范是什么？**

> 组件设计遵循三个原则：
> 1. **标准化 Props：** 统一 value/onChange 受控模式，兼容 Formily 的 connect 和 mapProps
> 2. **组合优于继承：** 通过 Formily 的 x-component-props 传参而非创建特殊组件变体
> 3. **业务语义封装：** 如"设备选择器"、"地区多选"、"时间范围选择"等具业务含义的组件，内部封装数据获取逻辑
>
> 发布流程：组件开发 → Code Review → 文档 + Demo → 发布到内部物料平台 → 设计器中可用

## 16. AI Agent 与 SSE 流式渲染

**Q: SSE 流式渲染方案怎么设计的？**

> ```
> 前端 fetch (stream: true) → 后端 LangChain Agent → LLM (streaming)
>                           ↑                              ↓
>                     SSE token 流                    token by token
>                           ↓
>     前端 ReadableStream.getReader() 逐条读取
>                           ↓
>     解析 SSE data 字段 → Markdown 增量渲染 + 自定义组件替换
> ```
>
> **断线重连：** 记录最后收到的 messageId，重连时通过 Last-Event-ID header 告诉服务端从断点续传
> **超时降级：** 30 秒无响应 → 提示用户"正在思考中，请稍候"；60 秒 → 超时兜底，返回已完成部分 + 错误提示
> **异常容错：** 单个 token 解析失败不影响后续（try/catch 包裹），Markdown 语法异常时用纯文本降级展示

**Q: 多轮对话上下文隔离怎么做的？**

> 问题：多个用户或同一用户多会话情况下，如果后端共享上下文（如全局 memory），会导致会话 A 的对话被会话 B 看到。
>
> 解决方案：
> 1. **前端维护 sessionId：** 每个会话生成唯一 sessionId（UUID），通过请求头传递
> 2. **后端按 sessionId 隔离上下文：** 每次请求带上 sessionId，服务端用 Map<sessionId, memory> 管理
> 3. **清理机制：** 30 分钟无活动的会话自动清理 memory，前端切回后重新初始化

**Q: Schema 自动生成的 few-shot 策略怎么设计的？**

> Prompt 模板结构：
> ```
> 系统角色：你是 Formily Schema 生成器，将用户需求转为 JSON Schema
> 
> Schema 规范：{字段类型、联动规则语法、示例}
> 
> Few-shot 示例 1：用户需求 → 对应 Schema
> Few-shot 示例 2：...
> Few-shot 示例 3：...
> 
> 用户需求：{用户输入}
> ```
>
> Few-shot 样本选取策略：
> - 从历史成功的 Schema 配置中选取 3-5 个覆盖不同场景的典型样本
> - 按场景分类（设备配置、活动配置、权限配置等），动态匹配最相关的样本
>
> 验证层：
> 1. JSON Schema 格式校验（结构层）
> 2. Formily 无头渲染环境挂载测试（业务层，检查是否产生运行时错误）
> 3. 不通过的标记为"需人工审核"，通过的直接可用

# 七、五福项目深挖

## 17. NFC 状态机设计

**Q: 7 阶段状态机为什么不用 XState 而用 Zustand 手写？**

> 考虑过 XState，但几个原因选了 Zustand：
> 1. 五福项目时间紧，团队对 Zustand 更熟，XState 学习成本高
> 2. 状态转移逻辑不算极端复杂，不需要可视化状态图
> 3. Zustand 的 selector 机制天然支持精确渲染——状态变化只触发关联组件重渲染
> 4. 状态转移校验通过自定义 `transition(from, to, condition)` 工具函数实现，代码量小
>
> 实际也没用手写 if/else 状态机——分了两层：Zustand store 管当前状态和上下文数据，独立的 stateMachine 模块管合法转移和副作用（side effects）。

**Q: 7 个阶段的设计逻辑是什么？**

| 阶段 | 含义 | 触发条件 |
|------|------|---------|
| 权限检测 | 检查 NFC 权限、登录状态、活动资格 | 进入页面 |
| 引导拦截 | 未授权或不符合条件时的引导页 | 权限检测失败 |
| 开始游戏 | 等待用户碰一碰 | 权限通过 |
| 碰撞中 | NFC 已触发，等待配对 | 检测到 NFC 事件 |
| 配对查询 | 轮询服务端查询配对结果 | NFC 数据上报完成 |
| 出奖 | 展示红包/奖品 | 配对成功 + 出奖结果返回 |
| 异常兜底 | 网络异常/超时/服务端错误 | 任何阶段发生异常 |

**Q: 如果服务端配对失败（比如两个设备上报的数据匹配不上），怎么处理？**

> 服务端配对逻辑：通过 NFC tag ID + 时间窗口（3 秒内）匹配两台设备。匹配不上有两种情况：
> 1. 只有一方上报了 → 另一方进入超时（10 秒），进入异常兜底，提示"配对超时"
> 2. 双方上报但信息不匹配（极少，可能是 Bug）→ 服务端返回"配对失败"，两端同时进入异常兜底
>
> 兜底体验：展示友好提示 + "再试一次"按钮，重新进入"开始游戏"阶段。不会让用户卡在中间态。

## 18. 动画分级降级

**Q: grading 的评分模型具体怎么做的？**

> 六维度加权评分，总分 100：
> - **设备型号（40 分）：** UA 解析，维护设备性能表。iPhone 15 Pro → 40 分，iPhone 8 → 15 分
> - **GPU 信息（20 分）：** WebGL RENDERER 字符串解析 GPU 型号
> - **CPU 核心（10 分）：** navigator.hardwareConcurrency，>=8 核满分
> - **内存（10 分）：** navigator.deviceMemory，>=8GB 满分
> - **屏幕（10 分）：** 分辨率 + DPR，过高分辨率的老设备拖不动
> - **OS 版本（10 分）：** 相同硬件不同系统版本性能差异大
>
> 阈值：>=70 高档 → 完整 Mars 粒子动画；40-69 中档 → 简化动画（减少粒子数）；<40 低档 → 静态图 + CSS transition
>
> 关键设计：评分脚本内联在 HTML `<head>` 中，body 渲染前完成决策，避免中途切换的视觉跳变。

**Q: Mars 引擎（@galacean/effects）是干什么的？你在其中的角色？**

> Mars 是蚂蚁内部的动效渲染引擎（现已开源 @galacean/effects），基于 WebGL 的粒子特效引擎，用于五福活动的红包雨、开宝箱等复杂动画效果。
>
> 我的角色是**前端集成**——不是开发 Mars 引擎本身，而是：
> 1. 在业务页面中集成 Mars 动画，控制动画的加载、播放、暂停、销毁
> 2. 设计分级降级策略，保证低端机不因动画卡死
> 3. 优化动画资源的加载时机和缓存策略

## 19. 资源加载优化

**Q: FCP 从 4.5s 到 2.0s 是怎么做到的？每一步贡献了多少？**

> 4.5s 的来源分析（通过 Performance API + 埋点）：
> | 阶段 | 耗时 | 优化 | 优化后 |
> |------|------|------|--------|
> | HTML 下载 + 解析 | 0.6s | CDN + Brotli | 0.4s |
> | 主 JS Bundle 下载 | 1.8s | 代码分割 + 懒加载 | 0.5s |
> | Mars 引擎加载 | 1.2s | 按需加载（出奖阶段才加载） | 0s（不计入 FCP） |
> | 接口请求 | 1.0s | 预请求（页面加载时并行发） | 0.2s |
> | 首屏渲染 | 0.9s | 关键 CSS 内联、骨架屏 | 0.9s（感知更快） |
>
> FCP 4.5s → 2.0s 的关键三招：
> 1. Mars 引擎从首屏加载移到出奖阶段懒加载（减 1.2s）
> 2. CDN 预缓存关键资源 + HTTP/2（减 0.8s）
> 3. 接口预请求，页面 onLoad 时并行调用（减 0.5s）

## 20. 项目管理和团队

**Q: 作为平台前端负责人，你日常怎么分配需求和管理进度？**

> 需求评审后我会先做技术方案拆解，评估各模块工作量和依赖关系。和产品对齐优先级后，用看板管理任务。每周同步进度，识别风险提前暴露。对新人我会分配相对独立、风险可控的模块，自己扛关键路径和新技术攻坚。

**Q: 你带教的新人怎么培养的？**

> 分三个阶段：
> 1. **上手期（第 1-2 周）：** 安排熟悉业务 + Code Review 旁听 + 分配小 Bug 修，建立 Code Review 准入标准意识
> 2. **成长期（1-3 月）：** 带他们做完整需求，我做方案评审和代码 Review。重点培养"为什么这么写"的思考习惯而非"怎么写"
> 3. **独立期（3 月+）：** 独立承担模块，我退出日常 Review，只在关键决策时介入
>
> 两个带教的新人都通过了转正考核。

**Q: 遇到和你技术方案分歧较大的同事，怎么处理？**

> 技术上分歧很正常，我的原则是"用数据说话、从业务出发"。先搞清楚双方方案的差异点是什么——性能、可维护性、开发成本还是扩展性。如果分歧在具体指标（如性能），做个 POC 对比数据。如果分歧在风格偏好，以团队规范和大多数人意见为准。最终目标是项目能交付好，不是证明自己更对。

**Q: 线上出过什么问题？怎么处理的？**

> 说一个案例。有一次设备运营平台的表单模块突然白屏，大量运营操作受阻。我作为应急响应 Owner 的处理流程：
> 1. **定位（2 分钟）：** 查看监控，发现是当天下午的一次发版引入了 Formily Schema 解析异常。快速定位到有问题的 commit
> 2. **止血（5 分钟）：** 回滚到上一个稳定版本，业务恢复
> 3. **复盘（故障后）：** 原因是 Schema 新增了一个联动规则，但缺少对应字段导致解析失败。根因是缺少 Schema 变更的自动化校验卡口。改进措施：发布流程中增加 Schema 合法性校验的 CI 步骤，Schema 变更必须经过 Code Review
