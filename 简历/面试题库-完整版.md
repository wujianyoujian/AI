# 一、前端基础

## 1. 浏览器渲染机制

**Q: 从输入 URL 到页面渲染的完整过程？**

- **网络阶段：** DNS 解析 → TCP 连接（TLS 握手）→ HTTP 请求 → 服务器响应
- **解析阶段：** HTML 解析（DOM 树）→ CSS 解析（CSSOM 树）→ 遇到 `<script>` 阻塞解析（除非 async/defer）
- **渲染阶段：** DOM + CSSOM → Render Tree → Layout（回流）→ Paint（重绘）→ Composite（合成层）
- **关键优化点：** 减少阻塞资源、避免强制同步布局、利用 GPU 合成层

**Q: 回流和重绘的区别？什么操作会触发回流？**

- **回流（Reflow）：** 改变元素几何属性（宽高、位置），触发重新布局。成本高。
- **重绘（Repaint）：** 只改变外观（颜色、阴影），不改变布局。成本较低。
- **触发回流的操作：** offsetTop/Left 读取、display: none、添加/删除 DOM、改变字体大小、resize 窗口
- **优化：** 用 class 批量修改样式、DocumentFragment 批量插入、transform 代替 left/top（跳过 Layout）

**Q: 合成层是什么？哪些属性会创建合成层？**

- 合成层由 GPU 独立绘制，不触发回流和重绘
- 触发条件：3D transform、video/canvas/iframe 元素、will-change、opacity 动画、filter
- 陷阱：过多合成层导致内存暴涨（层爆炸），需要合理控制

## 2. Event Loop

**Q: 详细解释 Event Loop 机制？**

- JS 是单线程，通过事件循环实现异步
- **调用栈：** 同步代码执行的地方
- **任务队列分两种：**
  - **宏任务（MacroTask）：** script 整体、setTimeout、setInterval、I/O、UI 渲染、postMessage
  - **微任务（MicroTask）：** Promise.then/catch/finally、MutationObserver、queueMicrotask
- **执行顺序：** 执行一个宏任务 → 清空所有微任务 → 检查是否需要渲染 → 下一个宏任务
- **关键：** 微任务在当前宏任务结束后立即全部执行，渲染可能在宏任务之间也可能在之后（浏览器 16.6ms 一帧）

**Q: 这道经典题输出什么？**

```js
console.log(1)
setTimeout(() => console.log(2), 0)
Promise.resolve().then(() => console.log(3))
console.log(4)
```

> 1 → 4 → 3 → 2。当前宏任务执行 1 和 4，微任务队列执行 3，下一个宏任务执行 2。

## 3. Promise 与 async/await

**Q: Promise 的三种状态？all、allSettled、race、any 的区别？**

- 三种状态：pending → fulfilled / rejected（不可逆）
- `Promise.all`：全部成功才成功，一个失败就失败
- `Promise.allSettled`：等全部完成，不管成功失败，返回每项结果
- `Promise.race`：返回最先完成的结果（不管成功失败）
- `Promise.any`：返回第一个成功的结果，全部失败才失败（ES2021）

**Q: async/await 的原理？和 Promise 的关系？**

- async 函数返回 Promise；await 暂停函数执行直到 Promise 完成
- 本质是 Generator + Promise 的语法糖
- await 后面的代码相当于 `.then()` 里的回调（微任务）
- **错误处理：** try/catch 包裹 await，或 .catch() 链式调用

**Q: 多个 await 串行 vs Promise.all 并行？**

```js
// 串行 — 各等各的
const a = await fetchA()
const b = await fetchB()  // B 等 A 完成才开始

// 并行 — 同时发起
const [a, b] = await Promise.all([fetchA(), fetchB()])
```

## 4. TypeScript

**Q: TypeScript 中 type 和 interface 的区别？**

- interface：可被合并声明（declaration merging）、更适合描述对象形状、extends 继承
- type：可定义联合类型、交叉类型、元组、不能重复声明、功能更强大
- **选型：** 对外 API/组件 Props 用 interface（可扩展），内部工具类型用 type

**Q: 泛型怎么用？写一个泛型工具类型？**

```ts
// 实际场景：提取 API 响应中的 data 字段类型

type UserListRes = ApiResponse<{ users: User[]; total: number }>

// Pick / Omit / Partial / Required 等内置工具类型的原理
type MyPick<T, K extends keyof T> = { [P in K]: T[P] }
```

# 二、React 深度

## 5. React Fiber 架构

**Q: React Fiber 是什么？解决了什么问题？**

- React 16 重构的协调引擎，解决 Stack Reconciler 的同步递归不可中断问题
- **核心改进：** 可中断的异步渲染、优先级调度、双缓冲（current ↔ workInProgress 两棵树交替）
- **工作过程：** Render 阶段（可中断，构建 Fiber 树）→ Commit 阶段（不可中断，更新 DOM）
- **实际收益：** 大列表更新时不会阻塞用户输入，动画更流畅

**Q: React 的 Diff 算法三个假设？**

1. 只对同级元素比较，不跨层级
2. 不同类型的元素产生不同的树（div → span 会整个替换）
3. key 属性标识元素是否变化，优化列表渲染

**Q: key 的作用？为什么不能用 index？**

- key 帮助 React 识别哪些元素变了、添加了、删除了
- 用 index：如果列表重新排序，key 不变导致错误复用 DOM、状态错乱
- **最佳实践：** 用稳定的唯一 ID

## 6. Hooks 原理

**Q: useState 的原理？为什么不能在条件语句中调用？**

- React 通过**调用顺序**维护 Hook 链表（Fiber.memoizedState 单向链表）
- 每次渲染按相同顺序读取 Hook → 必须保持调用顺序稳定
- 放条件语句里 → 顺序变化 → 状态错位

**Q: useEffect 和 useLayoutEffect 的区别？**

- useEffect：渲染提交到屏幕后**异步**执行，不阻塞渲染，用于数据请求、订阅
- useLayoutEffect：DOM 更新后、浏览器绘制前**同步**执行，会阻塞渲染，用于 DOM 测量、避免闪烁

**Q: useMemo 和 useCallback 的区别和使用场景？**

- useMemo：缓存计算结果，依赖不变不重新计算
- useCallback：缓存函数引用，避免子组件不必要的重渲染
- **不要滥用：** 简单计算不需要缓存，配合 React.memo 使用才有意义

**Q: 自定义 Hook 解决过什么实际问题？**

> 比如做了一个 usePolling Hook：轮询查询任务状态直到完成或超时，支持指数退避、组件卸载自动取消、返回 loading/data/error 三态。把轮询逻辑从业务组件中抽离，10+ 个页面复用。

## 7. 状态管理

**Q: Zustand 和 Redux 的对比？你为什么选 Zustand？**

- Zustand：极简 API（create 一个函数搞定）、不需要 Provider 包裹、原生支持 selector 精确渲染、TypeScript 友好、包体积极小（<1KB）
- Redux：概念多（store/reducer/action/middleware）、需要 Provider、样板代码多、但生态成熟
- **选型理由：** 中后台项目不需要 Redux 的中间件生态和时间旅行调试，Zustand 够用且开发效率高

# 三、Vue 与微前端

## 8. Vue 核心

**Q: Vue 3 Composition API 相比 Options API 的优势？**

- 逻辑复用：composables 替代 mixins（this 来源清晰、命名冲突可避免）
- 代码组织：相关逻辑聚合在一起，而非分散在 data/methods/computed 各块
- TypeScript 支持：组合式 API 天然适合类型推导

**Q: Vue 3 的响应式原理？和 Vue 2 的区别？**

- Vue 2：Object.defineProperty 劫持属性，无法检测新增/删除属性（需 $set）、数组索引修改
- Vue 3：Proxy 代理整个对象，支持数组、Map/Set、新增属性自动响应

**Q: Vue 迁移到 React 你经历了什么？怎么说服团队？**

> IOT 平台存量是 Vue 2（Element UI），新业务统一用 React（历史原因：团队 React 储备更强，Ant Design Pro 在中后台场景的开箱即用程度高于 Element Plus）。迁移策略不是一次性重写——通过 qiankun 让 Vue 和 React 子应用共存，新功能用 React 写，存量 Vue 模块在需要大改时逐步迁移。关键是渐进式，不阻塞业务迭代。

## 9. qiankun 微前端

**Q: qiankun 的核心原理？**

- 基于 single-spa，提供开箱即用的子应用加载、沙箱隔离、样式隔离
- **JS 沙箱：** 快照沙箱（SnapshotSandbox，单实例）和代理沙箱（ProxySandbox，多实例），通过 Proxy 劫持 window 操作
- **CSS 隔离：** strictStyleIsolation（Shadow DOM）和 experimentalStyleIsolation（CSS 前缀作用域）
- **生命周期：** bootstrap → mount → unmount，子应用需导出这三个方法

**Q: qiankun 的 JS 沙箱怎么工作的？**

- **ProxySandbox（默认）：** 为每个子应用创建 fakeWindow（Proxy），子应用对 window 的读写操作被拦截在 fakeWindow 上，不污染真正的 window。子应用卸载时 fakeWindow 随之销毁。
- **关键：** 激活子应用时将 fakeWindow 设为当前，代码中的全局变量操作实际落在隔离的 Proxy 上

**Q: 主子应用通信怎么做的？**

> 通过 qiankun 的 initGlobalState 定义全局状态池，主子应用都可以通过 onGlobalStateChange 监听和 setGlobalState 修改。我们约定只传必要的共享数据（用户信息、当前租户、主题配置），避免全局状态膨胀。复杂通信场景用自定义事件或共享 API 层，不依赖全局状态。

# 四、工程化与性能优化

## 10. 构建工具

**Q: Webpack 和 Vite 的核心区别？**

- Webpack：Bundle 模式，先打包再启动，大项目冷启动慢。基于 JS 模块解析，需要各种 loader/plugin
- Vite：No-Bundle 模式（开发时），利用浏览器原生 ESM，按需编译，启动极快。生产用 Rollup 打包
- **Vite 快的原理：** 预构建依赖用 esbuild（Go 写的，快 10-100 倍）；源码按需编译，只编译浏览器请求的模块

**Q: 做过哪些构建优化？**

> Webpack 配置：代码分割（SplitChunks 抽 vendor + 公共模块）、Tree Shaking（ES Module + sideEffects: false）、DLL 预编译（Vite 不需要）、thread-loader 多线程编译。产物分析用 webpack-bundle-analyzer 找大包，lodash 换成 lodash-es + tree shaking，moment.js 换成 dayjs。

## 11. 性能优化

**Q: 首屏性能优化做过哪些？**

- **资源层面：** 代码分割 + 路由懒加载（React.lazy + Suspense）、CDN 加速、Gzip/Brotli 压缩、图片 WebP + 懒加载
- **渲染层面：** 关键 CSS 内联、非关键 CSS 延迟加载、骨架屏提升感知性能、SSR/预渲染（根据场景）
- **网络层面：** 接口预请求（prefetch）、关键数据并行加载、HTTP/2 多路复用
- **框架层面：** React.memo + useMemo/useCallback 避免不必要渲染、虚拟列表处理长列表

**Q: 做过性能监控吗？指标有哪些？**

> 五福活动上线了实时性能监控：FCP（首次内容绘制）、LCP（最大内容绘制）、TTI（可交互时间）、FPS（帧率）、JS 异常率、接口耗时和成功率。用 PerformanceObserver 采集，异常自动上报到内部监控平台。活动期间实时大盘监控，支持按设备型号、系统版本、地域下钻。

# 五、跨端开发

## 12. 小程序与插件

**Q: 支付宝小程序和 H5 的核心差异？**

- **运行环境：** 小程序是双线程架构（渲染层 WebView + 逻辑层 JSCore），H5 是单线程
- **能力限制：** 小程序没有真实的 DOM/BOM API，不能直接操作 DOM；大部分 API 是异步的
- **包限制：** 小程序有包大小限制，需要分包加载、资源懒加载
- **JSAPI 能力：** 小程序可以调用更多原生能力（扫码、支付、蓝牙等），H5 内嵌 WebView 只能通过 JSBridge

**Q: 小程序插件怎么开发的？和普通小程序有什么区别？**

> 支付宝小程序插件是独立的功能组件，可以被其他小程序引用。和普通小程序的区别：插件有自己的独立上下文，不能直接访问宿主小程序的页面栈和数据。通信通过插件 API 暴露的接口。我们开发的插件面向商户，提供支付能力封装，30+ 商户接入使用。

**Q: 小程序包体积优化怎么做的？**

> 分包加载（主包只放核心页面）、图片资源上 CDN 不打包、公共组件抽离到独立分包、无用依赖清理。通过分析工具（支付宝 IDE 的包体积分析）找大文件，图标用 iconfont 代替图片。

## 13. WebView 与 JSBridge

**Q: WebView 白屏怎么排查和解决？**

- **排查：** 检查网络请求是否成功、JS 是否有阻断性报错、WebView 是否加载完成、原生侧是否正常初始化
- **兜底方案：** WebView 加载超时（如 5 秒）→ 自动切换为原生错误页 + 重试按钮；原生侧监听 WebView 加载状态，异常时重新加载
- **优化：** 预加载 WebView 实例（WebView 池）、静态资源离线包、骨架屏

**Q: 你设计的 JSBridge 协议规范包含哪些能力？**

> 三大设计原则：
> 1. **Promise 化封装：** 所有原生调用返回 Promise，统一异步处理
> 2. **版本兼容：** 协议带版本号，原生侧按版本号路由到对应实现，老版本 API 保持向后兼容
> 3. **降级策略：** 原生 Bridge 不可用时（如旧版 App），降级为 URL Scheme 方案或提示用户升级
>
> 具体实现：call(method, params) → Promise，内部通过 callbackId 关联请求和响应。支持同步调用（特定场景，如获取设备 ID）和异步调用（大部分场景）。

**Q: iOS 和 Android WebView 遇到过哪些兼容坑？**

- iOS WKWebView 本地文件跨域：Ajax 被 CORS 拦截，需原生配置或改用 http://localhost
- iOS 100vh 问题：地址栏占用视口空间，用 dvh 或 JS 动态设置
- Android 字体缩放：系统字体设置影响 WebView 内字体大小，CSS 用固定 px
- position: fixed + 软键盘 Android：键盘弹出导致 fixed 元素错位
- iOS 输入框被键盘遮挡：键盘不触发 resize，需监听 focusin 手动滚动

# 六、IOT 项目深挖

## 14. 微前端架构整体设计

**Q: 你们微前端架构的整体设计是什么样的？一句话说清楚。**

> 基座（主应用）+ N 个子应用，基座负责路由分发、全局状态、统一登录鉴权；子应用通过 qiankun 注册接入，各自独立开发、独立部署。技术栈不限——Vue 存量模块和 React 新模块共存运行。

**Q: 为什么选择 qiankun 而不是 Module Federation 或 iframe？**

> | 方案 | 优点 | 缺点 |
> |------|------|------|
> | qiankun | 技术栈无关、沙箱隔离完善、社区活跃 | 需要改造子应用（导出生命周期） |
> | Module Federation | 原生 Webpack 支持、运行时共享依赖 | 技术栈绑定（需同一构建体系） |
> | iframe | 隔离最彻底 | 通信成本高、URL 不同步、性能差、弹窗只能 iframe 内部 |
>
> 我们场景是 Vue + React 混用，qiankun 是最优解。

**Q: 子应用接入规范包含哪些内容？**

> 1. 必须导出 bootstrap/mount/unmount 生命周期
> 2. 必须配置 webpack publicPath 为子应用部署路径
> 3. 打包格式为 umd，注入到 window
> 4. CSS 命名规范：BEM + 子应用前缀，配合 experimentalStyleIsolation
> 5. 共享依赖声明：React、ReactDOM、Ant Design 等由基座提供（externals），避免重复加载
> 6. 路由前缀：每个子应用有独立的 base path

**Q: 主子应用共享依赖怎么管理？版本冲突怎么办？**

> 基座通过 webpack externals 暴露 React、ReactDOM、Ant Design 等公共依赖。子应用在 webpack externals 中声明使用基座提供的版本。版本冲突通过 qiankun 的 `excludeAssetFilter` 排除子应用打包的公共依赖。
>
> 如果两个子应用需要不兼容的依赖版本（如 Ant Design 4 vs 5），通过基座的 webpack alias 处理版本映射。实际策略是：推进统一升级，不加长期兼容多个主版本的逻辑以免复杂度失控。

## 15. Formily 低代码表单引擎

**Q: 为什么选 Formily 而不是其他方案？**

> 对比过三种方案：
> 1. **纯手写表单：** 可定制但不通用，中后台 80% 的表单是重复劳动
> 2. **FormRender（阿里开源）：** 基于 JSON Schema，简单场景够用，复杂联动支持弱
> 3. **Formily：** Schema + 响应式联动，支持复杂逻辑编排，有可视化设计器，组件扩展性好
>
> 我们的场景有大量设备配置表单，字段之间联动复杂（A 选"海报投放"→ 显示 BCD 字段 → B 选"定时"后显示时间选择器），Formily 的 reactions 机制天然适合这种场景。

**Q: Formily 的字段联动响应式依赖模型怎么设计的？**

> Formily 基于 observable 响应式系统，字段值变化自动触发 reactions。核心机制：
> 1. 声明式联动规则：在 Schema 中定义 x-reactions，描述"当某字段变化时做什么"
> 2. 依赖自动收集：reaction 中访问的字段值会被自动追踪为依赖
> 3. 联动类型：字段显隐（x-display）、状态（x-pattern：可编辑/只读/禁用）、数据源（x-data）、校验规则（x-validator）
>
> 循环依赖检测：在设置联动规则时构建字段依赖图，拓扑排序检测环。发现环 → 告警并拒绝该规则。运行时也设置了递归深度上限（5 层）作为兜底。

**Q: 20+ 物料组件的设计规范是什么？**

> 组件设计遵循三个原则：
> 1. **标准化 Props：** 统一 value/onChange 受控模式，兼容 Formily 的 connect 和 mapProps
> 2. **组合优于继承：** 通过 Formily 的 x-component-props 传参而非创建特殊组件变体
> 3. **业务语义封装：** 如"设备选择器"、"地区多选"、"时间范围选择"等具业务含义的组件，内部封装数据获取逻辑
>
> 发布流程：组件开发 → Code Review → 文档 + Demo → 发布到内部物料平台 → 设计器中可用

## 16. AI Agent 与 SSE 流式渲染

**Q: SSE 流式渲染方案怎么设计的？**

> ```
> 前端 fetch (stream: true) → 后端 LangChain Agent → LLM (streaming)
>                           ↑                              ↓
>                     SSE token 流                    token by token
>                           ↓
>     前端 ReadableStream.getReader() 逐条读取
>                           ↓
>     解析 SSE data 字段 → Markdown 增量渲染 + 自定义组件替换
> ```
>
> **断线重连：** 记录最后收到的 messageId，重连时通过 Last-Event-ID header 告诉服务端从断点续传
> **超时降级：** 30 秒无响应 → 提示用户"正在思考中，请稍候"；60 秒 → 超时兜底，返回已完成部分 + 错误提示
> **异常容错：** 单个 token 解析失败不影响后续（try/catch 包裹），Markdown 语法异常时用纯文本降级展示

**Q: 多轮对话上下文隔离怎么做的？**

> 问题：多个用户或同一用户多会话情况下，如果后端共享上下文（如全局 memory），会导致会话 A 的对话被会话 B 看到。
>
> 解决方案：
> 1. **前端维护 sessionId：** 每个会话生成唯一 sessionId（UUID），通过请求头传递
> 2. **后端按 sessionId 隔离上下文：** 每次请求带上 sessionId，服务端用 Map<sessionId, memory> 管理
> 3. **清理机制：** 30 分钟无活动的会话自动清理 memory，前端切回后重新初始化

**Q: Schema 自动生成的 few-shot 策略怎么设计的？**

> Prompt 模板结构：
> ```
> 系统角色：你是 Formily Schema 生成器，将用户需求转为 JSON Schema
> 
> Schema 规范：{字段类型、联动规则语法、示例}
> 
> Few-shot 示例 1：用户需求 → 对应 Schema
> Few-shot 示例 2：...
> Few-shot 示例 3：...
> 
> 用户需求：{用户输入}
> ```
>
> Few-shot 样本选取策略：
> - 从历史成功的 Schema 配置中选取 3-5 个覆盖不同场景的典型样本
> - 按场景分类（设备配置、活动配置、权限配置等），动态匹配最相关的样本
>
> 验证层：
> 1. JSON Schema 格式校验（结构层）
> 2. Formily 无头渲染环境挂载测试（业务层，检查是否产生运行时错误）
> 3. 不通过的标记为"需人工审核"，通过的直接可用

# 七、五福项目深挖

## 17. NFC 状态机设计

**Q: 7 阶段状态机为什么不用 XState 而用 Zustand 手写？**

> 考虑过 XState，但几个原因选了 Zustand：
> 1. 五福项目时间紧，团队对 Zustand 更熟，XState 学习成本高
> 2. 状态转移逻辑不算极端复杂，不需要可视化状态图
> 3. Zustand 的 selector 机制天然支持精确渲染——状态变化只触发关联组件重渲染
> 4. 状态转移校验通过自定义 `transition(from, to, condition)` 工具函数实现，代码量小
>
> 实际也没用手写 if/else 状态机——分了两层：Zustand store 管当前状态和上下文数据，独立的 stateMachine 模块管合法转移和副作用（side effects）。

**Q: 7 个阶段的设计逻辑是什么？**

| 阶段 | 含义 | 触发条件 |
|------|------|---------|
| 权限检测 | 检查 NFC 权限、登录状态、活动资格 | 进入页面 |
| 引导拦截 | 未授权或不符合条件时的引导页 | 权限检测失败 |
| 开始游戏 | 等待用户碰一碰 | 权限通过 |
| 碰撞中 | NFC 已触发，等待配对 | 检测到 NFC 事件 |
| 配对查询 | 轮询服务端查询配对结果 | NFC 数据上报完成 |
| 出奖 | 展示红包/奖品 | 配对成功 + 出奖结果返回 |
| 异常兜底 | 网络异常/超时/服务端错误 | 任何阶段发生异常 |

**Q: 如果服务端配对失败（比如两个设备上报的数据匹配不上），怎么处理？**

> 服务端配对逻辑：通过 NFC tag ID + 时间窗口（3 秒内）匹配两台设备。匹配不上有两种情况：
> 1. 只有一方上报了 → 另一方进入超时（10 秒），进入异常兜底，提示"配对超时"
> 2. 双方上报但信息不匹配（极少，可能是 Bug）→ 服务端返回"配对失败"，两端同时进入异常兜底
>
> 兜底体验：展示友好提示 + "再试一次"按钮，重新进入"开始游戏"阶段。不会让用户卡在中间态。

## 18. 动画分级降级

**Q: grading 的评分模型具体怎么做的？**

> 六维度加权评分，总分 100：
> - **设备型号（40 分）：** UA 解析，维护设备性能表。iPhone 15 Pro → 40 分，iPhone 8 → 15 分
> - **GPU 信息（20 分）：** WebGL RENDERER 字符串解析 GPU 型号
> - **CPU 核心（10 分）：** navigator.hardwareConcurrency，>=8 核满分
> - **内存（10 分）：** navigator.deviceMemory，>=8GB 满分
> - **屏幕（10 分）：** 分辨率 + DPR，过高分辨率的老设备拖不动
> - **OS 版本（10 分）：** 相同硬件不同系统版本性能差异大
>
> 阈值：>=70 高档 → 完整 Mars 粒子动画；40-69 中档 → 简化动画（减少粒子数）；<40 低档 → 静态图 + CSS transition
>
> 关键设计：评分脚本内联在 HTML `<head>` 中，body 渲染前完成决策，避免中途切换的视觉跳变。

**Q: Mars 引擎（@galacean/effects）是干什么的？你在其中的角色？**

> Mars 是蚂蚁内部的动效渲染引擎（现已开源 @galacean/effects），基于 WebGL 的粒子特效引擎，用于五福活动的红包雨、开宝箱等复杂动画效果。
>
> 我的角色是**前端集成**——不是开发 Mars 引擎本身，而是：
> 1. 在业务页面中集成 Mars 动画，控制动画的加载、播放、暂停、销毁
> 2. 设计分级降级策略，保证低端机不因动画卡死
> 3. 优化动画资源的加载时机和缓存策略

## 19. 资源加载优化

**Q: FCP 从 4.5s 到 2.0s 是怎么做到的？每一步贡献了多少？**

> 4.5s 的来源分析（通过 Performance API + 埋点）：
> | 阶段 | 耗时 | 优化 | 优化后 |
> |------|------|------|--------|
> | HTML 下载 + 解析 | 0.6s | CDN + Brotli | 0.4s |
> | 主 JS Bundle 下载 | 1.8s | 代码分割 + 懒加载 | 0.5s |
> | Mars 引擎加载 | 1.2s | 按需加载（出奖阶段才加载） | 0s（不计入 FCP） |
> | 接口请求 | 1.0s | 预请求（页面加载时并行发） | 0.2s |
> | 首屏渲染 | 0.9s | 关键 CSS 内联、骨架屏 | 0.9s（感知更快） |
>
> FCP 4.5s → 2.0s 的关键三招：
> 1. Mars 引擎从首屏加载移到出奖阶段懒加载（减 1.2s）
> 2. CDN 预缓存关键资源 + HTTP/2（减 0.8s）
> 3. 接口预请求，页面 onLoad 时并行调用（减 0.5s）

## 20. 项目管理和团队

**Q: 作为平台前端负责人，你日常怎么分配需求和管理进度？**

> 需求评审后我会先做技术方案拆解，评估各模块工作量和依赖关系。和产品对齐优先级后，用看板管理任务。每周同步进度，识别风险提前暴露。对新人我会分配相对独立、风险可控的模块，自己扛关键路径和新技术攻坚。

**Q: 你带教的新人怎么培养的？**

> 分三个阶段：
> 1. **上手期（第 1-2 周）：** 安排熟悉业务 + Code Review 旁听 + 分配小 Bug 修，建立 Code Review 准入标准意识
> 2. **成长期（1-3 月）：** 带他们做完整需求，我做方案评审和代码 Review。重点培养"为什么这么写"的思考习惯而非"怎么写"
> 3. **独立期（3 月+）：** 独立承担模块，我退出日常 Review，只在关键决策时介入
>
> 两个带教的新人都通过了转正考核。

**Q: 遇到和你技术方案分歧较大的同事，怎么处理？**

> 技术上分歧很正常，我的原则是"用数据说话、从业务出发"。先搞清楚双方方案的差异点是什么——性能、可维护性、开发成本还是扩展性。如果分歧在具体指标（如性能），做个 POC 对比数据。如果分歧在风格偏好，以团队规范和大多数人意见为准。最终目标是项目能交付好，不是证明自己更对。

**Q: 线上出过什么问题？怎么处理的？**

> 说一个案例。有一次设备运营平台的表单模块突然白屏，大量运营操作受阻。我作为应急响应 Owner 的处理流程：
> 1. **定位（2 分钟）：** 查看监控，发现是当天下午的一次发版引入了 Formily Schema 解析异常。快速定位到有问题的 commit
> 2. **止血（5 分钟）：** 回滚到上一个稳定版本，业务恢复
> 3. **复盘（故障后）：** 原因是 Schema 新增了一个联动规则，但缺少对应字段导致解析失败。根因是缺少 Schema 变更的自动化校验卡口。改进措施：发布流程中增加 Schema 合法性校验的 CI 步骤，Schema 变更必须经过 Code Review
