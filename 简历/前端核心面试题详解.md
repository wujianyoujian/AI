## 1. 打包优化如何做的，思路是啥

### 完整思路

核心原则：**先测量定位，再针对性优化，别盲目调参。** 三步走：

1. **分析**：用 `webpack-bundle-analyzer` 看产物体积构成，找出最大的包、重复的依赖。
2. **定位瓶颈**：是产物体积大？还是构建慢？还是加载慢？三者优化手段不同。
3. **针对性优化**：按三层分类处理。

### 三层优化

**① 产物体积（用户下载更小）**

| 手段 | 说明 |
|------|------|
| Tree Shaking | 摇掉未使用代码，需 ES Module + `sideEffects: false` |
| 代码分割 | `splitChunks` + 动态 `import()`，拆 vendor / 业务 / 异步 chunk |
| externals + CDN | React 等大库走 CDN，不打包进 bundle |
| 按需引入 | antd 等组件库按需加载 |
| 压缩 | Terser / esbuild 压缩 JS，CSS 压缩，图片 webp + 压缩 |
| gzip / brotli | 服务端开启，传输体积再小 70% |

**② 构建速度（开发/CI 更快）**

| 手段 | 说明 |
|------|------|
| 持久化缓存 | `cache: { type: 'filesystem' }` |
| 多线程 | `thread-loader`（配合 babel 等重 loader） |
| 换 loader | `esbuild-loader` / `swc-loader` 替代 babel，快几十倍 |
| 缩小范围 | loader 加 `include/exclude`，resolve 减少搜索目录、`noParse` |

**③ 加载性能（用户感知更快）**

- 路由懒加载（首屏只加载当前页面代码）
- `preload`（关键资源优先）/ `prefetch`（空闲预取）
- 首屏关键 CSS 内联、非关键资源延迟加载

### 口诉版

> 我打包优化的思路是先测量再优化，不盲目调参。第一步用 bundle-analyzer 看产物体积构成，找出最大的包。然后分三层优化：产物体积层做 tree shaking、代码分割、externals 走 CDN、按需引入、压缩加 gzip；构建速度层做持久化缓存、多线程、用 esbuild 替代 babel、缩小 loader 范围；加载性能层做路由懒加载、preload 和 prefetch。核心是先定位再动手。

### 高频追问

1. **怎么确定该优化哪个包？** → bundle-analyzer 可视化，找体积最大的、重复打包的。
2. **tree shaking 为什么有时失效？** → 用了 CommonJS、没设 sideEffects、副作用代码没标注。

## 2. React 封装动态表单，思路是什么

### 核心思路：字段配置化 + 统一状态管理 + 动态增删

动态表单 = 字段数量/类型不确定，由配置或数据决定，能动态增删。封装核心是**把字段抽象成配置，用统一的 Form / FormItem 组件管理值和校验**。

三个关键点：

1. **字段配置化**：用配置对象描述字段（type / label / rules / options），渲染时按 type 映射到对应组件。
2. **统一值管理**：整个表单的值是一个对象，`setField(key, value)` 局部更新。
3. **动态增删**：字段列表本身是 state，可以 `push` / `filter` 增删。

### 代码实现

**① 字段渲染器（type → 组件映射）**

```js
const fieldMap = {
  input: ({ value, onChange, ...rest }) =>
    <input value={value} onChange={e => onChange(e.target.value)} {...rest} />,
  select: ({ value, onChange, options }) => (
    <select value={value} onChange={e => onChange(e.target.value)}>
      {options.map(o => <option key={o.value} value={o.value}>{o.label}</option>)}
    </select>
  ),
};
```

**② FormItem（单个字段 + label + 错误提示）**

```js
function FormItem({ label, error, children }) {
  return (
    <div className="form-item">
      <label>{label}</label>
      {children}
      {error && <span className="error">{error}</span>}
    </div>
  );
}
```

**③ DynamicForm（统一管值 + 校验 + 提交）**

```js
function DynamicForm({ fields, onSubmit }) {
  const [values, setValues] = useState({});
  const [errors, setErrors] = useState({});

  const setField = (key, value) => setValues(v => ({ ...v, [key]: value }));

  const validate = (rules = [], value) =>
    rules.filter(r => r.required && !value).map(r => r.message || '必填');

  const submit = () => {
    const newErrors = {};
    fields.forEach(f => {
      const err = validate(f.rules, values[f.key]);
      if (err.length) newErrors[f.key] = err[0];
    });
    setErrors(newErrors);
    if (!Object.keys(newErrors).length) onSubmit(values);
  };

  return (
    <div>
      {fields.map(f => {
        const Comp = fieldMap[f.type] || fieldMap.input;
        return (
          <FormItem key={f.key} label={f.label} error={errors[f.key]}>
            <Comp value={values[f.key]} onChange={v => setField(f.key, v)} {...f} />
          </FormItem>
        );
      })}
      <button onClick={submit}>提交</button>
    </div>
  );
}
```

**④ 动态增删字段（字段列表是 state）**

```js
function DynamicFieldList() {
  const [fields, setFields] = useState([
    { key: 'name', type: 'input', label: '姓名', rules: [{ required: true, message: '姓名必填' }] },
  ]);

  const addField = () =>
    setFields(f => [...f, { key: `field_${Date.now()}`, type: 'input', label: '新字段' }]);
  const removeField = key => setFields(f => f.filter(i => i.key !== key));

  return <DynamicForm fields={fields} onSubmit={console.log} />;
}
```

### 封装思路总结

三层结构 + 三个关键点：

```
字段渲染器 fieldMap（type → 组件，扩展只需加映射）
FormItem（单个字段的 label + 错误提示）
DynamicForm（统一管值 + 校验 + 提交，字段数组驱动渲染）
```

- **新增字段类型** → 只在 `fieldMap` 加一个映射。
- **增删字段** → 操作字段数组 state。
- **校验** → 规则配置化（required/正则/自定义函数），提交时统一校验，可扩展异步校验。

### 口诉版

> 我封装动态表单的思路是字段配置化加统一管理。核心三点：第一，字段抽象成配置，描述 type、label、校验规则、选项；第二，整个表单的值用一个对象统一管理，用 setField 局部更新；第三，字段列表本身是 state，支持动态增删。结构上分三层：字段渲染器做 type 到组件的映射，FormItem 管单个字段的 label 和错误提示，DynamicForm 统一管值、校验和提交。这样加字段类型只在渲染器加个映射，增删字段操作 state 就行。

### 高频追问

1. **字段联动怎么做？** → 在 setField 里监听某字段变化，触发依赖字段的更新或校验（比如选择 A 后 B 的选项变化）。
2. **复杂/异步校验怎么做？** → 规则配置化（required/正则/自定义函数），校验支持返回 Promise 做异步（如查重）。
3. **大量字段性能？** → 字段级 memo 隔离 + 非受控 ref 批量取值（见第 7 题）。

## 3. useEffect 四个场景分别在什么时候触发

### 四种依赖数组写法

```js
// 场景一：不传第二个参数 → 每次渲染后都执行
useEffect(() => { console.log('每次渲染都执行'); });

// 场景二：空数组 [] → 只在挂载后执行一次
useEffect(() => { console.log('只执行一次（componentDidMount）'); }, []);

// 场景三：[a, b] → 挂载后 + a/b 变化时执行
useEffect(() => { console.log('a 或 b 变了'); }, [a, b]);

// 场景四：返回清理函数 → 卸载前 / 依赖变化前执行
useEffect(() => {
  const timer = setInterval(() => {}, 1000);
  return () => clearInterval(timer); // 清理副作用
}, []);
```

### 执行时机细节

- **useEffect** 是**异步**的，在浏览器**绘制之后**执行（不阻塞渲染）。
- **useLayoutEffect** 是**同步**的，在 DOM 更新后、绘制前执行（会阻塞渲染）。
- 清理函数：**卸载前**、以及**依赖变化重新执行 effect 前**都会先跑上一轮的清理。

### 口诉版

> useEffect 的触发时机取决于第二个参数。不传依赖数组，每次渲染后都执行；传空数组，只在挂载后执行一次，相当于 componentDidMount；传具体依赖，挂载后和依赖变化时执行；返回清理函数，会在卸载前和依赖变化前执行，用来清定时器、取消订阅这些副作用。另外 useEffect 是异步的，在浏览器绘制后执行，不阻塞渲染；想同步就用 useLayoutEffect。

### 高频追问

1. **useEffect 和 useLayoutEffect 区别？** → 异步绘制后 vs 同步绘制前，后者阻塞渲染。
2. **为什么空数组里用外部变量会有闭包陷阱？** → effect 捕获的是当次渲染的值，依赖没声明就拿到旧值。

## 5. Vite 和 Webpack 的区别，优缺点

### 本质区别

| 维度 | Webpack | Vite |
|------|---------|------|
| 原理 | **打包式**：开发时也要先 bundle 所有模块 | **ESM 直出**：开发环境不打包，浏览器原生 ESM 按需加载 |
| 冷启动 | 慢（全量打包） | 快（只编译当前访问的模块） |
| 依赖处理 | 全量处理 node_modules | esbuild 预构建依赖 |
| HMR | 慢（大项目明显） | 快（模块级精确更新） |
| 生产构建 | 成熟稳定（自研打包器） | Rollup（esbuild 压缩） |
| 生态 | 最成熟、插件海量 | 较新、增长快 |

### 为什么 Vite 快

1. **开发环境用浏览器原生 ESM**：不打包，按需编译。
2. **esbuild 预构建**：esbuild 是 Go 写的，比 JS 写的 babel/webpack 快几十倍。
3. **生产环境用 Rollup**：因为 esbuild 做生产代码分割、兼容性处理还不成熟，Rollup 生态更稳。

### 优缺点

**Webpack**：✅ 生态成熟、插件全、兼容好、生产稳定；❌ 慢、配置复杂。

**Vite**：✅ 冷启动快、HMR 快、配置简单、开发体验好；❌ 生产依赖 Rollup、老项目 CommonJS 依赖迁移成本高、生态较新。

### 口诉版

> 本质区别是，Webpack 是打包式，开发环境也要把模块 bundle 完才能跑，所以冷启动慢；Vite 开发环境用浏览器原生 ESM，按需编译，再用 Go 写的 esbuild 预构建依赖，所以冷启动和 HMR 都快。生产构建 Vite 用 Rollup，因为 esbuild 做代码分割和兼容处理还不成熟。优缺点上，Webpack 生态成熟、插件全，但慢、配置复杂；Vite 开发体验好、快，但生产依赖 Rollup、老项目迁移有成本。

### 高频追问

1. **为什么生产不用 esbuild？** → 代码分割、兼容性、插件生态不成熟，Rollup 更稳。
2. **老项目从 Webpack 迁 Vite 注意啥？** → CommonJS 依赖、require 语法、插件替换。

## 6. 如何解决受控组件和非受控组件

### 概念

- **受控组件**：值由 React state 管理，`value` + `onChange`，单一数据源。
- **非受控组件**：值由 DOM 自己管理，`defaultValue` 初始化，`ref` 读取。

```js
// 受控
function Controlled() {
  const [name, setName] = useState('');
  return <input value={name} onChange={e => setName(e.target.value)} />;
}

// 非受控
function Uncontrolled() {
  const ref = useRef();
  return <input defaultValue="" ref={ref} />; // 取值 ref.current.value
}
```

### "解决"什么：大量表单的卡顿

受控组件每次输入都 `setState`，触发组件重渲染。几十个输入框共用一个表单 state 时，**每敲一个字整个表单都重渲染**，卡顿。

**解决方式：**

1. **非受控 + ref 批量取值**：输入时不 setState，提交时一次性读所有值。
2. **字段级组件拆分 + memo**：每个字段独立组件，只重渲染变化的字段。
3. **useDeferredValue**：把输入状态标记为低优先级，避免阻塞渲染。
4. **局部 state**：字段值放局部，不每次打全局 store。

### 口诉版

> 受控组件是 state 作为单一数据源，value 加 onChange，实时校验联动方便，但大表单每次输入都触发整个表单渲染会卡。非受控组件值由 DOM 管，用 ref 取值，性能好但实时校验难。我的做法是，需要实时校验联动的用小表单受控，大表单用非受控加 ref 批量取值，或者字段拆组件加 memo 隔离，输入类用 useDeferredValue 降优先级。

### 高频追问

1. **受控和非受控怎么选？** → 实时校验/联动用受控，大表单性能敏感用非受控。
2. **非受控怎么初始化默认值？** → defaultValue（只生效一次），不能用 value。

## 7. 大量表单如何做性能优化

### 核心：输入时尽量少触发渲染

1. **非受控 + ref 批量取值**：提交时才读值，输入过程零 setState。
2. **字段级组件拆分 + `React.memo`**：每个字段独立组件，只有变化的字段重渲染，其余 memo 跳过。
3. **虚拟滚动**：字段几百个时，只渲染可视区域。
4. **输入防抖**：搜索类字段 debounce，减少请求/计算。
5. **局部 state / 表单库隔离**：Formily 是 field 级订阅，只有相关字段响应。
6. **避免全局 store 高频更新**：表单值放局部，提交时才同步。

### 代码示例（字段级隔离）

```js
const Field = React.memo(({ value, onChange }) => (
  <input value={value} onChange={e => onChange(e.target.value)} />
));
// 父组件传稳定引用，避免 memo 失效
```

### 口诉版

> 大量表单的性能优化核心是"输入时尽量少触发渲染"。第一，用非受控组件加 ref，提交时批量取值，输入过程不 setState。第二，字段拆成独立组件加 memo，只重渲染变化的字段。第三，字段特别多用虚拟滚动只渲染可视区域。第四，搜索类字段加防抖。第五，表单值放局部，不要每次输入都打全局 store。用 Formily 的话它本身就是 field 级订阅。

### 高频追问

1. **为什么受控表单会卡？** → 每次输入 setState 触发整表单重渲染。
2. **memo 为什么可能失效？** → 父组件每次渲染创建新函数/对象引用，需 useCallback/useMemo 稳定引用。

## 8. 虚拟滚动和分页

### 两者区别

- **分页**：解决**数据加载**问题，后端分页（page/pageSize），一次只加载一页数据。
- **虚拟滚动**：解决**渲染性能**问题，数据可能全在前端，但 DOM 只渲染可视区域。

### 虚拟滚动原理（手写核心）

```js
function VirtualList({ items, itemHeight = 40, containerHeight = 400 }) {
  const [scrollTop, setScrollTop] = useState(0);

  const visibleCount = Math.ceil(containerHeight / itemHeight);
  const start = Math.max(0, Math.floor(scrollTop / itemHeight) - buffer);
  const end = Math.min(items.length, start + visibleCount + buffer * 2);

  return (
    <div style={{ height: containerHeight, overflow: 'auto', position: 'relative' }}
         onScroll={e => setScrollTop(e.target.scrollTop)}>
      {/* 占位，撑出总高度，滚动条才正确 */}
      <div style={{ height: items.length * itemHeight, position: 'relative' }}>
        {/* 只渲染可视区域，用 translateY 定位 */}
        <div style={{ transform: `translateY(${start * itemHeight}px)` }}>
          {items.slice(start, end).map(item => <Row key={item.id} height={itemHeight} />)}
        </div>
      </div>
    </div>
  );
}
```

**核心三步**：① 可视数量 = 容器高度 / 每项高度；② 滚动偏移算 start/end 索引（上下加 buffer 缓冲）；③ 只渲染 `[start, end]`，用 `translateY` 定位，外层撑出总高度保证滚动条正确。

**固定高度 vs 动态高度**：固定高度简单（上面代码）；动态高度要先测量每项高度（缓存实测值 + 预估偏移），`react-window` 的 `VariableSizeList` 封装了。

### 口诉版

> 分页和虚拟滚动解决的是两个问题：分页解决数据加载，一次只加载一页；虚拟滚动解决渲染性能，数据可能全在前端，但 DOM 只渲染可视区域。虚拟滚动的原理是，用容器高度除以每项高度算出可视数量，根据滚动偏移算出起始和结束索引，上下加缓冲，只渲染这一小段，外层撑出总高度保证滚动条正确，再用 translateY 定位。固定高度好做，动态高度要预测量每项高度，可以用 react-window 封装。

### 高频追问

1. **为什么虚拟滚动比全渲染快？** → DOM 节点数量从 N 降到可视数量，减少渲染和内存。
2. **动态高度怎么处理？** → 先预估 + 实测后缓存，或用 react-window VariableSizeList。

## 9. 如何解决微前端的样式隔离和样式污染（简历重点）

### 问题本质

多个子应用共用一个 document，全局样式互相污染。你简历的场景：**Vue（Element Plus）和 React（Ant Design）的全局样式互相覆盖**（都是 `.el-xxx`、`.ant-xxx` 全局类，还有 reset、body 样式冲突）。

### qiankun 的两种隔离

**① `strictStyleIsolation`（Shadow DOM）**

- 把子应用包进 Shadow DOM，样式完全封闭，最彻底。
- **坑**：弹窗/下拉默认挂到 body（body 不在 Shadow 内），样式丢失；部分组件库兼容问题 → 需要**自定义沙箱补丁**（你简历里写的）。

**② `experimentalStyleIsolation`（作用域前缀）**

- 给子应用样式加选择器前缀，隔离不彻底但性能更好。

### 完整解决方案（多管齐下）

1. **Shadow DOM 隔离**（最彻底，配合补丁处理挂 body 的弹窗）。
2. **CSS Modules / CSS-in-JS**：组件级局部作用域，从源头避免全局类。
3. **命名空间前缀**：BEM 规范、组件库 prefix 定制（antd `prefixCls`、Element Plus 的 `namespace`）。
4. **CSS 变量**：主题统一用变量，避免硬编码颜色互相覆盖。
5. **重置样式范围控制**：`reset` 只作用于子应用根节点 `.app-root`，不碰全局 body。
6. **组件库主题定制**：`ConfigProvider` 统一主题，减少冲突。

### 口诉版

> 微前端样式污染的本质是多个子应用共用一个 document，全局样式互相覆盖。qiankun 提供两种隔离：strictStyleIsolation 用 Shadow DOM 彻底隔离，但弹窗挂 body 会丢样式，需要自定义补丁；experimentalStyleIsolation 加作用域前缀，隔离不彻底但性能好。我的项目里 Vue 的 Element Plus 和 React 的 Ant Design 全局样式互覆盖，我用 strictStyleIsolation 加自定义沙箱补丁解决，再配合 CSS Modules、组件库主题定制、CSS 变量、重置样式限定范围多管齐下。

### 高频追问

1. **Shadow DOM 隔离有什么坑？** → 弹窗挂 body 丢样式、组件库不兼容、事件穿透，需要补丁。
2. **strict 和 experimental 怎么选？** → 要彻底用 strict，要性能用 experimental 加规范约束。

## 10. JSX 编译原理

### JSX 是什么

JSX 是语法糖，不是 HTML，也不是字符串，最终**编译成 `React.createElement` 调用**，返回虚拟 DOM 对象。

### 编译过程

```jsx
// 源码
const el = <div className="box" onClick={fn}>Hello {name}</div>;
```

**React 17 之前**（编译成 createElement，需要手动 import React）：

```js
const el = React.createElement(
  'div',
  { className: 'box', onClick: fn },
  'Hello ',
  name
);
```

**React 17+**（jsx-runtime，自动引入，无需手动 import React）：

```js
import { jsx as _jsx } from 'react/jsx-runtime';
const el = _jsx('div', {
  className: 'box',
  onClick: fn,
  children: ['Hello ', name],
});
```

### 编译产物再往下

`createElement` / `_jsx` 返回一个**虚拟 DOM 对象**：

```js
{
  type: 'div',        // 组件类型（标签字符串 或 组件函数）
  props: { className: 'box', onClick: fn, children: ['Hello ', name] },
  key: null,
  ref: null,
}
```

React 用这个对象做 diff（对比新旧虚拟 DOM），算出最小更新，再操作真实 DOM。

### 编译器是谁

Babel 的 `@babel/plugin-transform-react-jsx`，或 TypeScript 的 `jsx` 配置（`react` / `react-jsx`）。转换过程：解析 JSX → AST → 转成函数调用 → 生成代码。

### 口诉版

> JSX 是语法糖，最终被 Babel 或 TS 编译成 React.createElement 调用，React 17 以后用 jsx-runtime，不用手动 import React。编译产物是一个虚拟 DOM 对象，包含 type、props、key、ref，React 用它做 diff，对比新旧虚拟 DOM 算出最小更新再操作真实 DOM。所以 JSX 本质是"用 HTML 语法写 JavaScript 对象"。

### 高频追问

1. **为什么 React 17 后不用 import React 了？** → 编译产物从 createElement 换成了 jsx-runtime 的 _jsx，自动引入。
2. **为什么 JSX 里 className 不是 class、htmlFor 不是 for？** → 因为要编译成 JS 对象属性，class/for 是 JS 保留字。

## 11. Webpack 配置优化

### 三类优化

**① 构建速度**

```js
module.exports = {
  // 持久化缓存
  cache: { type: 'filesystem' },
  module: {
    rules: [
      {
        test: /\.js$/,
        use: 'esbuild-loader',       // 替代 babel，快几十倍
        include: path.resolve('src'), // 缩小范围
        exclude: /node_modules/,
      },
    ],
  },
  resolve: {
    modules: [path.resolve('src'), 'node_modules'], // 优先本地搜索
    extensions: ['.js', '.jsx', '.ts', '.tsx'],
  },
  module: { noParse: /lodash/ }, // 跳过已打包库的解析
};
```

**② 产物体积**

```js
module.exports = {
  optimization: {
    splitChunks: {
      chunks: 'all',
      cacheGroups: {
        vendor: { test: /[\\/]node_modules[\\/]/, name: 'vendor' },
      },
    },
    sideEffects: true, // 配合 package.json 的 sideEffects:false 开 tree shaking
  },
  externals: { react: 'React', 'react-dom': 'ReactDOM' }, // 走 CDN
};
```

**③ 缓存（contenthash）**

```js
output: {
  filename: '[name].[contenthash].js', // 内容不变 hash 不变，提升缓存命中
}
```

### 口诉版

> Webpack 配置优化分三类。构建速度上，做持久化缓存、多线程、用 esbuild-loader 替代 babel、loader 加 include 和 exclude 缩小范围、resolve 减少搜索。产物体积上，用 splitChunks 分包、sideEffects 配合 ES Module 开 tree shaking、externals 把 React 这类大库走 CDN。缓存上用 contenthash，内容不变文件名不变，提升缓存命中率。

### 高频追问

1. **contenthash、chunkhash、hash 区别？** → hash 全量、chunkhash 按 chunk、contenthash 按内容（缓存最优）。
2. **externals 和 splitChunks 区别？** → externals 完全不打包走全局变量/CDN，splitChunks 是拆成独立 chunk 仍走构建。

## 12. 路由权限控制、拦截器、菜单渲染（React 实现路由拦截）

### 路由拦截（ProtectedRoute）

```jsx
function ProtectedRoute({ children }) {
  const token = useAuthStore(s => s.token);
  const location = useLocation();

  if (!token) {
    // 未登录，重定向登录页，记录来源
    return <Navigate to="/login" state={{ from: location }} replace />;
  }
  return children;
}

// 使用
<Route path="/dashboard" element={
  <ProtectedRoute><Dashboard /></ProtectedRoute>
} />
```

### 权限控制（路由级 + 按钮级）

```jsx
// 路由级：根据角色过滤路由表
const routes = allRoutes.filter(r => r.meta?.roles?.includes(userRole));

// 按钮级：权限组件
function Auth({ permission, children }) {
  const perms = useAuthStore(s => s.permissions);
  return perms.includes(permission) ? children : null;
}
<Auth permission="user:delete"><Button>删除</Button></Auth>
```

### 菜单渲染

```jsx
// 根据权限过滤后的路由表动态生成菜单
function renderMenu(routes) {
  return routes.map(r => (
    r.children
      ? <SubMenu title={r.meta.title}>{renderMenu(r.children)}</SubMenu>
      : <Menu.Item key={r.path}>{r.meta.title}</Menu.Item>
  ));
}
```

### axios 拦截器

```js
axios.interceptors.request.use(config => {
  config.headers.Authorization = `Bearer ${getToken()}`; // 注入 token
  return config;
});

axios.interceptors.response.use(
  res => res,
  err => {
    if (err.response?.status === 401) {
      clearToken();
      redirect('/login'); // 统一处理未授权
    }
    return Promise.reject(err);
  }
);
```

### 口诉版

> 路由拦截我用 ProtectedRoute 组件包裹需要权限的路由，判断有没有 token，没有就重定向登录页并记录来源。权限控制分路由级和按钮级，路由级根据角色过滤路由表，按钮级做一个权限组件判断是否渲染。菜单根据过滤后的路由表动态生成。拦截器在 axios 里统一注入 token，响应拦截统一处理 401 跳登录。

### 高频追问

1. **登录后怎么回到原页面？** → 重定向时 state 存来源路径，登录后 `navigate(from)`。
2. **权限是前端控制还是后端控制？** → 前端控制展示，后端控制真实鉴权，缺一不可。

## 13. React 性能优化 / shouldComponentUpdate

### shouldComponentUpdate

```js
class Comp extends React.Component {
  shouldComponentUpdate(nextProps, nextState) {
    // 返回 false 跳过本次渲染
    return nextProps.data !== this.props.data;
  }
}
```

### 对应的三种形式

| 组件类型 | 优化方式 |
|---------|---------|
| 类组件（手写） | `shouldComponentUpdate` 自定义比较 |
| 类组件（自动） | `PureComponent` 自动浅比较 props/state |
| 函数组件 | `React.memo` 浅比较 props，变了才渲染 |

### 配套 hooks

- `useMemo`：缓存计算结果，依赖不变返回缓存值。
- `useCallback`：缓存函数引用，避免子组件 memo 因函数引用变化而失效。

```js
const expensiveValue = useMemo(() => compute(a), [a]);
const handleClick = useCallback(() => { /* ... */ }, []);
```

### 局限（高频）

1. **都是浅比较**：深层对象/数组变化检测不到，可能漏更新或误更新。
2. **memo 有比较成本**：别到处乱用，比较本身要时间，简单组件 memo 反而更慢。
3. **引用不稳定导致失效**：父组件每次渲染传新对象/函数，memo 形同虚设，需 useMemo/useCallback 稳定引用。

### 口诉版

> shouldComponentUpdate 是类组件生命周期，返回 false 跳过渲染。PureComponent 和 React.memo 是它的自动浅比较版本，函数组件用 memo 配合 useMemo、useCallback 缓存计算结果和函数引用。但要清楚三个局限：都是浅比较、memo 本身有比较成本、引用不稳定会让 memo 失效。

### 高频追问

1. **什么时候不该用 memo？** → 简单组件（比较成本 > 渲染成本）、props 每次都变。
2. **深比较怎么做？** → 手写深比较或用 immutable 数据结构（引用不变即没变）。

## 14. 父组件调用子组件方法

### 函数组件：forwardRef + useImperativeHandle

```jsx
const Child = forwardRef((props, ref) => {
  const inputRef = useRef();

  // 只暴露想暴露的方法，更可控
  useImperativeHandle(ref, () => ({
    focusInput() { inputRef.current.focus(); },
    reset() { /* ... */ },
  }));

  return <input ref={inputRef} />;
});

// 父组件
function Parent() {
  const childRef = useRef();
  return (
    <>
      <Child ref={childRef} />
      <button onClick={() => childRef.current.focusInput()}>聚焦</button>
    </>
  );
}
```

### 类组件：ref 直接拿实例

```jsx
class Child extends React.Component {
  focusInput() { this.inputRef.focus(); }
  render() { return <input ref={el => this.inputRef = el} />; }
}
// 父组件 childRef.current.focusInput()
```

### 为什么用 useImperativeHandle

- 函数组件没有实例，`ref` 默认拿不到方法。
- `useImperativeHandle` 显式声明暴露哪些方法，避免把整个内部实现暴露出去（封装性更好）。

### 口诉版

> 函数组件没有实例，所以要用 forwardRef 转发 ref，再用 useImperativeHandle 把想暴露的方法挂到 ref 上，父组件通过 ref 调用。类组件可以直接用 ref 拿实例调方法。useImperativeHandle 的好处是显式控制暴露哪些方法，封装性更好。不过我的建议是优先用状态提升，实在需要命令式操作才用这种方式。

### 高频追问

1. **什么时候需要父调子？** → 命令式操作（聚焦、滚动、播放动画），能用状态提升就别用。
2. **useImperativeHandle 为什么比直接暴露好？** → 显式声明接口，封装内部实现，避免耦合。

## 15. React Hook 规则

### 两条硬规则

1. **只在顶层调用**：不能写在循环、条件、嵌套函数里。
2. **只在 React 函数组件或自定义 Hook 里调用**：不能在普通 JS 函数、类组件里调。

### 为什么（核心原理）

React 内部用**链表**存每个组件的所有 Hook，**靠调用顺序**来对应每个 Hook 的状态。渲染时按顺序逐个取，如果某次渲染少调了一个 Hook（比如写在 if 里，条件不满足就没调），后面的 Hook 顺序全错位，状态就串了。

```js
// ❌ 错误：条件里调 Hook
if (visible) {
  useState(); // 某次 visible 为 false 就少调一个，顺序错乱
}

// ✅ 正确：Hook 在顶层，条件放 Hook 内部
useEffect(() => {
  if (visible) { /* ... */ }
}, [visible]);
```

### 怎么保证

- ESLint 插件 `eslint-plugin-react-hooks` 的 `rules-of-hooks` 规则会静态检查，违反就报错。

### 口诉版

> Hook 有两条硬规则：只在顶层调用，只在函数组件或自定义 Hook 里调用。原因是 React 用链表按调用顺序存每个 Hook 的状态，渲染时按顺序取，如果写在条件里，某次渲染少调一个，后面全部错位，状态就串了。所以条件逻辑要写在 Hook 内部，而不是用它包住 Hook。项目里用 eslint-plugin-react-hooks 强制检查。

### 高频追问

1. **为什么不能在循环里调 Hook？** → 循环次数可能变，调用数量不定，顺序无法保证。
2. **自定义 Hook 命名要求？** → 必须 use 开头，否则 eslint 不识别、无法检查规则。

## 16. 错误边界

### 实现

```jsx
class ErrorBoundary extends React.Component {
  state = { hasError: false };

  // 渲染降级 UI（在错误发生时更新 state）
  static getDerivedStateFromError(error) {
    return { hasError: true };
  }

  // 记录错误日志、上报
  componentDidCatch(error, errorInfo) {
    reportError({ error, errorInfo });
  }

  render() {
    if (this.state.hasError) {
      return <Fallback onRetry={() => this.setState({ hasError: false })} />;
    }
    return this.props.children;
  }
}

// 使用
<ErrorBoundary>
  <MyComponent />
</ErrorBoundary>
```

### 关键限制（高频追问）

| 能捕获 | 不能捕获 |
|--------|---------|
| 渲染（render）中的错误 | 事件处理（onClick 里的错误） |
| 生命周期方法中的错误 | 异步（setTimeout/Promise） |
| 构造函数中的错误 | 服务端渲染（SSR） |
| | 错误边界自身的错误 |

**为什么捕获不了事件和异步**：事件处理和异步不在 React 渲染流程里，错误边界只能捕获**渲染期间**的错误。事件里的错误要用 `try/catch` 自己处理。

### 函数组件怎么办

函数组件不能直接当错误边界（需要生命周期方法），用 `react-error-boundary` 库：

```jsx
import { ErrorBoundary } from 'react-error-boundary';

<ErrorBoundary fallback={<Fallback />} onError={reportError}>
  <MyComponent />
</ErrorBoundary>
```

### 口诉版

> 错误边界是一个类组件，用 getDerivedStateFromError 在错误时渲染降级 UI，用 componentDidCatch 记录和上报错误。但它只能捕获渲染、生命周期、构造函数里的错误，捕获不了事件处理和异步的错误，因为那些不在 React 渲染流程里，要自己 try catch。函数组件要用 react-error-boundary 这个库。

### 高频追问

1. **错误边界怎么做"重试"？** → 降级 UI 加按钮，点击重置 state 重新渲染。
2. **全局错误兜底怎么做？** → window.onerror + unhandledrejection 捕获边界外的错误，配合错误边界双层兜底。
