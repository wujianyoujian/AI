### 【八股文-1】Event Loop 与异步模型的工程化理解

**面试题：** 你简历里写了「熟悉 Event Loop 与 Promise / async/await 异步模型」。假设现在有一个场景：你需要批量请求 1000 条数据，每次最多并发 5 个，且要求按原始顺序输出结果。请写出实现，并解释：如果某个请求超时了怎么办？如果是 Node.js 服务端做这件事，和浏览器端有什么本质区别？

**P10 满分答案：**

**第一步 — 核心概念/原理：**

Event Loop 的本质是「单线程的异步调度器」。浏览器端有宏任务队列（setTimeout、setInterval、I/O、UI rendering）和微任务队列（Promise.then、MutationObserver、queueMicrotask），每轮 Event Loop 先清空一个宏任务，再清空所有微任务，然后可能触发渲染。Node.js 在这之上引入了 libuv 的线程池 + 6 个阶段的宏任务队列（timers → pending callbacks → idle/prepare → poll → check → close），且每个阶段之间清空微任务。

**第二步 — 工程实践/场景：**

```typescript
// 核心实现：并发控制 + 顺序保持
async function batchRequest<T>(
  urls: string[],
  concurrency: number,
  fetcher: (url: string, signal: AbortSignal) => Promise<T>,
  timeout = 10000
): Promise<T[]> {
  const results: T[] = new Array(urls.length);
  let index = 0;

  async function worker() {
    while (index < urls.length) {
      const i = index++;  // 关键：先取索引再 await，保证不乱序
      try {
        const controller = new AbortController();
        const timer = setTimeout(() => controller.abort(), timeout);
        results[i] = await fetcher(urls[i], controller.signal);
        clearTimeout(timer);
      } catch (e) {
        results[i] = undefined as T;
        // 实际项目中这里会打点上报
      }
    }
  }

  // 启动 concurrency 个 worker
  await Promise.all(Array.from({ length: concurrency }, () => worker()));
  return results;
}
```

"我们当时是怎么做的"：在 IOT 平台的 AI Agent 中，上游大模型 API 有 RPM 限制，前端不能直接打，由 NestJS BFF 层做并发控制。当时用的是一个 p-limit 风格的信号量模式——本质就是上面这个 worker 模型。核心心得：**不要用 `Promise.all` 直接打所有请求**，哪怕你加了 `.catch`，TCP 连接池也会被打爆（浏览器同域名 6 个连接限制，Node.js 虽然没有这个限制，但 `Promise.all` 会瞬间创建 N 个 socket，内存压力很大）。

**第三步 — 深度理解/思考/踩坑：**

- **浏览器 vs Node.js 的本质区别**：不只是 API 不同（XHR vs http 模块）。浏览器的并发控制受 HTTP/1.1 同域 6 连接限制约束，Node.js 没有；但 Node.js 的事件循环有 poll 阶段，大量 I/O 在 poll 阶段堆积可能阻塞其他阶段。浏览器端 `fetch` 的 AbortController 是真正能中断 TCP 连接的（在支持的情况下），而 Node.js 早期版本的 abort 只是 reject promise，连接本身没断——所以服务端还会继续处理请求。
- **为什么 `index++` 要写在 `await` 前面**：如果写在 await 后面，就变成了串行——因为每个 worker 会等上一个请求完成才取下一个索引。这是新人最容易犯的错。
- **超时不只是一个计时器**：超时后 `results[i]` 是 undefined，调用方怎么区分「真的没数据」和「请求超时了」？需要设计一个 Result 类型 —— `{ ok: true, data: T } | { ok: false, reason: 'timeout' | 'network' | 'server' }`。这是生产级代码和面试代码的区别。

**面试官评价要点：**
- 及格：能说出 Event Loop 的基本概念（宏任务/微任务），写出基本并发控制
- 良好：能解释为什么先取索引再 await，能处理超时场景
- 优秀：能说出浏览器和 Node.js 事件循环差异，能讨论 AbortController 的底层机制，能设计 Result 类型处理错误态

### 【八股文-2】闭包与内存泄漏 — 从排查到修复的完整链路

**面试题：** 你在简历里提到了「内存泄漏排查」。请描述一次你实际排查内存泄漏的经历：你看到了什么现象、用了什么工具、怎么定位到根因、最后怎么修的？

**P10 满分答案：**

**第一步 — 核心概念/原理：**

闭包本质是「函数 + 函数能访问的外部变量组成的词法环境」。垃圾回收基于可达性分析（从 root 出发能访问到的对象不会被回收）。闭包之所以容易泄漏，不是因为闭包本身有问题，而是因为**闭包持有的引用意外地阻止了 GC**。V8 还有一个特殊行为：闭包会持有整个外部作用域的对象，即使你只引用了其中某一个变量——这叫「闭包的 over-capture」，老版本 V8 尤其明显。

**第二步 — 工程实践/场景：**

"当时在招银云创做混合 H5 应用时遇到的真实案例"：

现象：App 内嵌 WebView 页面使用一段时间后，页面操作明显变卡，iOS 端在低端机上有概率触发 WebView 的 `didReceiveMemoryWarning` 导致白屏。

排查过程：
1. **Chrome DevTools Performance Monitor** — 看到 JS Heap Size 持续增长，垃圾回收后降不下来，呈「锯齿上升」趋势，确认内存泄漏
2. **Memory → Heap Snapshot** — 在页面上反复操作（打开弹窗 → 关闭弹窗 → 重复 10 次），取两次快照对比。用 Comparison 视图按 Delta 排序，发现 **detached DOM tree** 数量异常——说明某些 DOM 节点被移除了但 JS 还持有引用
3. **关键发现**：查找 detached 节点的 Retainers 路径，发现引用的源头是一个全局的 `eventListeners Map`——代码里 `addEventListener` 注册了事件但组件销毁时没有 `removeEventListener`
4. 进一步排查：`useEffect` 里 `addEventListener` 但 return 里没 cleanup；`setInterval` 没 `clearInterval`；更隐蔽的是，一个闭包里引用了整个 `event` 对象（`event.target` 持有了 DOM 引用），而这个闭包被存到了全局状态里

修复方案：
```typescript
// 修复前
useEffect(() => {
  const handler = (e: Event) => {
    setPosition({ x: e.clientX, y: e.clientY }); // 闭包捕获了 e，e.target 持有 DOM
  };
  window.addEventListener('mousemove', handler);
  // ❌ 忘记清除
}, []);

// 修复后
useEffect(() => {
  const handler = (e: MouseEvent) => {
    const { clientX, clientY } = e; // 只取需要的基本类型值，避免持有多余引用
    setPosition({ x: clientX, y: clientY });
  };
  window.addEventListener('mousemove', handler);
  return () => window.removeEventListener('mousemove', handler); // ✅ cleanup
}, []);
```

**第三步 — 深度理解/思考/踩坑：**

- **Heap Snapshot 的三视图用法**：Summary 看自己写了什么（按构造函数分组）、Comparison 看泄漏了什么（两个快照的差量）、Containment 看谁持有了它（从全局对象出发的引用链）
- **一个容易忽略的场景**：`useCallback` / `useMemo` 的依赖数组如果包含了「每次渲染都新建的对象」，缓存实际上不会生效，如果这些函数被存到外部（比如事件总线），就会持有过期闭包中的引用
- **Performance Monitor ≠ Memory 面板**：Monitor 是实时看趋势的（发现异常），Memory 是用来定位根因的（找到谁造成的）
- **如果不用 Chrome DevTools，还有什么替代**：Node.js 端用 `--inspect` + Chrome DevTools Remote Debugging，或者用 `node --expose-gc` + `process.memoryUsage()` + heapdump 做定期快照分析

**面试官评价要点：**
- 及格：知道闭包会导致泄漏，知道 useEffect cleanup
- 良好：能说出用 Chrome DevTools 的 Memory 面板定位，能描述 detached DOM 的概念
- 优秀：能从现象到根因讲完整链路（包括 Retainer 路径），知道 over-capture 行为，能说清楚三种视图的用途区别

### 【八股文-3】TypeScript 类型系统 — 从类型体操到工程落地

**面试题：** 你在 IOT 平台的低代码表单引擎中，用 TypeScript 泛型实现了 Schema 字段的类型推导。请具体说说：你是怎么设计的？如果 Schema 本身是从后端 JSON 配置动态加载的（运行时才知道结构），类型推导还能生效吗？不能的话怎么办？

**P10 满分答案：**

**第一步 — 核心概念/原理：**

TypeScript 的类型系统是「结构类型系统」（Structural Type System），且是「编译时擦除」的——编译成 JS 后所有类型信息消失。这决定了：**能类型推导的前提是类型信息在编译时就已知**。运行时动态加载的 JSON，编译时 TS 不知道结构，所以不能自动推导。

**第二步 — 工程实践/场景：**

"当时我的做法分两层"：

**编译时层（开发者写 Schema 配置时）**：
```typescript
// Formily 的 Schema 结构，关键是用泛型关联字段值和 schema 结构
interface FieldSchema<T = unknown> {
  type: 'string' | 'number' | 'select' | 'date';
  required?: boolean;
  // 核心：根据 type 推导出 value 类型
  'x-reactions'?: Reaction<T>[];
}

// 利用条件类型 + 映射，让 Schema 类型和表单值类型联动
type SchemaToValues<S extends Record<string, FieldSchema>> = {
  [K in keyof S]: S[K] extends { type: 'number' }
    ? number
    : S[K] extends { type: 'string' }
    ? string
    : S[K] extends { type: 'date' }
    ? Date
    : unknown;
};

// 使用：定义 Schema 时值类型自动推导出来
const schema = {
  name: { type: 'string' as const, required: true },
  age: { type: 'number' as const },
  birthday: { type: 'date' as const },
};

// values 的类型自动推导为 { name: string; age: number; birthday: Date }
```

**运行时层（后端返回动态 Schema 时）**：这时编译时推导失效。做法是用 **Zod / io-ts 做运行时校验**：
```typescript
import { z } from 'zod';

// 后端返回的 JSON → 运行时解析 → Zod Schema → 类型推断
const remoteSchema = await fetch('/api/form-schema/123').then(r => r.json());

// 运行时根据 type 动态构建 Zod schema
function buildZodSchema(fields: RemoteField[]): z.ZodObject<any> {
  const shape: Record<string, z.ZodTypeAny> = {};
  for (const field of fields) {
    shape[field.key] = field.type === 'number'
      ? z.number()
      : field.type === 'date'
      ? z.coerce.date()
      : z.string();
    if (field.required) shape[field.key] = (shape[field.key] as any).min(1);
  }
  return z.object(shape);
}

const validator = buildZodSchema(remoteSchema);
type FormValues = z.infer<typeof validator>; // 运行时校验 + 编译时类型二合一
```

**第三步 — 深度理解/思考/踩坑：**

- **「TS 只编译时有效」这个限制的工程解法**：就是「编译时写类型 → 运行时要校验」。不要相信任何外部输入的类型符合你的 TypeScript interface。zod 的 `z.infer` 是双向的：既定义了运行时校验规则，又能反推出编译时类型。这是目前最优雅的方案。
- **Formily 的 `x-reactions` 联动**：最难的不是显隐，而是 A 字段的值变化时 B 字段的可选值也变化（比如「选择省份 → 城市下拉框联动」）。这里的类型约束是：B 字段的选项列表类型依赖 A 字段的值。在 Formily 里通过 `$deps` 声明依赖 + `when` 模式匹配来做，但如果用 TypeScript 严格描述这个关系，条件类型会非常深，得不偿失。实际工程中，这一层的类型推到「字段名 + 值类型」就够了，联动逻辑用运行时校验兜底。
- **Formily vs 纯自研的取舍**：Formily 的 Schema 驱动确实减少了大量模板代码，但代价是调试链路变长——Schema JSON → 渲染引擎 → React 组件树，出问题时堆栈很深。如果业务表单特别简单（少于 10 个字段），用 Formily 是过度设计，直接用 Ant Design 的 Form 组件更快。

**面试官评价要点：**
- 及格：知道 TypeScript 泛型基本用法
- 良好：能说清编译时推导 vs 运行时校验的互补关系，知道 zod 的 z.infer
- 优秀：能讨论为什么联动逻辑不追求类型完备，能评价 Formily 的工程边界

### 【框架源码-1】React Fiber — 可中断渲染的调度与恢复机制

**面试题：** 你说你「理解 React 原理」。React 16 引入 Fiber 架构后，渲染变成了可中断的。请描述：从 `setState` 调用到屏幕上的像素变化，完整链路是怎样的？Fiber 是怎么实现「中断」和「恢复」的？为什么 Fiber 没有用 requestIdleCallback？

**P10 满分答案：**

**第一步 — 核心概念/原理：**

"Fiber 的本质是给 React 的渲染过程加了一层「操作系统级的调度」"。

理解这个需要先理解 React 15 的问题：Stack Reconciler 的递归过程一气呵成，主线程被长时间占用（一帧 16ms 里可能 React 占了 50ms），导致掉帧。Fiber 做的事：把渲染拆成可中断的小工作单元（Fiber Node），用链表串联，可以在任意 Fiber 之间暂停和恢复。

**完整链路**：
```
setState → enqueueUpdate → scheduleUpdateOnFiber
  → Scheduler（优先级调度）
  → Render Phase（构建 Fiber Tree + Diff，可中断）
  → Commit Phase（DOM 变更，不可中断）
  → Layout Effects（useLayoutEffect）
  → 浏览器绘制 → Passive Effects（useEffect）
```

**第二步 — 工程实践/场景：**

中断与恢复的核心是 **Fiber 数据结构**：
```javascript
// 每个组件实例对应一个 Fiber Node（简化版）
{
  type: 'div',           // 组件类型
  stateNode: domNode,    // 对应的 DOM 节点
  child: firstChildFiber,    // 第一个子节点（单向链表）
  sibling: nextSiblingFiber, // 下一个兄弟节点
  return: parentFiber,       // 父节点
  alternate: oldFiber,       // 指向上一次渲染的 Fiber（双缓冲）
  memoizedState: hooksHead,  // Hooks 链表头
  lanes: 0b0001,             // 优先级（lane 模型）
  flags: Update,             // 副作用标记
}
```

**为什么不用 requestIdleCallback？**
1. `requestIdleCallback` 的执行优先级太低，可能永远轮不到执行
2. 它的回调间隔不稳定（Safari 不支持，polyfill 用 setTimeout，最小间隔 50ms 完全不够）
3. Fiber 需要更细粒度的控制——它需要知道「现在还能执行多久」，`requestIdleCallback` 给的是一个 `timeRemaining()` 估算，不够精确
4. React 因此自研了 **Scheduler 包**：基于 `MessageChannel`（产生宏任务）+ 5ms 时间切片（每个 Fiber 单元执行不超过 5ms 就让出主线程）+ Lane 优先级模型

"实际项目中怎么应用这个理解？"：在 IOT 的画布模块，大规模节点渲染时，如果一次性 render 全部节点，主线程卡顿明显。当时的优化方案之一是：不是让 React 去渲染全部节点，而是自己做了一层「视口内可见节点才挂载到 React 树」的逻辑——本质上是模拟了 Fiber 的「只做必要工作」的思想。但 React 18 的 `useDeferredValue` / `useTransition` 提供了更原生的支持：
```typescript
// React 18：标记低优先级更新，不阻塞用户输入
const [nodes, setNodes] = useState(allNodes);
const deferredNodes = useDeferredValue(nodes); // 可被高优先级更新打断

return <Canvas nodes={deferredNodes} />;
```

**第三步 — 深度理解/思考/踩坑：**

- **中断的是什么，不能中断的是什么**：Render Phase（生成 Fiber Tree 的过程）可中断，Commit Phase（DOM 变更）不可中断——因为 DOM 变更对用户可见，如果只改了一半就中断，用户看到的是不一致的 UI。所以 Commit 是同步的、不可分的。
- **双缓冲（Double Buffering）**：每一帧有两棵 Fiber Tree — current（屏幕上正在显示的）和 workInProgress（正在构建的）。中断时直接丢弃 workInProgress 树，下次恢复时从 current 树上重新 copy 一个新的 workInProgress 开始。这就是「不会丢失进度」的原因——因为不需要「回退 DOM」，本来就没提交。
- **Lane 模型 vs 早期 Expiration Time**：React 17 的 Expiration Time 是连续的数字，多个更新容易被打包到同一个批次导致低优先级更新饿死高优先级。React 18 的 Lane 用位运算，每位代表一个优先级，可以精细取交集、并集——IO 优先级和 CPU 优先级的调度不再互相干扰。
- **面试中容易被追问的点**：如果面试官问「你怎么确定自己写的代码不会阻断高优先级更新」，你应该答——`useTransition` / `useDeferredValue` 包裹低优先级更新，`flushSync` 强制同步（但慎用，因为它绕过了调度机制）。

**面试官评价要点：**
- 及格：知道 Fiber 是可中断的
- 良好：能说出 Scheduler + MessageChannel + 时间切片
- 优秀：能说清楚双缓冲、Lane vs Expiration Time、requestIdleCallback 为什么不用

### 【框架源码-2】React Hooks — 闭包陷阱与状态同步

**面试题：** 你在简历里写了「精通 React Hooks」。假设有一个场景：一个轮询 hooks `usePolling(fn, interval)`，每 N 秒执行一次回调，回调里需要读取最新的 state。你能写出一个不丢数据、不产生闭包陷阱的实现吗？`useRef` 在这里的作用是什么？除了这个场景，还有什么方式能解决 Hooks 的闭包陷阱？

**P10 满分答案：**

**第一步 — 核心概念/原理：**

"闭包陷阱的本质是 Hooks 的 **memoizedState 链表 + 闭包** 的副作用。"

每次 render 都会创建新的闭包上下文。`useCallback(fn, [])` 只在首次渲染创建 fn，之后不会再更新——所以 fn 内部读取的 state 永远是初始值。这就是「过时闭包」（Stale Closure）。

**第二步 — 工程实践/场景：**

```typescript
function usePolling(fn: () => void | Promise<void>, interval: number) {
  // 核心：用 ref 打破闭包陷阱
  const fnRef = useRef(fn);

  // 每次 render 更新 ref，保证轮询回调始终能拿到最新的 fn
  useEffect(() => {
    fnRef.current = fn;
  });

  useEffect(() => {
    const timer = setInterval(() => {
      fnRef.current(); // 始终读最新值
    }, interval);
    return () => clearInterval(timer);
  }, [interval]);
}
```

"为什么不用 `useCallback` + 加依赖？"：
```typescript
// ❌ 有问题的写法
const handler = useCallback(() => {
  console.log(count); // 如果依赖不加 count，读的是旧值
}, []); // 加了 count 后，count 一变，handler 引用就变，interval 被重置，轮询节奏被打乱
```

而 `useRef` 的方案：interval 只创建一次，fnRef.current 始终指向最新的 fn，闭包里读的是 ref（引用不变，值可变）。

**第三步 — 深度理解/思考/踩坑：**

解决闭包陷阱的几种方式，各有适用场景：

| 方案 | 适用场景 | 代价 |
|------|---------|------|
| `useRef` 打破闭包 | 定时器、轮询、事件监听 | 失去了 React 的「数据驱动」语义，变成命令式 |
| `useReducer` | 复杂的状态更新逻辑 | 写法比 useState 啰嗦 |
| 直接在 setState 里用函数更新 `setCount(c => c + 1)` | 新值依赖旧值时 | 只能用于当前状态，读不到其他状态 |
| `useSyncExternalStore` (React 18) | 订阅外部 store | 需要适配外部 store 的 subscribe 语义 |

"真实的坑"：在五福 NFC 项目的状态机中，Zustand 的 `getState()` 天然就是「总是读到最新值」的模式，因为它是外部 Store，不绑定 React 的渲染周期。这也是当时选 Zustand 而不是 useReducer 的一个原因——状态机的状态流转中有大量异步（轮询配对结果、定时器倒计时），Zustand 的 `getState()` 在异步回调里直接读最新状态，天然避免了闭包陷阱。

**面试官评价要点：**
- 及格：能说出闭包陷阱是什么
- 良好：能用 useRef 解决
- 优秀：能对比多种方案的使用场景，能从 Hooks 源码层面解释为什么是链表存储

### 【框架源码-3】状态管理方案对比 — Zustand vs 其他

**面试题：** 你用过 Zustand、React Context、Ant Design Pro 的 umi model。你在五福项目里选了 Zustand 做状态机，面试官可能会问：为什么不用 Redux Toolkit 或者直接用 Context + useReducer？什么场景下 Context 够用，什么场景下必须上外部 Store？

**P10 满分答案：**

**第一步 — 核心概念/原理：**

区分两个概念：「共享状态」和「响应式状态」。Context + useReducer 是 React 内置方案，但它有一个致命的性能问题——**只要 Provider 的 value 变了，所有 Consumer 都会 re-render**，不管用了 value 的哪部分。这就是「Context 的订阅粒度问题」。

Zustand 等外部 Store 的原理是用 `useSyncExternalStore`（或手动 subscribe）做细粒度订阅——只订阅你用到的字段，字段不变就不 re-render。

**第二步 — 工程实践/场景：**

"选型逻辑不是非黑即白"：

**Context 够用的场景**：
- 状态变化频率低（如主题、语言、用户信息，整个应用生命周期只变几次）
- Consumer 数量少且可控
- 不需要复杂中间件（持久化、devtools、immer集成）

**必须外部 Store 的场景**（五福项目的几个选型理由）：
1. **高频更新**：NFC 状态机每秒都在变（倒计时、轮询结果），用 Context 会导致整个组件树每秒重新渲染一次——这在低端机上扛不住
2. **异步回调中读取状态**：`getState()` 在 setTimeout / setInterval 里直接拿最新值，不需要考虑闭包陷阱
3. **跨 React 树访问**：五福的页面上有多个独立的 React 树（主页面 + 弹窗 Portal），Context 跨树需要 Provider 包裹所有 root
4. **订阅粒度**：Zustand 的选择器（selector）天然支持按字段订阅，配合 `shallow` 比较，只有相关组件更新

```typescript
// Zustand 的细粒度订阅 — 只有 count 变了，这个组件才 re-render
const count = useGameStore(state => state.count);

// 如果某组件只读 playerName，count 变了它不 re-render
const name = useGameStore(state => state.playerName);
```

**第三步 — 深度理解/思考/踩坑：**

- **为什么 Redux Toolkit 没被选**：不是因为 Redux 不好，而是因为五福项目整个团队规模小（2-3 个前端），不需要 Redux 的强约束（action type 枚举、slice 拆分、middleware 链）。Zustand 的 API 极其简单——一个 `create` 函数 + 选择器，3 分钟上手。但在 10+ 人的团队做大型中后台时，Redux Toolkit 的约束反而是优势——它强制你按规范写，降低了多人协作的维护成本。技术选型不是比谁更先进，而是看团队上下文。
- **immer 集成**：Zustand 天然支持 immer——`set(state => { state.nested.deep.value = 1 })`，不需要手动展开。这是比 immutability-helper 更直觉的方式。但注意 immer 的 `produce` 有性能开销，高频更新场景（比如动画帧更新）不要用。
- **Jotai vs Zustand vs Valtio**：都是 Poimandres 团队的，思路不同。Jotai 是「自底向上的原子化状态」（类似 Recoil），Valtio 是「Proxy 代理的响应式状态」（类似 Vue Reactive），Zustand 是「传统的 Redux 式单 Store + 选择器」。如果组件间状态依赖多且粒度细，Jotai 更合适；如果就是需要一个全局 Store 且团队熟悉 Redux 范式，Zustand 最合适。

**面试官评价要点：**
- 及格：知道 Context 有什么问题
- 良好：能说清楚 Zustand 的选择器订阅机制，能讲 Context 性能问题的本质
- 优秀：能够结合团队规模、业务场景做选型分析，理解「约束」在某些场景是「收益」

### 【工程化-1】构建工具原理 — Webpack vs Vite

**面试题：** 你简历写了熟悉 Webpack 和 Vite。它们本质的区别是什么？为什么 Vite 开发时那么快？它的原理能用在生产环境吗？如果能，为什么 Vite 生产环境还是用的 Rollup？

**P10 满分答案：**

**第一步 — 核心概念/原理：**

"Webpack 是 **Bundle First**，Vite 是 **ESM First**。"

- **Webpack**：不管你改了哪个文件，都要从入口出发，把所有依赖打包成一个或多个 bundle。开发模式下虽然不做压缩，但打包本身（resolve、AST 分析、依赖图构建）就是 O(n) 的，项目越大越慢。
- **Vite 开发模式**：利用浏览器原生 ES Module。启动时只做**预打包**（用 esbuild 把 node_modules 里的 CommonJS 依赖转成 ESM），源代码不做打包。浏览器请求哪个文件，就编译哪个文件——本质是 **on-demand compilation**。

**第二步 — 工程实践/场景：**

"当时蚂蚁的项目从 Webpack 切到 Vite，有数据对比"：

| 维度 | Webpack (webpack-dev-server) | Vite |
|------|------|------|
| 冷启动 | 45s+ | 3s |
| HMR（改一行代码到浏览器更新） | 2-3s | <100ms |
| 构建时间 | 3min+ | 50s（Rollup） |

"但 Vite 不是银弹"：
1. Vite 开发时把编译压力分摊给了浏览器——每个 import 一个请求，项目大了浏览器需要发几百个请求。所以 Vite 对 HTTP/2 有依赖（多路复用），如果某个环境不支持 HTTP/2（比如内网的 HTTP 代理），Vite 反而慢。
2. node_modules 里的依赖如果有大量 ESM 不兼容的情况，esbuild 预打包也可能失败——比如一些老的 CSS-in-JS 库、依赖 Node.js 内置模块的库。

**第三步 — 深度理解/思考/踩坑：**

- **为什么生产环境不用 ESM 方案而用 Rollup 打包**：核心原因是 HTTP 请求数量。一个生产页面有 300+ 个 ESM import，浏览器发 300 个请求，每个 round-trip 就算 20ms，光请求就 6s——页面白屏。打包成一个 bundle，一个请求 200KB，比 300 个请求 200KB 快得多（因为 HTTP 的头部开销和连接成本）。
- **Rollup 为什么比 Webpack 打包更快**：Rollup 的输出更干净（不注入 runtime），Tree Shaking 更彻底（Rollup 天然基于 ESM 的静态 import/export 分析，而 Webpack 的 Tree Shaking 依赖 TerserPlugin 对标记的 `unused harmony export` 做消除，是两步走）。但 Rollup 的生态没有 Webpack 丰富——Webpack 的 loader plugin 体系几乎覆盖所有场景。所以 Vite 的明智之处是：开发用 esbuild + 原生 ESM，生产用 Rollup，既快又稳。
- **关于 esbuild 为什么最快**：它是 Go 写的，不是 JS。编译阶段直接用 Go 的并发模型（Goroutine），而不是 Node.js 的单线程 + worker_threads。而且 esbuild 的 AST 是自建的，不做 AST → IR → Codegen 的多步转换，而是直接从源码到输出。

**面试官评价要点：**
- 及格：知道 Vite 快是因为用 esbuild + 不打包
- 良好：能解释清楚 ESM on-demand 编译原理
- 优秀：能说清楚为什么 Vite 生产用 Rollup、为什么 HTTP 请求数决定方案选择

### 【工程化-2】qiankun 微前端 — 沙箱隔离原理与 CSS 冲突

**面试题：** 你在 IOT 平台用 qiankun 做微前端。qiankun 的 JS 沙箱是怎么工作的？CSS 隔离有几种方案？各自的局限是什么？如果让你重新设计，你会怎么处理主子应用的隔离问题？

**P10 满分答案：**

**第一步 — 核心概念/原理：**

qiankun 的 JS 沙箱有两套：**SnapshotSandbox**（快照沙箱）和 **ProxySandbox**（代理沙箱）。

- **SnapshotSandbox**：在子应用激活前，把 `window` 上所有属性拍个快照存下来；在子应用卸载时，把 `window` 恢复到快照状态，删掉子应用新增的属性。问题是：遍历 `window` 所有属性非常慢，而且是「全量快照」，不支持多实例同时运行。
- **ProxySandbox**：用 `Proxy` 劫持 `window` 的操作。每个子应用的沙箱维护一个 `fakeWindow` 对象，代码里对 `window.xxx` 的读写会被 Proxy 拦截，写入操作写到 `fakeWindow` 而不是真正的 `window`。这样多个子应用可以并存，且不需要「恢复」操作。

**第二步 — 工程实践/场景：**

CSS 隔离的三层方案（从简单到复杂）：

| 方案 | 原理 | 优点 | 局限 |
|------|------|------|------|
| CSS Module | 编译时给类名加 hash | 零运行时开销 | 只对组件内 CSS 有效，全局样式不隔离 |
| Shadow DOM | 浏览器原生隔离 | 完全隔离 | 弹层/Ant Design 的 Portal 无法穿透，dialog 会被困在 Shadow DOM 里 |
| qiankun 的 experimentalStyleIsolation | 运行时给子应用所有选择器加前缀 `div[data-qiankun="xxx"]` | 对子应用无侵入 | 性能开销（遍历 CSSOM 重写），动态添加的 style 标签可能漏掉 |

"当时踩的最大的坑"：
- Ant Design 的 Dropdown/Modal 通过 Portal 渲染到 `document.body`，不受子应用根节点的 `data-qiankun` 包裹——所以样式隔离对它失效。如果不额外处理，子应用 A 的 Modal 样式可能被子应用 B 覆盖。解决方案是在 qiankun 的 `beforeMount` / `beforeUnmount` 中，配置 Antd Modal/Dropdown 的 `getPopupContainer` 指向子应用根节点。
- 主子应用如果 Antd 版本不一致（一个 4.x 一个 5.x），CSS 变量名冲突是常见的——因为 Antd 5 的 CSS-in-JS 方案（cssinjs）生成的名字在不同版本可能碰撞。解决方案是统一版本或者给子应用的 Antd 做 prefixCls 定制。

**第三步 — 深度理解/思考/踩坑：**

- **如果重新设计，我会考虑什么**：
  1. **不再强依赖 qiankun 的 JS 沙箱**，而是靠**规范约束子应用不污染 window** + 构建时 ESM 隔离。因为 Proxy 沙箱的性能开销在低端机上不可忽略（每次 `window.xxx` 访问都经过 Proxy 代理），而且某些第三方库（如部分地图 SDK）直接在 window 上挂全局对象，Proxy 沙箱拦不住。
  2. **CSS 隔离优先考虑 CSS Module + BEM 命名约定**，运行时隔离作为兜底。运行时 CSS 隔离的「全量遍历 + 重写选择器」在 DOM 节点多时（比如可视化画布有上千个节点），隔离性能开销显著。
  3. **考虑 Webpack Module Federation 替代 qiankun**：MF 在构建时确定了共享依赖（比如 React 只加载一次），而不是运行时通过 `window` 共享。缺点是不能独立部署（需要协调依赖版本）。蚂蚁内部很多团队已经从 qiankun 迁移到 MF 或自研的微前端方案了。
- **qiankun vs Module Federation 的决策框架**：如果团队独立性强、不需要同步发布、技术栈可能不同（Vue + React 混合），选 qiankun；如果团队在一个大仓、发布节奏一致、技术栈统一、追求极致性能，选 Module Federation。实际中大多数「微前端」项目是前者。

**面试官评价要点：**
- 及格：知道 qiankun 有 JS 沙箱和 CSS 隔离
- 良好：能说清楚 ProxySandbox 的原理，能列举 CSS 隔离方案的优劣
- 优秀：能讨论 Portal 穿透问题及实际解决方案，能对比 Module Federation，有自己的选型思考

### 【工程化-3】低代码表单引擎 — Schema 驱动的响应式依赖

**面试题：** 你用 Formily 做了低代码表单平台。请讲一下：Schema 定义了一个字段 A 控制字段 B 的显隐，这个「联动」在 Formily 内部是怎么从 Schema 声明变成实际的 DOM 变更的？如果你不用 Formily，自己从零实现这个联动机制，你会怎么设计？

**P10 满分答案：**

**第一步 — 核心概念/原理：**

Formily 的联动机制本质是一个「响应式依赖图」——类似 Vue 的 Dep-Watcher 模型或 MobX 的 observable-observer。

核心路径：`字段值变化 → 触发依赖收集 → 计算联动条件 → 更新目标字段状态 → 触发重渲染`。

**第二步 — 工程实践/场景：**

Formily 内部的关键环节（按链路拆解）：

1. **Schema 解析**：`x-reactions` 被解析为一个 Reaction 对象，内部有 `dependencies`（依赖哪些字段的值）和 `fulfill`（满足条件后执行什么操作）
2. **依赖收集**：每个 Field 被 Proxy 包装，当 Reaction 的 `fulfill` 函数里读取了 `$deps.xxx.value`，会触发 getter → 收集依赖
3. **脏检查/通知**：依赖的字段值变化 → getter 触发 → 遍历订阅者 → 重新执行 Reaction 的 `fulfill`
4. **批量更新**：多个 Reaction 在一个批次内触发，Formily 用 `scheduler` 合并 → 一次 commit → 一次渲染

```typescript
// Formily 联动的声明式写法
{
  province: {
    type: 'select',
    'x-reactions': {
      target: 'city',       // 联动目标字段
      effects: ['onFieldValueChange'], // 触发时机
      fulfill: {
        state: {
          visible: '{{ $self.value !== undefined }}', // 公式表达式
          dataSource: '{{ fetchCities($self.value) }}', // 异步加载选项
        }
      }
    }
  }
}
```

**如果从零实现**，核心设计：

```typescript
// 简化版依赖追踪器
class FormEngine {
  private fields = new Map<string, Field>();
  private watchers = new Map<string, Set<() => void>>(); // fieldId → 订阅者

  register(fieldId: string, config: FieldConfig) {
    const field = new Field(config);
    this.fields.set(fieldId, field);

    // 解析联动规则，建立依赖图
    for (const reaction of config.reactions) {
      for (const depId of reaction.dependencies) {
        if (!this.watchers.has(depId)) this.watchers.set(depId, new Set());
        this.watchers.get(depId)!.add(() => {
          const newState = reaction.fulfill(this.snapshot());
          this.fields.get(reaction.target)?.patch(newState);
        });
      }
    }
  }

  setValue(fieldId: string, value: any) {
    this.fields.get(fieldId)?.setValue(value);
    // 通知所有依赖此字段的 watcher
    for (const watcher of this.watchers.get(fieldId) ?? []) {
      watcher();
    }
    this.batchNotify(); // 合并更新，一次重新渲染
  }
}
```

**第三步 — 深度理解/思考/踩坑：**

- **Schema 驱动 vs 代码驱动的决策边界**：Schema 驱动适合「结构类似的表单有很多个」的场景——比如 IOT 平台有 20+ 个运营配置表单，模板是相似的。但如果每个表单都很独特（逻辑复杂、字段少、交互特殊），Schema 的抽象反而成了负担。当时订的规则是：**重复 3 次以上的表单结构才值得抽成 Schema 字段组件**，否则直接写代码。
- **Formily 的最大坑：表达式字符串调试**：`'{{ $self.value !== undefined }}'` 这种字符串表达式，写错了一个字符，在运行时才发现，没有编译时检查。而且堆栈信息很不直观——报错在 Formily 内部的表达式引擎里，不是在用户的代码行上。解决方案是：写单元测试覆盖表达式逻辑，而不是在页面上调试。
- **性能的边界**：如果一个表单有 100+ 个字段，且字段间有复杂的联动关系（比如 A 影响 B，B 影响 C，形成链路），依赖追踪的开销可能比直接计算还大。这时候「脏检查」比「依赖追踪」更合适——也就是每次值变化时全量检查所有字段是否需要更新。这是 Formily 默认用依赖追踪的原因（99% 场景它更快），但极端场景需要知道怎么降级。

**面试官评价要点：**
- 及格：知道 Formily 是 Schema 驱动的，能说出联动的基本概念
- 良好：能描述依赖收集 → 通知 → 更新的链路
- 优秀：能设计自己的简化版实现，能讨论 Schema 驱动的适用边界和性能极限

## 四、性能优化

简历关键词：首屏性能优化、FCP 4.5s→2.0s、帧率 30fps→55fps+、内存泄漏排查、CDN 接入。

---

### 【性能优化-1】首屏加载 — FCP 优化的完整链路

**面试题：** 你把五福活动的 FCP 从 4.5s 降到了 2.0s。请具体说：你用了什么工具测量的？4.5s 这个数据的组成是怎么拆解的？你分别做了什么优化？减少的 2.5 秒分别从哪些环节省出来的？

**P10 满分答案：**

**第一步 — 核心概念/原理：**

FCP（First Contentful Paint）是浏览器首次渲染任何内容的时间点。它的瓶颈通常不在 JS 执行，而在**网络阶段**。理解 CRP（Critical Rendering Path）：`DNS → TCP → TLS → Request → Response → Parse HTML → Load CSS → Build CSSOM → Load JS → Execute JS → Render`。

FP < FCP < LCP。FCP 是「有东西出来了」，LCP 是「最重要的内容出来了」。优化 FCP 最核心的思路是：**减少关键路径上的阻塞资源**。

**第二步 — 工程实践/场景：**

"当时的拆解和方法（数据为示例，实际上有 Lighthouse + Web Vitals 监控数据支撑）"：

| 环节 | 原始耗时 | 优化后 | 省下 | 手段 |
|------|---------|--------|------|------|
| DNS + TCP + TLS | ~600ms | ~150ms | 450ms | CDN 预缓存（阿里 CCDN）+ DNS Prefetch + preconnect |
| HTML 响应 | ~800ms | ~200ms | 600ms | CDN 边缘节点缓存 HTML + 接口预请求 |
| 阻塞 JS/CSS 下载 | ~1500ms | ~600ms | 900ms | 代码分割 + 按需加载 + Tree Shaking |
| JS 执行 + 渲染 | ~1600ms | ~1050ms | 550ms | 非首屏资源懒加载 + 动画首帧前完成降级决策 |
| **总计 (FCP)** | **~4.5s** | **~2.0s** | **2.5s** | |

具体手段细节：
1. **资源预加载器**：不是简单的 `<link rel="preload">`，而是根据游戏阶段做**预测性预加载**。A 阶段结束时，后台静默加载 B 阶段的资源，用户无感。但如果 A 阶段用户只花了 2 秒就完成了，B 阶段的资源还在加载怎么办？——预加载器维护了加载状态，进入 B 阶段时如果资源还没好，显示骨架屏；好了就直接展示。这就是「懒加载 + 预加载的组合拳」。
2. **CCDN（阿里内容分发）**：本质是边缘 CDN + DNS 优化。五福活动是全国性的，用户分布广，CCDN 把静态资源推到离用户最近的节点，DNS 解析也走阿里的 HTTPDNS（绕过运营商 Local DNS 的劫持和慢解析）。
3. **接口预请求**：在 HTML 里内联一个 `<script>`，在 JS Bundle 加载之前，先发一个 `fetch` 拿核心数据。数据到达时 JS 刚好加载完，直接消费。代价是：这个 `<script>` 是阻塞的（inline script 会阻塞 HTML 解析），所以只放最核心的请求。

**第三步 — 深度理解/思考/踩坑：**

- **4.5s → 2.0s 不是线性优化**：前 1s 比较好省（CDN + 压缩），后面的每 500ms 都是硬骨头。比如优化 JS 执行时间，从 1600ms → 1050ms，靠的是拆分 + 懒加载，但懒加载带来的问题是：用户点了按钮，资源还没加载，需要额外处理 loading 态。所以优化方案是整体设计的，不是单个手段的堆砌。
- **怎么验证优化效果**：靠 Web Vitals 的上报。`web-vitals` 库嵌在页面里，每次 FCP/LCP/CLS 变化时上报。但注意：实验室数据（Lighthouse 本地测的）和实际用户数据（RUM，Real User Monitoring）往往差很大——因为用户网络环境千差万别。当时建立了一个「性能预算」——FCP P75 < 2.5s，超过就告警。
- **Lighthouse 分数不代表一切**：Lighthouse 99 分不代表用户真的快。因为 Lighthouse 是在本地高速网络 + 无 CPU 节流下模拟的。真正要关注的是 RUM 数据、用户投诉、Crash 率。

**面试官评价要点：**
- 及格：知道 FCP 是什么，能说出几种优化手段
- 良好：能量化拆解各项耗时，知道 CDN / preload / 代码分割的作用
- 优秀：能区分实验室数据和 RUM，有性能预算体系的概念，能说清楚预加载和懒加载的矛盾和平衡

### 【性能优化-2】动画帧率优化 — 从底层机制到分级策略

**面试题：** 你说五福的 Mars 引擎动画在低端机上从 30fps 优化到了 55fps+。从浏览器渲染的底层来看，帧率掉到 30fps 的原因有哪几类？你的「设备性能分级策略」中，CSS/SVG 动画比 Mars 引擎动画快的原理是什么？这个方案有什么局限？

**P10 满分答案：**

**第一步 — 核心概念/原理：**

浏览器一帧的预算只有 16.67ms（60fps）。帧率掉的原因分三类：

1. **JS 执行超预算**：主线程被 JS 占用（长任务 > 50ms），Layout/Paint/Composite 被推迟
2. **Layout Thrashing**：强制同步布局——在 JS 里写 `element.offsetHeight` 后立刻修改样式，导致浏览器必须立即计算布局
3. **绘制开销过大**：每一帧要重绘的区域太大、图层太多、或者不必要的合成层（隐式合成）

Mars 引擎的问题主要是**第 3 类 + GPU 瓶颈**：Mars 基于 WebGL/Canvas 渲染粒子动画，低端机的 GPU 性能不够，绘制一帧超过 16.67ms，就掉帧。

**第二步 — 工程实践/场景：**

CSS/SVG 动画比 Canvas 快，不是因为 CSS 本身更快，而是因为**浏览器可以把它放到合成器线程（Compositor Thread）独立处理**：

- CSS `transform` + `opacity` 动画：触发 Composite 阶段，不经过 Layout 和 Paint，合成器线程可以独立完成，主线程阻塞了动画也不会卡
- Canvas 动画：每帧都要在主线程上执行 JS → 调用 GPU API → 等待 GPU 返回 → 合成。主线程任何一个长任务都会导致掉帧
- SVG 动画：可以用 SVG SMIL 或 CSS animation，也走合成器线程，且矢量图形在低端机上缩放不发虚

```typescript
// 分级策略的核心——在首帧渲染前做完决策
function getPerformanceTier(): 'high' | 'mid' | 'low' {
  // 方法1：UA 特征
  const ua = navigator.userAgent;

  // 方法2：容器 JSAPI 获取设备硬件信息（支付宝容器内有效）
  const deviceInfo = await jsapi.getDeviceInfo(); // CPU 核心数、内存、GPU 型号

  // 方法3：实际性能基准测试（在执行前跑一个轻量 benchmark）
  const score = computeScore(ua, deviceInfo, memory);

  // 按分位线划分
  if (score > 70) return 'high';
  if (score > 30) return 'mid';
  return 'low';
}

// 渲染决策映射
const AnimationStrategy = {
  high: { engine: 'mars', effects: ['particle', 'bloom', 'rotate'] },
  mid:  { engine: 'css-svg', effects: ['simple-rotate', 'fade'] },
  low:  { engine: 'static', effects: ['image-sequence'] },
};
```

**第三步 — 深度理解/思考/踩坑：**

- **「合成层陷阱」—— 隐式合成**：以为给一个元素加了 `will-change: transform` 就只会提升这一个，但实际上如果它和一个 `z-index` 较低的元素重叠，浏览器可能把周围一堆元素都提升到合成层，导致内存暴涨。这是 Chrome 的「隐式合成」行为，DevTools 的 Layers 面板可以看到。解决方法：给合成元素设置较高的 `z-index`，避免和其他元素层叠。
- **为什么不在运行时动态切换动画策略**：因为用户已经看到了高配动画，切换到低配会有视觉跳变。所以降级决策必须在首帧渲染前完成。这就要求「设备信息获取」必须在 JS 的最前面同步完成，不能等异步请求。
- **低端机的「看似流畅」和「真的流畅」不一样**：55fps 是平均值，但可能有单帧超过 100ms 的卡顿（jank），用户感知很明显。要关注的是 **帧时间的 P99** 而不是平均帧率。
- **这个方案的局限**：只能分三档，且分档规则是拍脑袋定的。更理想的做法是用 **RAIL 模型 + 自适应降级**——实时监控帧率，动态减效果，但复杂度高很多，不适合短期项目。

**面试官评价要点：**
- 及格：知道 CSS transform 动画性能好
- 良好：能说清楚 Composite 阶段和合成器线程，知道 GPU 加速的原理
- 优秀：能讨论隐式合成陷阱、为什么决策要在首帧前完成、帧时间 P99 vs 平均帧率

### 【跨端-1】JSBridge 通信原理与协议设计

**面试题：** 你在招银云创主导了 JSBridge 通信协议的设计。请说说：H5 和 Native 之间双向通信的底层原理是什么？你设计的协议解决了什么问题？如果一个 JSBridge 调用 5 秒没有收到 Native 回复，你的方案怎么处理？

**P10 满分答案：**

**第一步 — 核心概念/原理：**

JSBridge 本质是在 WebView 和 Native 之间建立一条**异步消息通道**。三要素：消息序列化格式、传输载体、回调机制。

**传输载体有三种**：
1. **URL Scheme 拦截**（最老）：H5 用 `location.href = 'bridge://method?params'` 发请求，Native 拦截 URL 变化。Android 拦截 `shouldOverrideUrlLoading`，iOS 拦截 `webView:shouldStartLoadWithRequest:`。缺点：有长度限制（URL 2KB 左右）、不支持回调、会触发页面跳转闪烁
2. **Native 注入 API**（最常见）：Native 在 `window` 上注入对象，比如 `window.NativeBridge.call(method, params, callback)`。Android 用 `addJavascriptInterface`（有安全风险，4.2 以下可被反射利用），iOS 用 `WKScriptMessageHandler`（WKWebView，安全）
3. **`postMessage` 或 `evaluateJavascript`**：WebView 间或 Native → H5 通信。`evaluateJavascript` 是 Native 调用 JS 的主动方式，但它是异步的

**第二步 — 工程实践/场景：**

"当时设计的协议规范包含这几个核心设计"：

```typescript
// JSBridge 协议核心设计
interface BridgeMessage {
  id: string;            // 全局唯一 ID，用于回调和超时追踪
  method: string;        // 调用方法名 'device.scanQRCode'
  params: Record<string, unknown>;
  callbackId?: string;   // 如果有，Native 回复时带回
}

interface BridgeResponse {
  id: string;
  code: number;          // 0 成功，非 0 错误码
  data?: unknown;
  error?: string;
}

// Promise 化封装 — 把回调地狱变成 async/await
class JSBridge {
  private pending = new Map<string, {
    resolve: Function;
    reject: Function;
    timer: number;
  }>();

  call<T>(method: string, params: Record<string, unknown>, timeout = 10000): Promise<T> {
    const id = generateId();
    return new Promise((resolve, reject) => {
      // 超时保护
      const timer = setTimeout(() => {
        this.pending.delete(id);
        reject(new BridgeError('TIMEOUT', `call ${method} timeout after ${timeout}ms`));
      }, timeout);

      this.pending.set(id, { resolve, reject, timer });
      this.post({ id, method, params });
    });
  }

  // Native 回调入口
  onNativeResponse(resp: BridgeResponse) {
    const pending = this.pending.get(resp.id);
    if (!pending) return; // 超时后的延迟回复，丢弃
    clearTimeout(pending.timer);
    this.pending.delete(resp.id);
    if (resp.code === 0) {
      pending.resolve(resp.data);
    } else {
      pending.reject(new BridgeError(resp.code, resp.error));
    }
  }
}
```

**设计的核心要点**：
1. **Promise 化**：把回调模式改成 async/await，解决回调地狱
2. **超时机制**：每个调用都有一个定时器，超时自动 reject 并清理 pending 队列，防止内存泄漏
3. **版本兼容**：Native SDK 可能有不同版本，某些方法在旧版本不支持——加了一层 `isMethodSupported(method, minVersion)` 检查，调用前先降级判断
4. **降级策略**：如果 JSBridge 不可用（如在外部浏览器中打开），自动降级到 H5 自己的实现（如用 HTML5 API 代替 Native API）

**第三步 — 深度理解/思考/踩坑：**

- **Android `addJavascriptInterface` 的安全漏洞**：Android 4.2 以下，注入的 Java 对象的 public 方法可以被 JS 通过反射调用，包括 `Runtime.exec()`。这就是著名的 **WebView 远程代码执行漏洞**。4.2+ 加了 `@JavascriptInterface` 注解限制，但只建议在内部应用中用。在对外 App 中更安全的方案是通过 `WebChromeClient.onJsPrompt` 拦截消息——JS 调 `window.prompt()`，Native 拦截，不是一个常规做法但确实比注入安全。
- **WKWebView vs UIWebView 的差异**：iOS 端 WKWebView 的 JS 执行在独立进程，内存管理更好（不像 UIWebView 和 App 共享进程，内存泄漏会导致整个 App 被杀）。但 WKWebView 的文件上传、Cookie 同步和缓存策略与 UIWebView 表现不同——比如 WKWebView 不会自动在 AJAX 请求中带 Cookie（iOS 11 之前），需要手动在 Native 层注入 Cookie。
- **JSBridge 的性能考量**：Native 注入的 API 调用虽然快，但如果高频率调用（比如滚动事件中每帧调用一次），通信开销会很大。当时设计了一条规则：**高频数据用 `evaluateJavascript` 一次性下发给 H5，H5 在 JS 层做节流，降低 Bridge 调用频率**。

**面试官评价要点：**
- 及格：知道 JSBridge 的基本概念
- 良好：能说清 URL Scheme 和注入 API 的区别，知道超时机制
- 优秀：能讲安全漏洞（Android 反射）和 WKWebView 的 Cookie 问题，有版本兼容与降级设计

### 【跨端-2】WebView 白屏 — 排查与兜底

**面试题：** 你说设计了 WebView 白屏/渲染异常的兜底方案。白屏的原因有哪些？你怎么区分类别，分别怎么兜底？如果用户在弱网环境下打开页面，你的方案是怎么表现的？

**P10 满分答案：**

**第一步 — 核心概念/原理：**

WebView 白屏的分类（按根因分层）：

| 类别 | 根因 | 现象 |
|------|------|------|
| **网络层** | DNS 失败/TCP 超时/HTTP 非 2xx | HTML 都没下载，WebView 一片空白 |
| **资源层** | JS Bundle 404/503/CDN 故障 | HTML 下载了，但 JS 报错，React 没挂载 |
| **脚本层** | JS 报错（语法错误/API 不兼容/依赖缺失）| React 挂载了但渲染中断 |
| **渲染层** | CSS 异常/WebView 内核 bug/内存不足 | JS 执行正常，DOM 存在但不可见 |

**第二步 — 工程实践/场景：**

"兜底方案是分层设计的"：

```
用户打开页面
  ├── 网络正常？
  │    ├── YES → HTML 返回 200？ → YES → 继续
  │    │                          → NO  → Native 降级页（"服务繁忙"）
  │    └── NO  → Native 离线兜底页（本地预置的 HTML）
  │
  ├── JS 加载成功？（静态监听 window.__MAIN_LOADED__）
  │    ├── YES → React 渲染成功？→ YES → ✅ 正常页面
  │    │                        → NO  → Native WebView 重试（reload WebView）
  │    └── NO  → 重试 CDN（切到备用域名）→ 仍失败 → Native 降级页
  │
  └── 白屏检测（MutationObserver + 采样像素点）
       └── 5s 内无内容渲染 → 自动 reload WebView
```

"白屏检测的简单实现"：
```javascript
// 白屏检测 — 在 HTML 的 <head> 里内联（不能等 JS Bundle 加载）
(function() {
  var start = Date.now();
  var timer = setInterval(function() {
    // 方法1：检测根节点是否有内容
    var root = document.getElementById('root');
    if (root && root.children.length > 0) {
      clearInterval(timer);
      return; // 正常渲染
    }
    // 方法2：采样骨架屏判定 — 取页面四角和中心的像素
    // 如果全是白色，判定为白屏
    if (Date.now() - start > 5000) {
      clearInterval(timer);
      // 上报 + reload
      location.reload();
    }
  }, 500);
})();
```

**第三步 — 深度理解/思考/踩坑：**

- **白屏检测的准确性很难保证**：用 `MutationObserver` 检测 DOM 变化不能区分「正常加载中」和「已经挂了」——比如网络慢的时候，5s 可能还在加载，reload 反而让用户更慢。所以检测逻辑需要和资源加载状态联动：如果 5s 内 DOM 无变化 + 资源加载状态是 idle/error，才判定为白屏。
- **WKWebView 的一个特殊坑**：iOS WKWebView 在内存压力大时，会直接杀掉 WebView 进程而不触发任何回调（不会执行 JS 的 `beforeunload`）。表现为「页面突然白了，然后自动恢复」。这种情况 reload 是没用的，需要在 Native 层监听 `webViewWebContentProcessDidTerminate`，重建 WebView。
- **离线兜底页的设计原则**：不能只显示「网络错误」，要给出有用的信息。比如五福活动离线页展示了活动规则和参与方式（本地预置的图文），用户在恢复网络后可以看到入口按钮。
- **为什么不用 Service Worker 做离线兜底**：因为 WebView 的 SW 支持不一致——iOS WKWebView 到 iOS 14+ 才支持，且 App 中的 WKWebView 默认不启用 SW（需要 Native 端额外配置）。所以离线兜底只能靠 Native 端的离线包机制。

**面试官评价要点：**
- 及格：知道白屏需要兜底，能说 reload
- 良好：能讲清白屏的分类，能设计分层兜底
- 优秀：能讨论 WKWebView 进程被杀的特殊场景，能讨论检测准确性的工程权衡

### 【跨端-3】小程序性能优化 — 包大小与懒加载

**面试题：** 你提到对小程序做了包大小优化和动态加载。小程序的主包限制通常是 2MB，你是怎么做拆分的？主包和分包之间的通信和跳转有什么坑？

**P10 满分答案：**

**第一步 — 核心概念/原理：**

支付宝小程序的包分两类：**主包**（打开即加载，限制 2MB）和**分包**（按需加载，总限制 20MB）。核心优化思路是：主包只放首屏必要资源，其他全部下沉到分包。但挑战在于：公共组件和公共依赖如果放在主包之外，分包之间不能共享。

**第二步 — 工程实践/场景：**

"实际做法三步走"：

**1. 分析现状**：用开发者工具的「代码质量」面板，看哪些文件在主包里占用大。常见罪魁祸首：大的图片（base64 内联）、未 Tree Shaking 的组件库、重复的 polyfill。

**2. 主包瘦身**：
```
原主包 2.3MB（超标300KB）
├── 砍掉 base64 图片 → 上传 CDN → 省 450KB
├── 组件库按需引入（Ant Design Mobile 不要全量 import）
│    └── import { Button } from 'antd-mobile' 改为 import Button from 'antd-mobile/es/button'
│    └── 省 200KB
├── 公共工具函数拆分到分包后的共享策略 → 省 150KB
├── moment.js → dayjs（省 60KB）
└── 优化后：1.44MB（达标）
```

**3. 分包加载策略**：
```javascript
// 分包预加载 — 在用户进入主页时，后台预下载分包
my.loadSubPackage({
  name: 'game',       // 游戏分包名
  success() { /* 预加载完成，跳转秒开 */ },
});

// 分包间共享模块 — 放在一个 common 分包，被其他分包引用
// app.json
{
  "subPackages": [
    { "root": "common", "pages": [] },       // ✅ common 分包可被其他分包引用
    { "root": "game",   "pages": ["index"] },
    { "root": "profile","pages": ["index"] }
  ]
}
```

**分包通信的坑**：
- 分包之间不能通过 `getCurrentPages()` 直接通信——因为页面栈里的页面可能来自不同分包，而分包卸载后其中页面的引用会失效
- 解决方案：用全局 `getApp().globalData` 或小程序的 EventBus 做数据中转，不用直接引用页面实例

**第三步 — 深度理解/思考/踩坑：**

- **支付宝 vs 微信小程序的差异**：支付宝的分包限制更宽松（主包 2MB vs 微信也 2MB，但总包 20MB vs 微信 20MB 含主包），但支付宝的独立分包（independent subpackage）限制更多——不能引用主包的公共组件。所以需要仔细规划哪些组件放主包、哪些放分包。
- **插件也有包大小**：支付宝插件有独立的 2MB 限制。如果插件里引用了一个大库，插件使用者会被这个额外体积拖累。当时做了「插件按需导出」——只导出核心 API，完整功能通过插件内部的动态加载实现。
- **预加载的时机和成本**：`loadSubPackage` 不是免费的——它消耗网络带宽和小程序内存。如果预加载了 5 个分包，但用户只访问了 1 个，剩下 4 个白白占了内存。当时规则：只在用户行为有强烈意图时才预加载（比如点击了「进入游戏」的入口，开始下载游戏分包），而非进入首页就全预加载。

### 【项目深挖-2】FMS 状态机 — 边界态的完整覆盖

**面试题：** 五福 NFC 项目中的有限状态机（FSM）是你设计的。你说解决了「简单 if/else 流程极易产生状态逻辑混乱」的问题。请具体描述一个最复杂的边界态场景，以及你的 FSM 是怎么处理它的。

**P10 满分答案：**

**第一步 — 核心概念/原理：**

FSM 的核心约束是：在任何时刻，系统只能处于一个确定的状态；状态之间的跃迁受规则约束。这解决的核心问题是——**使得不可能的状态在编译期就被排除掉**（用 TypeScript 枚举和联合类型）。

**第二步 — 工程实践/场景：**

最复杂的边界态场景：「单边碰成功 + 对端网络断开」。

场景描述：
```
用户 A（碰撞中）──── NFC 碰成功 ────→ 用户 A 进入「配对查询中」
用户 B（碰撞中）──── 网络断开 ────────→ 用户 B 进入「网络异常」

此时：A 已经碰撞成功，在轮询等待配对结果
      B 网络断了，不知道 A 是否成功了
```

如果用 if/else 写：
```typescript
// ❌ 传统写法 — 状态混乱且无法穷尽所有情况
if (aState === 'colliding' && bNfcOk) {
  aState = 'querying';
}
if (bState === 'colliding' && bNetworkFailed) {
  bState = 'networkError';
}
// 问题：A 在 querying 时，如果 B 网络恢复了，A 的状态要不要变？
//       如果 B 恢复了但 A 已经出奖了，B 的状态是什么？
//       这种交叉组合会爆炸
```

FSM 的解法：
```typescript
type GameState =
  | 'idle'
  | 'permission_checking'
  | 'guide_blocking'
  | 'game_starting'
  | 'colliding'
  | 'pair_querying'    // 等待配对结果
  | 'reward_showing'    // 展示奖励
  | 'error_handling';   // 统一异常处理

// 用 Zustand 实现的状态管理器
const useGameFSM = create<GameStore>((set, get) => ({
  state: 'idle',
  peerState: null as PeerState | null,

  // 核心：transition 函数，只允许合法的状态跃迁
  transition(to: GameState) {
    const from = get().state;
    if (!isValidTransition(from, to)) {
      console.error(`非法状态跃迁: ${from} → ${to}`);
      reportError('fsm_invalid_transition', { from, to });
      return;
    }
    set({ state: to });
    get().onStateEnter(to); // 进入新状态时执行副作用
  },

  // 状态进入时执行副作用（统一的 Effect 管理）
  onStateEnter(state: GameState) {
    switch (state) {
      case 'colliding':
        get().startCollisionTimer();
        get().startPairingPoll();  // 启动配对轮询
        break;
      case 'pair_querying':
        get().startQueryTimer(30000); // 30秒超时
        break;
      case 'reward_showing':
        get().broadcastPeerResult();  // 广播同步给对端
        break;
      case 'error_handling':
        get().showErrorUI();
        get().reportError();
        break;
    }
  },

  // 配对轮询 — 核心的异步逻辑
  async startPairingPoll() {
    const timer = setInterval(async () => {
      const result = await checkPairResult();
      if (result) {
        get().transition('reward_showing');
        get().broadcastPeerResult();
      }
    }, 2000);
    // 30 秒超时进入异常
    setTimeout(() => {
      if (get().state === 'pair_querying') {
        get().transition('error_handling');
      }
    }, 30000);
  },
}));
```

**处理「单边碰成功 + 对端网络断开」的完整流程**：
1. A 进入 `colliding` → NFC 成功 → 进入 `pair_querying` → 开始轮询
2. B 进入 `colliding` → 网络断开 → 进入 `error_handling` → 显示「网络异常」
3. B 网络恢复 → B 重新进入 `colliding` → 配对查询结果发现 A 已经成功了 → B 进入 `reward_showing`（**广播同步机制**：不依赖 B 自己的 NFC 硬件，而是通过后端配对结果来实现双端一致）
4. 如果 B 一直没恢复 → A 的 `pair_querying` 30 秒超时 → A 进入 `error_handling`（而非一直等待）

**第三步 — 深度理解/思考/踩坑：**

- **FSM 的层次设计**：7 个状态看起来少，但每个状态内部还有子状态（比如 `colliding` 内有关键帧动画阶段、提示语切换阶段）。设计了「主状态机 + 子状态上下文」——主 FSM 管理流程跃迁，子状态用普通的 React state 管理，避免主状态机膨胀。这也是 `XState` 等 FSM 库的思路，但当时没有引入（团队规模小，自研就够了）。
- **广播同步的最终一致性**：双端不一定 100% 同时出奖（网络延迟），但这个场景下 300ms 的差异用户感知不到。设计目标不是强一致性，而是「最终一致性 + 视觉自然的过渡动画」。
- **如果不用 FSM**：可以用 Actor Model（每个用户的游戏进程是一个 Actor，通过消息通信），但这个项目规模不需要。或者用 Redux Saga 的 Generator 管理异步流程——Saga 的方式本质也是状态机，但用 Generator 的 yield 来做状态跃迁，代码更接近同步写法。五福项目没选 Saga 是因为团队已有 Zustand 的使用习惯。

**面试官评价要点：**
- 及格：知道状态机能解决什么问题
- 良好：能画出状态流转图，能说清楚边界态处理
- 优秀：能讨论 FSM 的层次设计（主/子状态）、广播同步的一致性策略、不同方案的适用场景

### 【项目深挖-3】技术决策复盘 — 低代码表单 vs 代码生成

**面试题：** 你基于 Formily 做了低代码表单引擎。当时有没有考虑过「代码生成」方案——即根据配置直接生成 React 组件的源代码？这两种方案各有什么优劣？你当初为什么选 Schema 驱动而不是代码生成？

**P10 满分答案：**

**第一步 — 决策背景：**

当时的需求：有 20+ 个运营配置表单，结构相似但不完全相同。产品希望自己能改一些简单配置（如字段顺序、必填/选填），但不涉及业务逻辑变化。

两个方案：
- **Schema 驱动**（Formily）：运行时解析 JSON Schema，动态渲染表单
- **代码生成**：根据配置生成 React 组件源代码 → CI 构建 → 部署

**第二步 — 选型分析：**

| 维度 | Schema 驱动 | 代码生成 |
|------|------------|---------|
| 配置修改成本 | 改 JSON → 即时生效 | 改配置 → 生成代码 → 构建部署 → 生效 |
| 复杂逻辑支持 | 有限（Schema 能表达的逻辑有上限） | 无限（生成的代码可以加任何逻辑） |
| 调试体验 | 差（出问题在 Schema 解析层，堆栈深） | 好（生成的代码就是源码，DevTools 直出） |
| 运行时性能 | 有解析开销 | 和手写代码一样 |
| 灵活性 | 产品可自助改 | 只能改配置，改不了生成的代码逻辑 |

选 Schema 驱动的核心原因：**当时的需求方（产品/运营）的诉求是「自助配置」，不是「开发者生成代码再发版」**。代码生成的方案意味着每次改配置都要走 CI/CD 流程，单次变更的时间成本在 1 小时以上（提交 + 构建 + 灰度验证 + 全量），而 JSON 配置是秒级生效的。

**第三步 — 深度理解/思考/踩坑：**

- **实际运行中暴露的问题**：Schema 驱动的调试成本被低估了。一次表单联动的 bug 排查，需要在「Schema JSON → Formily Reaction 引擎 → React 组件树 → 最终的 DOM」这个链路上定位，链路太长。后来做了两个补救措施：
  1. **Schema 调试面板**：在开发环境渲染一个 DevPanel，实时展示 Schema 的解析结果和各字段的当前状态（值、visible、disabled、errors），相当于 Formily 的 Redux DevTools
  2. **Schema 校验工具**：发布前在 CLI 里跑 Schema 的校验规则（字段引用是否存在、表达式语法是否正确），提前发现低级错误

- **「低代码」的边界感很重要**：低代码只适合「结构化重复」的场景，不适合「逻辑复杂 + 交互独特」的场景。IOT 平台的表单是前一种——字段多但交互固定（输入框、选择器、日期）。但如果是一个复杂的审批流表单（每个节点有不同的权限、不同的校验规则），Schema 表达不了，应该回归代码。

- **两种方案的融合**：现在回头看，最优解可能是 **Schema 驱动做 90% 的通用表单 + 代码扩展做 10% 的复杂定制**。Formily 支持在 Schema 中引用自定义组件和自定义 Reaction，这就是为「代码扩展」留的口子。当时的做法也确实是这么做的——通用表单 Schema 化，特殊表单走代码。

### 【AI前端-1】SSE 流式渲染的完整前端方案

**面试题：** 你基于 SSE 做了流式渲染。请描述：从用户输入问题开始，到页面上逐字显示 AI 回复，中间的完整数据链路是怎样的？流式渲染中，如果连接断开怎么办？你怎么保证「断线重连」后不丢消息、不重复消息？

**P10 满分答案：**

**第一步 — 核心概念/原理：**

SSE（Server-Sent Events）是 HTTP 长连接，服务端持续推送事件流，客户端通过 EventSource API 消费。关键特性：单向（服务端 → 客户端）、自动重连（浏览器原生支持）、基于 HTTP（不需要升级为 WebSocket）。

完整链路：
```
用户输入 → 前端 fetch POST → BFF(NestJS)
  → BFF 调用大模型 API(stream: true)
  → 大模型逐 token 返回
  → BFF 逐 token 转发给前端(SSE)
  → 前端 EventSource/ReadableStream 逐 token 渲染
  → UI 逐字显示（打字机效果）
```

**第二步 — 工程实践/场景：**

"当时为什么不直接用前端调大模型 API 而要加 BFF 层？"

三个原因：
1. **API Key 安全**：不能暴露在前端代码里
2. **多模型适配**：不同大模型的 SSE 格式不一样（OpenAI 的 `data: [DONE]` vs 其他厂商的自定义结束标记），BFF 层统一抹平
3. **鉴权和审计**：用户身份验证、调用次数统计、内容安全审查，都在 BFF 层做

```typescript
// BFF 层（NestJS）- SSE 转发
@Post('chat/stream')
@Header('Content-Type', 'text/event-stream')
@Header('Cache-Control', 'no-cache')
@Header('Connection', 'keep-alive')
async chatStream(@Body() body: ChatDto, @Res() res: Response) {
  const stream = await this.aiService.streamChat(body.messages);

  // 核心：逐 chunk 转发，每个 chunk 包装成 SSE 格式
  for await (const chunk of stream) {
    res.write(`data: ${JSON.stringify(chunk)}\n\n`);
  }
  res.write('data: [DONE]\n\n');
  res.end();
}
```

```typescript
// 前端 — ReadableStream 消费（比 EventSource 更灵活）
async function streamChat(messages: Message[]): Promise<string> {
  const response = await fetch('/api/chat/stream', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ messages }),
  });

  const reader = response.body!.getReader();
  const decoder = new TextDecoder();
  let fullText = '';

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;

    const text = decoder.decode(value, { stream: true });
    // SSE 格式：data: {...}\n\n
    for (const line of text.split('\n')) {
      if (line.startsWith('data: ')) {
        const data = line.slice(6);
        if (data === '[DONE]') break;
        const chunk = JSON.parse(data);
        fullText += chunk.content;
        // 增量更新 UI（React state setter）
        onChunk(chunk.content);
      }
    }
  }
  return fullText;
}
```

**第三步 — 深度理解/思考/踩坑：**

**断线重连方案 —— 基于消息 ID 的断点续传：**

```typescript
// 核心机制：服务端给每个 chunk 编号，前端记录 lastReceivedId
// 重连时带上 lastReceivedId，服务端从该 ID 之后继续发送
class StreamManager {
  private lastMessageId = 0;
  private buffer: string[] = [];   // 已接收的文本，防止丢失

  async connect(messages: Message[]) {
    try {
      const resp = await fetch('/api/chat/stream', {
        method: 'POST',
        body: JSON.stringify({
          messages,
          lastMessageId: this.lastMessageId, // 断点续传
        }),
      });
      await this.consumeStream(resp);
    } catch (e) {
      // 自动重连（指数退避）
      await this.reconnect(messages);
    }
  }

  async reconnect(messages: Message[]) {
    for (let attempt = 1; attempt <= 3; attempt++) {
      await sleep(Math.pow(2, attempt) * 1000); // 2s, 4s, 8s
      try {
        await this.connect(messages);
        return; // 重连成功
      } catch (e) {
        if (attempt === 3) throw new Error('重连失败');
      }
    }
  }
}
```

**几个需要注意的点**：
- **「丢消息」比「重复消息」更严重**：重复消息可以通过 UI 去重（用 messageId），但丢消息意味着用户看到的内容不完整。所以宁可重发，不能漏发。
- **EventSource vs ReadableStream**：EventSource 不支持 POST 请求（只能 GET），不能带自定义 Header（如 Authorization）。ReadableStream（fetch 的 `response.body`）更灵活，但需要手动解析 SSE 格式和数据缓冲，代码量多了一倍。项目中用的是 ReadableStream（因为需要 POST），但如果是简单的通知推送场景，EventSource 足够了。
- **流式渲染的 UI 闪烁问题**：每次收到一个 token 就 `setState`，React 在短时间内高频 setState，低端机上可能出现闪烁。优化方法是——用一个 `requestAnimationFrame` 做 token 的批量合并：

```typescript
let rafId: number;
let pendingText = '';

function onToken(token: string) {
  pendingText += token;
  if (!rafId) {
    rafId = requestAnimationFrame(() => {
      setDisplayText(prev => prev + pendingText);
      pendingText = '';
      rafId = 0;
    });
  }
}
```

### 【AI前端-2】Function Calling 的前端落地 — 工具调用与 UI 交互

**面试题：** 你提到了 Function Calling。在一个对话场景中，用户说「帮我查下最近一周设备告警数最高的 5 台设备」，AI 需要调用 Function 去查数据库。请描述从前端发出这个请求到渲染结果的全链路。中间 AI 调 Function 时，前端应该显示什么？如果 Function 调用失败了怎么办？

**P10 满分答案：**

**第一步 — 核心概念/原理：**

Function Calling（也叫 Tool Use）的流程不是「用户问 → AI 答」的简单对话，而是多轮的交互式流程：

```
用户输入 → 前端 → BFF → 大模型（判断需要调哪个 tool）
  → 返回 tool_call（不返回文本）→ BFF 执行 tool → 拿到结果
  → 把结果发回大模型 → 大模型基于结果生成最终回复
  → 流式返回给前端
```

本质是「大模型做决策 + 后端执行 + 大模型做总结」的三段式。

**第二步 — 工程实践/场景：**

```typescript
// 前端 — 处理多轮 tool call 的完整流程
async function chatWithTools(userMessage: string) {
  // 1. 发送用户消息
  addMessage({ role: 'user', content: userMessage });

  // 2. 调用 BFF，BFF 内部可能有多轮 tool call
  const stream = await fetchChatStream({ messages });

  for await (const event of stream) {
    switch (event.type) {
      case 'tool_call': {
        // 3a. 显示「正在执行工具」—— 给用户的中间态反馈
        addMessage({
          role: 'assistant',
          content: null,
          toolCalls: [{
            name: event.toolName,        // 'query_device_alerts'
            arguments: event.arguments,   // { days: 7, limit: 5, sort: 'desc' }
            status: 'executing',          // 执行中
          }]
        });
        break;
      }
      case 'tool_result': {
        // 3b. 工具执行完成，更新状态
        updateLastToolCall(event.toolCallId, { status: 'done' });
        break;
      }
      case 'text': {
        // 4. 最终的文本回复
        appendToLastMessage(event.content); // 流式追加
        break;
      }
    }
  }
}
```

**UI 层的实现：**

```tsx
// ToolCallBubble — AI 调用工具的中间态 UI

  return (

    </div>

}
```

**第三步 — 深度理解/思考/踩坑：**

- **Tool Call 的三种失败及不同处理**：
  1. **工具不存在**（大模型幻觉，编造了一个不存在的 tool name）：BFF 层拦截，返回 `tool_not_found`，让大模型重新生成。如果重试 2 次仍然幻觉，直接告诉用户「我无法完成这个操作，请换一种方式描述」
  2. **参数错误**（如 `days: -7`，负数天数）：BFF 层校验参数合法性，返回 error + 原因，让大模型修正
  3. **工具执行失败**（如数据库连接超时）：前端展示「执行失败」+ 重试按钮。重试时只重发失败的 tool 调用，不重发整个对话

- **并行 Tool Call 的处理**：大模型可能一次返回多个 `tool_calls`（如同时查设备告警和查设备详情）。这些调用是独立的，可以并行执行。前端 UI 需要展示多个 ToolCallBubble 并行渲染，但注意顺序——先返回的先显示，不要按数组顺序排队等待。

- **Tool Call 的可观测性**：每个 tool call 的调用链路（入参→耗时→结果→是否影响最终回答）都需要上报。这是 AI 产品质量保障的基础——你可以通过数据分析哪些 Function 调用频率高但成功率低，哪些耗时过长影响了用户体验。

**面试官评价要点：**
- 及格：知道 Function Calling 的概念
- 良好：能描述多轮 tool call 的完整流程和 UI 中间态
- 优秀：能讨论三种失败模式的区别处理、并行调用、可观测性设计

### 【AI前端-3】多轮对话上下文隔离 — LangGraph 的工程化实践

**面试题：** 你在 IOT 平台中「构建了多轮对话上下文隔离机制」。这里的「上下文隔离」具体指什么？为什么需要隔离？你用 LangGraph 实现时，和直接用 `messages` 数组管理上下文有什么区别？

**P10 满分答案：**

**第一步 — 核心概念/原理：**

「上下文隔离」指的是：用户在同一个对话界面，可能先后问了三个不相关的问题——「帮我查 N5 设备的告警」「N5 的固件版本是什么」「你们平台支持哪些设备型号」。AI 不应该因为前面问了告警，就认为后面问的固件也和告警相关。也不能把三个完全不同的问题混在同一个上下文窗口里，导致 AI 输出的内容被历史消息「污染」。

本质上这是「对话中的注意力边界管理」——哪些历史消息应该保留，哪些应该摘除。

**第二步 — 工程实践/场景：**

直接管理 `messages` 数组（简单方案）的问题：
```typescript
// ❌ 简单方案：全量 message 数组
const messages = [
  { role: 'user', content: '查询 N5 告警' },
  { role: 'assistant', content: '最近一周 N5 告警 3 次...', toolCalls: [...] },
  { role: 'user', content: 'N5 固件版本？' },
  { role: 'assistant', content: 'N5 当前固件 v2.3.1...', toolCalls: [...] },
  { role: 'user', content: '支持哪些设备型号？' },
  // 问题：第三条问题和前两条完全无关，但全都带上了
  // → 浪费 token → 可能被历史回答误导 → 大模型的注意力被稀释
];
```

**LangGraph 的方案 — Checkpoint + 消息过滤**：

```python
# BFF 层 LangGraph 实现（简化版）
from langgraph.graph import StateGraph, MessagesState
from langgraph.checkpoint.memory import MemorySaver

class ChatState(MessagesState):
    current_topic: str         # 当前话题
    topic_window_size: int     # 当前话题保留最近 N 轮
    global_memory: list        # 跨话题的记忆（精简后的摘要）

builder = StateGraph(ChatState)

# 在每个新消息到达时，先做话题检测
def detect_topic(state: ChatState) -> str:
    last_msg = state["messages"][-1]
    # 1. 轻量判断：消息中是否包含新的设备名/操作意图
    # 2. 如果话题变了，截断旧上下文，生成一个摘要存入 global_memory
    new_topic = classify_topic(last_msg.content)
    if new_topic != state["current_topic"]:
        # 切换话题 → 隔离上下文
        summary = summarize_context(state["messages"][-state["topic_window_size"]:])
        state["global_memory"].append(summary)
        # 只保留最近 2 轮（当前问题的上下文）+ 全局记忆
        state["messages"] = state["messages"][-4:] + state["global_memory"]
        state["current_topic"] = new_topic
    return state

builder.add_node("topic_detect", detect_topic)
builder.add_node("chat", chat_node)  # 实际调用 LLM

builder.add_edge("topic_detect", "chat")
builder.set_entry_point("topic_detect")

# Checkpoint — 每次对话自动保存，支持回溯和恢复
memory = MemorySaver()
graph = builder.compile(checkpointer=memory)
```

**第三步 — 深度理解/思考/踩坑：**

- **话题切换的「信号」设计**：不只在用户发消息时判断，还设计了 UI 侧的话题切换入口——用户点击「新话题」按钮，前端在请求里带 `topic: 'new'`，BFF 强制清空上下文。这比纯算法判断更可靠，因为算法可能误判。
- **window 大小的权衡**：
  - 太小（如 2 轮）：用户追问两次就没上下文了，AI 表现差
  - 太大（如 10 轮）：上下文污染问题没解决，token 浪费
  - 实际做法：当前话题内保留 6 轮（经验值），跨话题时压缩成摘要（150 字以内）
- **摘要的丢失**：压缩成摘要会丢失细节，如果用户后续追问摘要中的某个细节，AI 答不上来。补救：摘要里附带一个 `context_id`，用户可以「展开此前某段对话的完整上下文」——这需要 Checkpoint 的持久化支持。
- **LangGraph 的价值**：不只是做了消息管理，更重要的是**流程的可视化和可调试性**。用 LangGraph 的 `StateGraph`，你可以把整个对话流程画成 DAG（有向无环图），在开发时可视化每个 node 的输入输出。这比直接写 `if-else` 的消息管理逻辑要清晰得多。但代价是引入了一个 Python 依赖——前端团队需要 Python 能力支撑。

**面试官评价要点：**
- 及格：知道上下文窗口有限制
- 良好：能说出话题切换和消息过滤的机制
- 优秀：能讨论 window 大小的权衡、摘要丢失的补救、LangGraph 的工程价值

### 【AI前端-4】Claude Code Skill/Workflow 的方法论沉淀

**面试题：** 你提到将「高频开发场景沉淀为标准化 Skill/Workflow」。请具体讲一个你沉淀的 Skill 的例子：这个 Skill 解决了什么问题、它的 prompt 是怎么设计的、你是怎么验证它的效果的？如果这个 Skill 给一个新人用，你怎么衡量它「好用还是不好用」？

**P10 满分答案：**

**第一步 — 核心概念/原理：**

AI Coding Agent（如 Claude Code）的能力边界很大，但「只在经过设计的场景中能稳定产出」。Skill/Workflow 的本质是**把一个人操作的隐性知识，外化成 Agent 可执行的标准流程**。关键要素：
- **上下文约束**：告诉 Agent 它在什么代码环境下工作（技术栈、目录结构、代码规范）
- **流程约束**：明确步骤（先做什么、再做什么、怎么检查）
- **输出约束**：指定输出的格式、文件路径、命名规范

**第二步 — 工程实践/场景：**

以「CRUD 页面生成 Skill」为例：

**背景**：IOT 平台有大量类似的 CRUD 页面（设备列表、消息列表、配置管理等），每次新建页面都要：建目录 → 列表页 → 详情页 → 编辑弹窗 → 搜索栏 → API 对接。熟练开发大概 2-3 小时一个页面。

**Skill 设计**：

```markdown
# Skill: 生成 Ant Design Pro CRUD 页面

## 输入
- 数据模型描述（字段名、类型、是否必填、是否可搜索）
- API 端点（列表接口、详情接口、编辑接口）

## 流程
1. 分析数据模型，确定列表列、搜索字段、编辑表单字段
2. 按照约定生成文件：
   - `src/pages/{module}/index.tsx` — 列表页（ProTable）
   - `src/pages/{module}/detail.tsx` — 详情页
   - `src/pages/{module}/components/EditModal.tsx` — 编辑弹窗（Formily Schema）
   - `src/services/{module}.ts` — API 调用（基于 request.ts 封装）
3. 对生成代码进行 ESLint + TS 检查
4. 输出：所有文件路径 + 待人工确认的 TODO 项（如复杂的校验逻辑）

## 约束
- 使用项目封装的 ProTable + Formily 组合
- API 调用统一用 `src/services/request.ts` 的 request 方法
- 枚举值从 `src/constants/` 导入
- 所有文本用中文
- 不生成测试文件，不在代码中写注释（除非逻辑复杂）

## 示例
[贴 2 个已有的 CRUD 页面作为 few-shot 示例]
```

**效果验证**：
- 原始开发时间：2-3 小时/页面
- Skill 生成 + 人工调整：30 分钟/页面（生成约 2 分钟 + 人工调整接口和特殊逻辑 28 分钟）
- 新人上手：原来需要熟悉 ProTable + Formily 的 API 和项目约定（约 1 周），Skill 生成后只需要审查代码并微调（约 1 天）

**第三步 — 深度理解/思考/踩坑：**

- **Skill 的「衰减」问题**：代码库在变，项目约定在变，但 Skill 的 prompt 不会自动更新。一个月前的 Skill 生成出的代码可能不符合现在的规范。解决方案：把 Skill 纳入 Code Review 流程——每次发现 Skill 生成的代码有问题，就更新 Skill 的 prompt。相当于「AI 的代码也要过 CR」。
- **衡量 Skill 好不好的指标**：
  1. **采纳率**：Agent 生成的代码，开发者直接接受的比例。如果每次都要大改（比如超过 30% 的行被手动修改），说明 Skill 不够好
  2. **首次正确率**：生成后 ESLint/TS 检查直接通过的比例。如果每次都要修类型错误或格式问题，说明 Skill 的约束不够精确
  3. **认知负荷降低**：开发者需要review的代码量 vs 自己写的代码量。如果生成 500 行但需要review 300 行，收益不大
- **Skill 不是一个技术问题，是一个知识管理问题**：最难的不是写 prompt，而是把团队里「最会写这个模块的人」的隐性知识提炼出来。当时做了一个「Skill 共创会」——让每个模块的 Owner 分享自己怎么写这个模块的，然后一起把 check list 写出来，转化成 prompt。这个过程本身就有价值——很多老员工在此之前也没正式梳理过自己的操作流程。
- **避免过度 Skill 化**：不是所有场景都值得做 Skill。如果某个任务只做 1-2 次，花 1 小时写 prompt 不如直接花 30 分钟写代码。当时的规则：**一个任务在 1 个月内出现 5 次以上，才值得沉淀为 Skill**。

**面试官评价要点：**
- 及格：知道 AI Coding Agent 能做什么
- 良好：能讲出一个具体的 Skill 设计，知道 Few-shot 示例的价值
- 优秀：能从知识管理角度思考 Skill 的维护和衰减问题，有量化评估意识

### 【补充-1】流式渲染中的 Thinking 组件设计

**面试题：** 现在主流的 AI 产品（ChatGPT、Claude）都有「思考过程可见」的 UI。如果你要给 IOT 平台的 AI Agent 加一个 `Thinking` 组件——展示 AI 的推理步骤（不是最终回答），从数据协议到 UI 渲染，你会怎么设计？

**性能注意**：thinking token 也可能很长（比如推理复杂问题时有几百个 token），如果不做虚拟列表优化，长时间对话的 thinking DOM 会很多。考虑「仅保留最新一条 thinking 的完整内容，历史 thinking 只保留摘要」。

### 【补充-2】AI 功能的可观测性与降级

**面试题：** 你接入 AI 后，作为前端你怎么监控 AI 功能的健康状态？如果大模型 API 突然挂了，你的前端怎么降级？用户感知是什么？

**P10 满分答案：**

**可观测性三件套**：
1. **延迟指标**：首 token 时间（TTFT）、平均 token 速率（tokens/s）、流结束时间
2. **质量指标**：用户点赞/点踩率、追问率（用户连续发了 3 条以上消息说明 AI 没答好）、对话中断率
3. **可用性指标**：SSE 连接成功率、Function Calling 成功率、降级触发次数

**降级方案的层次**：
1. **模型降级**：主模型挂 → 切备用模型（如 Claude → GPT-4o-mini 快速兜底）
2. **能力降级**：Function Calling 失败 → 纯文本回复（「抱歉，当前无法查询数据，请稍后重试」）
3. **完全降级**：整个 AI 服务不可用 → 显示预设的 FAQ 入口 + 工单系统入口（让用户有替代路径）

**用户感知设计**：降级不是「显示一个错误弹窗」，而是「优雅地提供替代方案」。比如 AI 查询功能挂了，页面显示：「智能助手暂时休息中，您可以先查看常见问题或提交工单，我们会尽快回复」。这比「500 Internal Server Error」好得多。

### 设计思路（给候选人看的说明）

1. **开场一句话定调**：姓名 + 年限 + 当前公司/岗位 + 核心方向，让面试官 3 秒内知道你是谁
