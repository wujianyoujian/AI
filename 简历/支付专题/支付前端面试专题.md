# 支付前端面试专题（Vue 视角）

> 目标岗位：海外业务 Web 收银台 + 支付中台运营后台前端
> 技术栈锁定：Vue 3 + TypeScript，不涉及 React

## 一、JD 解读

这份 JD 本质是「**支付中台前端**」岗，不是普通中后台岗。它有两个完全不同的面，要分开准备：

| 面 | 内容 | 技术特征 |
|---|---|---|
| **C 端收银台** | 海外 Web 收银台、多支付方式、3DS、轮询 | 高并发、弱网、状态机、安全合规 |
| **B 端中台** | 运营后台、渠道/路由/审核/账单、数据看板 | 复杂表单、动态表格、权限、可视化 |

面试官最看重 C 端这一面，因为「支付成功率」直接跟钱挂钩。会写 Vue 的人多，**懂支付链路的人少**——这是区分度所在。

### 岗位职责 → 能力点映射

1. **收银台开发 + 多支付方式灵活接入/动态展示** → 配置驱动渲染、支付方式抽象层、渠道 SDK 隔离
2. **支付漏斗分析、提升成功率** → 支付埋点、漏斗指标（下单→提交→3DS→成功）、弱网/首屏性能
3. **支付中台后台：渠道管理、路由策略、订单/退款审核、账单下载** → 中后台架构、动态表单/表格、权限、文件导出
4. **数据看板** → ECharts、大数据量渲染、可配置图表
5. **抽象通用 B 端组件（复杂表单、动态表格、可视化流程编排）** → Schema 驱动、组件抽象
6. **性能优化 + 全球兼容（网络、浏览器）** → 首屏、弱网、多币种、多语言、时区、老浏览器降级
7. **跨端支付状态同步、3DS 跳转、支付结果轮询** → 状态机、轮询/长轮询、跳转与 iframe、回调处理

### 任职要求 → 关键词

- 「支付链路、状态机流转、异步通知机制」——**必考题**，判断「是不是真做过支付」的分水岭
- 「3DS 2.0 前端对接」——加分项，能讲清楚就是亮点
- 「国际化与多币种」——海外业务刚需，金额精度 + 时区 + 语言三件事
- 「性能分析工具定位首屏/交互延迟」——Performance、Lighthouse、LCP/INP

## 三、支付业务核心

### 3.1 支付「心智模型」

```
用户选支付方式
   ↓
创建支付单（后端）→ 前端拿到 payOrderId / clientToken
   ↓
前端调起收银台（收集卡号 or 跳转三方）
   ↓
后端调用支付渠道（信用卡网关 / PayPal / 本地钱包）
   ↓
【可能】3DS 2.0 挑战（challenge）
   ↓
渠道返回结果 → 后端落库 → 前端轮询/回调得知最终状态
   ↓
异步通知（webhook）→ 后端幂等处理 → 前端刷新订单
```

**核心一句话**：前端永远不持有「支付是否成功」的最终真相，最终真相在后端；前端只做「发起 + 引导 + 展示结果 + 轮询兜底」。

### 3.2 3DS 是啥

**3DS = 3-D Secure**，信用卡线上支付的**一道额外身份验证**。「3-D」指验证发生在三个域之间：商户侧（收单行）、发卡行、卡组织（Visa/Mastercard）。

**一句话理解**：网购信用卡付款，填完卡号后银行要确认「真的是本人」——类似国内银联的短信验证码，3DS 就是这个国际化标准。

**为什么要它**：信用卡只有卡号+有效期+CVV 就能刷，盗刷风险高，3DS 强制加一道验证，把盗刷责任从商户转移到发卡行。

**1.0 vs 2.0 关键区别（面试必讲）**：

| | 3DS 1.0 | 3DS 2.0 |
|---|---|---|
| 验证方式 | 几乎每次都弹窗强制验证 | 风控驱动，大部分静默通过 |
| 体验 | 跳出收银台，流失率高 | 大多无感，高风险才验证 |
| 手段 | 固定密码/短信 | 短信 OTP、生物识别、App 确认等 |

**为什么 2.0 能无感**：浏览器带上风控数据（设备指纹、交易历史、地理位置），银行风控引擎判断低风险就直接放行（**frictionless**）；高风险才弹出验证（**challenge**）。

**真实体感**：国外网站信用卡付款「付完直接成功」= frictionless；偶尔跳页让输验证码/指纹 = challenge。前端要接住这两种情况。

### 3.3 支付状态机（对标「状态机流转」）

支付订单状态经典流转（简化）：

```
INIT(待支付) → PAYING(支付中) → SUCCESS(成功)
                        ├→ FAILED(失败)
                        └→ CLOSED(超时关闭)
SUCCESS → REFUNDING(退款中) → REFUNDED(已退款)
```

Vue 3 + TS 落地（纯 TS，可单测）：

```typescript
// pay-state-machine.ts
export enum PayStatus {
  INIT = 'INIT',
  PAYING = 'PAYING',
  SUCCESS = 'SUCCESS',
  FAILED = 'FAILED',
  CLOSED = 'CLOSED',
  REFUNDING = 'REFUNDING',
  REFUNDED = 'REFUNDED',
}

const TRANSITIONS: Record<PayStatus, PayStatus[]> = {
  [PayStatus.INIT]: [PayStatus.PAYING, PayStatus.CLOSED],
  [PayStatus.PAYING]: [PayStatus.SUCCESS, PayStatus.FAILED, PayStatus.CLOSED],
  [PayStatus.SUCCESS]: [PayStatus.REFUNDING],
  [PayStatus.REFUNDING]: [PayStatus.REFUNDED, PayStatus.SUCCESS],
  [PayStatus.FAILED]: [PayStatus.INIT],
  [PayStatus.CLOSED]: [],
  [PayStatus.REFUNDED]: [],
};

export function canTransition(from: PayStatus, to: PayStatus): boolean {
  return TRANSITIONS[from]?.includes(to) ?? false;
}

export class PayStateMachine {
  private status: PayStatus = PayStatus.INIT;
  private handlers = {
    onEnter: new Map<PayStatus, () => void>(),
    onExit: new Map<PayStatus, () => void>(),
  };

  get current() {
    return this.status;
  }

  onEnter(status: PayStatus, fn: () => void) {
    this.handlers.onEnter.set(status, fn);
    return this;
  }
  onExit(status: PayStatus, fn: () => void) {
    this.handlers.onExit.set(status, fn);
    return this;
  }

  transition(to: PayStatus): boolean {
    if (!canTransition(this.status, to)) {
      console.warn(`非法状态转移: ${this.status} -> ${to}`);
      return false;
    }
    this.handlers.onExit.get(this.status)?.();
    this.status = to;
    this.handlers.onEnter.get(to)?.();
    return true;
  }
}
```

Vue 组件里用：

```vue
<script setup lang="ts">
import { ref, onUnmounted } from 'vue';
import { PayStateMachine, PayStatus } from './pay-state-machine';

const sm = new PayStateMachine();
const status = ref<PayStatus>(PayStatus.INIT);

function sync() {
  status.value = sm.current;
}

sm.onEnter(PayStatus.PAYING, () => {
  startPolling();       // 进入支付中 → 开始轮询
  startCountdown();     // 开始超时倒计时
});
sm.onExit(PayStatus.PAYING, () => {
  stopPolling();        // 离开支付中 → 停轮询
  stopCountdown();
});

onUnmounted(() => { stopPolling(); stopCountdown(); });
</script>
```

**面试讲法**：状态机把散落的 `if (status === xxx)` 收敛成显式转移表 + 生命周期钩子，非法流转直接拒绝，配合埋点精确统计「每个状态停留时长 / 转移率」——正是支付漏斗分析的数据底座。

> 引库可用 **XState**，但面试最好说「先自己抽象纯 TS 版本，复杂到一定程度才引 XState」——体现懂原理而不是只会调 API。

### 3.4 异步通知机制（必考）

- **同步返回**：发起支付后渠道/后端**立即**返回结果（如余额不足直接失败）
- **异步通知（webhook / notify_url）**：渠道在支付真正完成后**主动**回调后端 URL（通常带签名）
- **主动查询（query）**：后端主动向渠道查单，用于对账和兜底

**前端为什么懂**：「支付成功但页面没刷新」的根因就是异步通知有延迟、甚至丢失。

```
用户支付成功 → 渠道异步通知后端 → 后端标记订单成功
                                    ↑ 有延迟，甚至通知丢失
```

所以前端**不能只依赖一次接口返回**，要轮询兜底（见 3.5）。

**要能说清**：异步通知的幂等性、签名校验、重试（失败渠道按间隔重发）。前端层面是「轮询 + 手动查询 + 页面可见性恢复时主动刷新」。

### 3.5 3DS 2.0 前端对接（加分项）

流程：

```
1. 后端创建 PaymentIntent / payment 会话
2. 前端收集卡信息（网关 SDK 的 iframe 组件，不落自己服务器）
3. 提交 → 网关返回三种结果之一：
   - frictionless：直接成功，前端无感
   - challenge：需要挑战 → 返回 3DS 认证 URL + 参数
   - 失败：直接展示失败
4. 若 challenge：跳转认证页面（redirect）或内嵌 iframe
5. 用户完成验证（OTP / 生物识别）
6. 认证结果回传 → 前端拿到结果继续走支付
```

前端处理三个技术点：

**(1) challenge 是「跳转」还是「iframe」——两种都要会**

```typescript
interface ThreeDSChallenge {
  type: 'redirect' | 'iframe';
  acsUrl: string;      // 认证服务商 ACS 的 URL
  creq: string;        // 发送给 ACS 的认证请求
  termUrl?: string;    // redirect 模式认证完成后的回调地址
}

function handleChallenge(challenge: ThreeDSChallenge) {
  if (challenge.type === 'redirect') {
    // 整页跳转（老方案、部分银行），认证完成 ACS 跳回 termUrl
    window.location.assign(buildRedirectUrl(challenge.acsUrl, challenge.creq));
  } else {
    // iframe 内嵌（2.0 主流），不离开收银台，体验更好
    openIframe(challenge.acsUrl, challenge.creq);
  }
}
```

**(2) iframe 模式下感知「认证完成」——靠 postMessage（跨域通信）**

```typescript
window.addEventListener('message', (e) => {
  // 校验来源，防止任意页面伪造消息
  if (!isTrustedAcsOrigin(e.origin)) return;
  if (e.data?.type === '3ds-challenge-complete') {
    closeIframe();
    continuePayment(e.data.transactionId);
  }
});
```

**(3) 超时 / 取消兜底**：用户关闭挑战、iframe 卡死、超时，都要有明确状态（认证失败/取消），不能卡在「支付中」。

**面试讲法**：3DS 2.0 把风险决策从银行侧下放到实时风控引擎，把 UX 从强制跳转变成 iframe 无感嵌入，前端要处理 redirect/iframe 两种形态 + postMessage 感知完成 + 超时兜底。

### 3.6 支付结果轮询（高频实现题）

```typescript
import { ref } from 'vue';

export function usePayPolling(queryStatus: () => Promise<PayStatus>) {
  const status = ref<PayStatus>('PAYING');
  let timer: number | null = null;
  let stopped = false;
  let attempts = 0;

  async function poll() {
    if (stopped) return;
    try {
      status.value = await queryStatus();
      if (status.value === 'SUCCESS' || status.value === 'FAILED') {
        return; // 终态，停止
      }
    } catch (e) {
      // 网络抖动：不中断，继续下一轮（但要记连续失败次数）
    }
    timer = window.setTimeout(poll, interval());
  }

  // 退避策略，避免给后端刷 QPS
  function interval(): number {
    const n = attempts++;
    if (n < 5) return 1000;   // 前 5 次：1s
    if (n < 15) return 2000;  // 5~15 次：2s
    return 5000;              // 之后：5s 封顶
  }

  function start() { attempts = 0; poll(); }
  function stop() { stopped = true; timer && clearTimeout(timer); }

  return { status, start, stop };
}
```

**关键细节（加分）**：
- **退避**：固定 1s 会刷 QPS，用阶梯/指数退避
- **终态才停**：SUCCESS/FAILED 是终态，PAYING 继续轮
- **页面可见性恢复主动查一次**：切后台再回来立即查一次，而不是等下一个定时器
- **后端主动推送优先**：有 WebSocket/SSE 就推，轮询只是兜底

### 3.7 收银台「多支付方式动态展示」

核心是**配置驱动 + 组件映射**：

```typescript
// 后端下发当前订单可用的支付方式（受地域、币种、风控影响）
interface PayMethod {
  code: 'card' | 'paypal' | 'alipay_plus' | 'gcash' | 'klarna' | 'pix';
  name: string;
  icon: string;
  enabled: boolean;
  supportedCurrencies: string[];
  priority: number;   // 排序权重，影响默认选中
}

// 支付方式 code → 渲染组件 的映射
const payMethodComponents = {
  card: () => import('./methods/CardPay.vue'),        // 内嵌卡表单/iframe
  paypal: () => import('./methods/PayPalRedirect.vue'),// 跳转型
  klarna: () => import('./methods/Klarna.vue'),       // 先买后付
} as const;
```

**为什么每个渠道独立组件**：不同渠道交互形态完全不同（卡是内嵌表单、PayPal 是跳转、本地钱包是二维码/跳 App），隔离后新增渠道只加一个组件、不改主流程——「灵活接入」的含义。

**排序 + 默认选中规则**：优先级、用户上次使用的渠道（本地化记忆）、币种是否支持。

### 3.8 国际化与多币种

**(1) 金额精度——永远用最小货币单位（分）存和算**

```typescript
const amountInCents = 123456; // 1234.56

// 用 Intl.NumberFormat 按币种格式化，不要手写 toFixed 拼字符串
function formatMoney(cents: number, currency: string, locale: string) {
  return new Intl.NumberFormat(locale, {
    style: 'currency',
    currency,
  }).format(cents / 100);
}

formatMoney(123456, 'USD', 'en-US'); // $1,234.56
formatMoney(123456, 'JPY', 'ja-JP');  // ￥1,235（JPY 无小数）
```

**要点**：`Intl` 自动处理不同币种小数位（JPY/KRW 是 0 位、BHD 是 3 位），别写死 `/100`。**金额只展示，不做浮点运算**。

**(2) 多语言**：vue-i18n，文案 + 日期 + 数字都本地化。

**(3) 时区**：订单时间用用户时区还是商户时区要明确；账单/对账通常用商户时区（或 UTC）避免歧义。

### 3.9 支付安全（安全意识必考）

- **卡信息不落自有服务器**（PCI DSS）：卡号/有效期/CVV 只进网关 SDK 的 iframe，前端只拿 token / paymentMethod id
- **防重复提交**：按钮防抖 + 幂等键（幂等由后端保证，前端传同一个 idempotency key）
- **金额防篡改**：前端展示金额仅供参考，以服务端下单金额为准，前端不传「实付金额」
- **回跳校验**：第三方支付跳回（return_url）后**不能只看 URL 参数就认为成功**，必须再调后端查真实状态
