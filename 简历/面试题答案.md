## 一、JavaScript / TypeScript 基础

### 基础题

**Q1. 请解释 Event Loop 的执行机制，宏任务与微任务的区别是什么？**

JS 是单线程语言，Event Loop 是其实现非阻塞异步的核心机制。

**执行顺序：**
1. 执行调用栈中的同步代码
2. 同步代码执行完毕，清空微任务队列（全部执行完）
3. 取出一个宏任务执行
4. 再次清空微任务队列
5. 重复 3-4，直到两个队列都为空

**宏任务（Macrotask）：** `setTimeout`、`setInterval`、`setImmediate`（Node）、I/O 回调、UI rendering、`MessageChannel`

**微任务（Microtask）：** `Promise.then/catch/finally`、`queueMicrotask`、`MutationObserver`、`async/await` 中 await 后的代码

**关键规则：** 每执行完一个宏任务，必须把微任务队列清空，才能执行下一个宏任务。

```js
console.log(1);
setTimeout(() => console.log(2), 0);
Promise.resolve().then(() => console.log(3));
console.log(4);
// 输出：1 → 4 → 3 → 2
// 原因：1/4 同步；3 是微任务优先于宏任务 2
```

**Node.js 补充：** Node 的 Event Loop 分 6 个阶段（timers → pending callbacks → idle → poll → check → close），`process.nextTick` 优先级高于 Promise 微任务。

**Q2. Promise、async/await 的错误处理有哪些方式？两者有什么本质区别？**

**Promise 错误处理方式：**
- `.catch(err => {})` — 链式捕获，推荐，能捕获链上任意位置的 reject
- `.then(null, onRejected)` — then 第二个参数，只捕获当前 then 之前的错误
- `Promise.allSettled()` — 不抛出，返回每个 Promise 的 `{status, value/reason}`
- `window.addEventListener('unhandledrejection', e => {})` — 全局兜底

**async/await 错误处理方式：**
- `try/catch` 包裹 await，最直观
- 封装 `to(promise)` 工具函数返回 `[err, data]` 元组，避免多层嵌套

```ts
const to = <T>(p: Promise<T>): Promise<[Error | null, T | null]> =>
  p.then(data => [null, data]).catch(err => [err, null]);

const [err, data] = await to(fetchUser());
if (err) return handleError(err);
```

**本质区别：**
- Promise 是对象，代表异步操作的最终结果，通过链式调用组合
- async/await 是语法糖，基于 Promise + Generator 协程，让异步代码具备同步的可读性
- async 函数始终返回 Promise；await 暂停当前函数执行，不阻塞主线程
- 错误传播：Promise 链中未捕获的 reject 沿链传递；async/await 中未捕获的异常变成 rejected Promise

**陷阱：** `await Promise.all([p1, p2])` 中任一 reject 会立即抛出，其他 Promise 仍在运行但结果被丢弃，应用 `allSettled` 或逐个 try/catch。

**Q3. TypeScript 中 `type` 和 `interface` 的区别？什么场景下用哪个？**

| 维度 | interface | type |
|------|-----------|------|
| 声明合并 | 支持（同名自动合并） | 不支持 |
| 扩展方式 | `extends` | `&` 交叉类型 |
| 联合类型 | 不支持 | 支持 `A \| B` |
| 映射类型 | 不支持 | 支持 |
| 元组/原始类型别名 | 不支持 | 支持 |
| 错误提示 | 更友好（显示接口名） | 有时展开显示 |

**选型原则：**
- **用 interface：** 定义对象结构、类的契约（`implements`）、需要声明合并的场景（如扩展第三方库类型 `declare module 'xxx'`）
- **用 type：** 联合类型、交叉类型、工具类型、映射类型、元组、函数类型别名

```ts
// interface 适合：对象结构 + 可扩展
interface User { id: number; name: string; }
interface AdminUser extends User { role: string; }

// type 适合：联合/工具类型
type Status = 'idle' | 'loading' | 'error';
type Nullable<T> = T | null;
type ReadonlyUser = Readonly<User>;
```

**实践建议：** 公共 API 和库类型用 interface（便于使用者扩展），内部实现和复杂类型运算用 type。

**Q4. 说说 JS 中的原型链，`__proto__` 和 `prototype` 的关系？**

**核心概念：**
- 每个函数都有 `prototype` 属性，指向一个对象（原型对象）
- 每个对象都有 `__proto__`（内部 `[[Prototype]]`），指向其构造函数的 `prototype`
- 原型链：对象查找属性时，沿 `__proto__` 链向上查找，直到 `null`

```js
function Person(name) { this.name = name; }
Person.prototype.greet = function() { return `Hi, ${this.name}`; };

const p = new Person('Alice');
p.__proto__ === Person.prototype;          // true
Person.prototype.__proto__ === Object.prototype; // true
Object.prototype.__proto__ === null;       // true（链的终点）
```

**`new` 操作符做了什么：**
1. 创建空对象 `obj = {}`
2. 设置 `obj.__proto__ = Constructor.prototype`
3. 以 `obj` 为 `this` 执行构造函数
4. 若构造函数返回对象则返回它，否则返回 `obj`

**继承实现：**
```js
// ES6 class 本质是语法糖
class Animal { speak() {} }
class Dog extends Animal { bark() {} }
// Dog.prototype.__proto__ === Animal.prototype
```

**`Object.create(proto)`：** 创建以 `proto` 为原型的对象，是实现原型继承的标准方式。

**Q5. `var`、`let`、`const` 的区别？什么是暂时性死区？**

| 维度 | var | let | const |
|------|-----|-----|-------|
| 作用域 | 函数作用域 | 块作用域 | 块作用域 |
| 变量提升 | 提升并初始化为 undefined | 提升但不初始化（TDZ） | 提升但不初始化（TDZ） |
| 重复声明 | 允许 | 不允许 | 不允许 |
| 全局对象属性 | 是（window.x） | 否 | 否 |
| 重新赋值 | 允许 | 允许 | 不允许（绑定不可变） |

**暂时性死区（Temporal Dead Zone, TDZ）：**
从块作用域开始到 `let/const` 声明语句之间的区域，变量已存在于作用域中但不可访问，访问会抛出 `ReferenceError`。

```js
console.log(x); // ReferenceError: Cannot access 'x' before initialization
let x = 1;

// 对比 var：
console.log(y); // undefined（提升并初始化为 undefined）
var y = 1;
```

**const 的注意点：** const 约束的是绑定（变量名与值的绑定），不是值本身。对象/数组的属性仍可修改，要深度不可变需用 `Object.freeze()`。

**Q6. 你在五福项目中深度使用了 Zustand + FSM，请问在 TypeScript 中如何对有限状态机的状态流转做严格类型约束，防止非法状态跳转？**

**完整实现方案：**

```ts
// 1. 定义合法状态联合类型
type GameState = 'idle' | 'detecting' | 'guiding' | 'gaming' 
               | 'colliding' | 'querying' | 'rewarding' | 'error';

// 2. 定义合法转换表（映射类型约束）
type TransitionMap = {
  [S in GameState]?: Partial<Record<GameState, () => void>>;
};

const TRANSITIONS: TransitionMap = {
  idle:      { detecting: startDetect },
  detecting: { guiding: showGuide, error: handleError },
  guiding:   { gaming: startGame, idle: cancelGame },
  gaming:    { colliding: onCollide, error: handleError },
  colliding: { querying: queryResult },
  querying:  { rewarding: showReward, error: handleError },
  rewarding: { idle: reset },
  error:     { idle: reset },
};

// 3. 严格 transition 函数，编译期约束
function transition<S extends GameState>(
  from: S,
  to: keyof NonNullable<TransitionMap[S]>
): void {
  const handler = TRANSITIONS[from]?.[to as GameState];
  if (!handler) throw new Error(`Invalid transition: ${from} → ${String(to)}`);
  handler();
}

// 4. 穷举检查（exhaustive check）
function assertNever(x: never): never {
  throw new Error(`Unexpected state: ${x}`);
}

function handleState(state: GameState) {
  switch (state) {
    case 'idle': return renderIdle();
    case 'detecting': return renderDetecting();
    // ... 所有状态都处理
    default: return assertNever(state); // 漏掉任何状态，编译报错
  }
}

// 5. Zustand 集成（immer 保证不可变）
import { create } from 'zustand';
import { immer } from 'zustand/middleware/immer';

interface GameStore {
  state: GameState;
  transition: (to: GameState) => void;
}

const useGameStore = create<GameStore>()(
  immer((set, get) => ({
    state: 'idle',
    transition: (to) => {
      const from = get().state;
      const valid = TRANSITIONS[from]?.[to];
      if (!valid) throw new Error(`Invalid: ${from} → ${to}`);
      set(draft => { draft.state = to; });
      valid();
    },
  }))
);
```

**核心价值：** 非法状态跳转在编译期就能发现，不需要运行时才报错，大幅降低状态管理 Bug。

**Q7. TypeScript 的协变（Covariance）与逆变（Contravariance）是什么？函数参数为什么是逆变的？**

**协变（Covariance）：** 子类型关系在类型构造器中保持方向。`Dog extends Animal`，则 `Dog[]` 可赋值给 `Animal[]`。返回值位置是协变的。

**逆变（Contravariance）：** 子类型关系在类型构造器中反转方向。函数参数位置是逆变的。

**为什么函数参数是逆变的（Liskov 替换原则）：**

```ts
type Handler<T> = (arg: T) => void;

// Dog extends Animal
// Handler<Animal> 可赋值给 Handler<Dog>（逆变）
// 因为：能处理 Animal 的函数，一定能处理 Dog（Dog 是 Animal 的子集）
// 反过来不行：只能处理 Dog 的函数，不能处理任意 Animal

const handleAnimal: Handler<Animal> = (a) => a.breathe();
const handleDog: Handler<Dog> = handleAnimal; // ? 安全
// const handleAnimal2: Handler<Animal> = handleDog; // ? 不安全，Dog 特有方法 Animal 没有
```

**`strictFunctionTypes` 的影响：**
- 开启后：函数类型参数位置严格逆变检查
- 关闭后：双变（bivariant），参数既协变又逆变，类型不安全但兼容性更好

**方法声明 vs 函数属性的差异：**
```ts
interface A {
  method(x: Dog): void;    // 方法声明：双变（历史原因）
  func: (x: Dog) => void;  // 函数属性：严格逆变（strictFunctionTypes 生效）
}
```

**Q8. 实现一个 `DeepReadonly<T>` 工具类型，递归地将所有属性设为只读。**

```ts
type DeepReadonly<T> = T extends (infer U)[]
  ? ReadonlyArray<DeepReadonly<U>>
  : T extends (...args: any[]) => any
  ? T  // 函数类型不递归
  : T extends object
  ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
  : T; // 原始类型直接返回

// 测试
type Config = {
  server: { host: string; port: number };
  tags: string[];
  handler: () => void;
};

type ReadonlyConfig = DeepReadonly<Config>;
// {
//   readonly server: { readonly host: string; readonly port: number };
//   readonly tags: ReadonlyArray<string>;
//   readonly handler: () => void;
// }
```

**处理边界情况：**
- 数组：转为 `ReadonlyArray<DeepReadonly<U>>`，元素也递归
- 函数：不递归，保持原类型（函数参数/返回值递归没有实际意义）
- 原始类型（string/number/boolean/null/undefined）：直接返回
- TS 4.1+ 递归类型有深度限制，超深嵌套可能报 `Type instantiation is excessively deep`，可用 `& {}` 打断递归或用 `interface` 绕过

**Q9. 说说 JS 内存泄漏的常见场景，在 React 应用中如何排查和解决？**

**常见场景：**

1. **闭包引用大对象：** 闭包持有外部变量引用，导致 GC 无法回收
2. **事件监听未移除：** `addEventListener` 后未 `removeEventListener`
3. **定时器未清理：** `setInterval` 持有回调引用，回调又引用组件状态
4. **全局变量：** 意外挂载到 `window` 的对象
5. **DOM 引用：** JS 持有已从 DOM 树移除的节点引用

**React 特有场景：**

```tsx
// ? 泄漏：组件卸载后 setState 仍被调用
useEffect(() => {
  fetchData().then(data => setData(data)); // 组件卸载后 setData 仍执行
}, []);

// ? 修复：AbortController 取消请求
useEffect(() => {
  const controller = new AbortController();
  fetchData({ signal: controller.signal })
    .then(data => setData(data))
    .catch(err => { if (err.name !== 'AbortError') throw err; });
  return () => controller.abort();
}, []);

// ? 泄漏：SSE/WebSocket 订阅未清理
useEffect(() => {
  const es = new EventSource('/stream');
  es.onmessage = (e) => setMessages(prev => [...prev, e.data]);
  return () => es.close(); // ? cleanup 必须关闭
}, []);
```

**排查方法：**
1. Chrome DevTools → Memory → Heap Snapshot，操作前后各拍一次，对比 `#Delta` 列
2. 筛选 `Detached DOM` 节点，找到仍被 JS 引用的已卸载 DOM
3. `Performance` 面板录制，观察 JS Heap 是否持续增长不回落
4. `WeakMap/WeakRef` 存储对象引用，不阻止 GC

**在 SSE 流式处理场景中：** 每个 SSE 连接都要在 cleanup 中 `close()`，流式 buffer 要在组件卸载时清空，避免 token 累积占用内存。

**Q10. Promise.all、Promise.race、Promise.allSettled、Promise.any 的区别？如何实现并发控制（最多同时 N 个请求）？**

| 方法 | 语义 | resolve 时机 | reject 时机 |
|------|------|-------------|------------|
| `Promise.all` | 全部成功 | 全部 resolve | 任一 reject |
| `Promise.race` | 最快完成 | 最快 resolve | 最快 reject |
| `Promise.allSettled` | 全部完成 | 全部完成（无论成败） | 永不 reject |
| `Promise.any` | 任一成功 | 任一 resolve | 全部 reject（AggregateError） |

**并发控制实现：**

```ts
async function limitConcurrency<T>(
  tasks: (() => Promise<T>)[],
  concurrency: number
): Promise<T[]> {
  const results: T[] = new Array(tasks.length);
  let index = 0;

  async function worker() {
    while (index < tasks.length) {
      const current = index++;
      results[current] = await tasks[current]();
    }
  }

  // 启动 concurrency 个 worker 并行消费任务队列
  await Promise.all(Array.from({ length: concurrency }, worker));
  return results;
}

// 使用
const tasks = urls.map(url => () => fetch(url).then(r => r.json()));
const results = await limitConcurrency(tasks, 3); // 最多同时 3 个请求
```

**结合接口预请求场景：** 在五福项目中，首屏需要并行预请求多个接口（游戏配置、用户状态、资源清单），但要避免同时发起过多请求打爆带宽，用并发控制将同时请求数限制在 4 个以内，配合 `Promise.allSettled` 保证即使部分接口失败也能继续渲染。

## 二、浏览器原理 & 性能优化

### 基础题

**Q1. 浏览器从输入 URL 到页面渲染完成，经历了哪些过程？**

1. **DNS 解析：** 域名 → IP，经过浏览器缓存 → 系统缓存 → 路由器缓存 → ISP DNS → 权威 DNS
2. **TCP 三次握手：** 建立连接（HTTPS 还需 TLS 握手，1-2 个 RTT）
3. **发送 HTTP 请求：** 请求行 + 请求头 + 请求体
4. **服务器处理并响应：** 返回 HTML 文档
5. **浏览器解析 HTML：** 构建 DOM 树（遇到 script 阻塞，遇到 CSS 阻塞渲染）
6. **解析 CSS：** 构建 CSSOM 树
7. **构建 Render Tree：** DOM + CSSOM 合并，排除 `display:none` 节点
8. **Layout（回流）：** 计算每个节点的几何信息（位置、尺寸）
9. **Paint（重绘）：** 将节点绘制到图层
10. **Composite（合成）：** 多图层合并，GPU 上屏

**关键优化点：**
- 减少 DNS 查询：`dns-prefetch`
- 减少 TCP 连接：HTTP/2 多路复用
- 减少阻塞：CSS 放 head，script 加 `defer/async`
- 减少回流：批量 DOM 操作，避免强制同步布局

---

**Q2. 什么是回流（Reflow）和重绘（Repaint）？如何减少它们？**

**回流（Reflow/Layout）：** 元素的几何属性（尺寸、位置）发生变化，浏览器需要重新计算布局。代价极高，会触发整个渲染树的重新计算。

**重绘（Repaint）：** 元素的外观属性（颜色、背景）变化，不影响布局，只需重新绘制。代价低于回流。

**触发回流的操作：**
- 修改 `width/height/margin/padding/border`
- 读取 `offsetWidth/offsetHeight/scrollTop/clientWidth` 等（强制同步布局）
- 添加/删除 DOM 节点
- 修改字体大小、窗口 resize

**减少回流的策略：**
```js
// ? 布局抖动：读写交替，每次读都强制回流
for (let i = 0; i < 100; i++) {
  el.style.width = el.offsetWidth + 1 + 'px'; // 读 → 写 → 读 → 写
}

// ? 批量读，批量写
const width = el.offsetWidth; // 一次读
for (let i = 0; i < 100; i++) {
  el.style.width = width + i + 'px'; // 只写
}

// ? 使用 transform 替代 top/left（不触发回流，只触发合成）
el.style.transform = 'translateX(100px)'; // GPU 合成层，不回流不重绘

// ? 批量 DOM 操作用 DocumentFragment 或 display:none 离线操作
// ? 使用 requestAnimationFrame 批量更新
```

**Q3. FCP、LCP、TTI、CLS 分别是什么？如何测量？**

| 指标 | 全称 | 含义 | 优秀阈值 |
|------|------|------|---------|
| FCP | First Contentful Paint | 首次内容绘制（文本/图片/SVG） | < 1.8s |
| LCP | Largest Contentful Paint | 最大内容绘制（主要内容可见） | < 2.5s |
| TTI | Time to Interactive | 页面可交互时间 | < 3.8s |
| CLS | Cumulative Layout Shift | 累计布局偏移（视觉稳定性） | < 0.1 |
| FID/INP | First Input Delay / Interaction to Next Paint | 首次输入延迟/交互响应 | < 100ms |

**测量方式：**
```js
// PerformanceObserver 采集
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.name === 'first-contentful-paint') {
      console.log('FCP:', entry.startTime);
    }
  }
}).observe({ type: 'paint', buffered: true });

// LCP
new PerformanceObserver((list) => {
  const entries = list.getEntries();
  const lcp = entries[entries.length - 1];
  console.log('LCP:', lcp.startTime);
}).observe({ type: 'largest-contentful-paint', buffered: true });
```

**Q4. 浏览器缓存机制：强缓存和协商缓存如何工作？相关 HTTP 头有哪些？**

**强缓存（不发请求，直接用缓存）：**
- `Cache-Control: max-age=31536000`（优先级高）
- `Expires: Wed, 21 Oct 2025 07:28:00 GMT`（HTTP/1.0，绝对时间，受客户端时钟影响）
- 命中时状态码：`200 (from disk cache)` 或 `200 (from memory cache)`

**协商缓存（发请求验证，服务端决定是否使用缓存）：**
- `Last-Modified` / `If-Modified-Since`：基于文件修改时间（精度 1s，可能误判）
- `ETag` / `If-None-Match`：基于内容 hash（精确，优先级高于 Last-Modified）
- 命中时状态码：`304 Not Modified`

**最佳实践：**
```
# HTML 文件：不缓存或短缓存（保证能拿到最新入口）
Cache-Control: no-cache

# JS/CSS（带 hash 文件名）：长期强缓存
Cache-Control: max-age=31536000, immutable

# 图片/字体：长期强缓存
Cache-Control: max-age=86400
```

**Q5. 什么是 CORS？预检请求（Preflight）什么时候触发？**

**CORS（Cross-Origin Resource Sharing）：** 浏览器的同源策略限制跨域请求，CORS 是服务端通过响应头告知浏览器允许哪些跨域访问的机制。

**简单请求（不触发预检）：** 满足以下全部条件：
- 方法：GET / POST / HEAD
- Content-Type：`text/plain` / `multipart/form-data` / `application/x-www-form-urlencoded`
- 无自定义请求头

**预检请求（OPTIONS）触发条件：** 不满足简单请求条件，如：
- 方法：PUT / DELETE / PATCH
- Content-Type：`application/json`
- 自定义 Header：`Authorization`、`X-Custom-Header`

**服务端响应头：**
```
Access-Control-Allow-Origin: https://example.com
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 86400  # 预检结果缓存时间
Access-Control-Allow-Credentials: true  # 允许携带 Cookie
```

### 高级题

**Q6. 五福项目将 FCP 从 4.5s 优化到 2.0s，请详细描述你的优化思路和每项措施的收益量化。**

**整体思路：** 分析瀑布图，找到关键路径上的阻塞点，逐项优化并 A/B 验证。

**优化措施与收益：**

1. **CCDN 预缓存（-0.8s）：**
   - 活动开始前 24h 预热 CDN 节点，命中率从 60% 提升到 95%+
   - 关键 JS/CSS/图片资源提前推送到边缘节点
   - 收益：网络传输时间从 1.2s → 0.4s

2. **接口预请求（-0.6s）：**
   - 在 HTML 解析阶段（`DOMContentLoaded` 前）并行发起游戏配置、用户状态接口
   - 原来等 JS 执行后才发请求，现在提前 600ms 并行
   - 使用 `<link rel="preconnect">` 提前建立连接

3. **资源分包懒加载（-0.5s）：**
   - 首屏只加载入场动画所需资源（~150KB gzip）
   - 游戏主界面、出奖动画、3D 粒子素材按阶段懒加载
   - 首屏 JS 体积从 800KB → 200KB

4. **降级决策前移（-0.6s，视觉稳定性）：**
   - 原来首帧渲染后才做设备评分，导致低端机出现动画降级的视觉跳变
   - 改为在 HTML inline script 中同步读取缓存评分，首帧直接渲染正确版本
   - 消除了低端机 20-30% 用户的视觉抖动

**验证方法：** 每项措施单独开 A/B 实验，实验组/对照组各 5% 流量，观察 P50/P90 FCP 数据，确认收益后全量。

**Q7. 你提到"降级决策在首帧渲染前完成"，请详细说明这个时机是如何卡的？**

**问题背景：** GPU Benchmark 是支付宝客户端提供的 JSBridge 异步接口，需要 Promise 包装，天然是异步的。如果等 JSBridge 回调才决定渲染哪个版本，首帧已经渲染完了，后续降级会造成视觉跳变。

**解决方案：三层缓存策略**

```js
// 方案一：App 壳层提前注入（最优）
// Native 在 WebView 创建时就把评分注入到全局变量
// HTML 中可同步读取
const gpuScore = window.__GPU_SCORE__ ?? 0;

// 方案二：inline script 读取 localStorage 缓存
// 首次进入时异步获取并缓存，后续同步读取
<script>
  (function() {
    const cached = localStorage.getItem('gpu_score');
    window.__GPU_SCORE__ = cached ? parseInt(cached) : null;
  })();
</script>

// 方案三：首次进入时的处理
async function initGpuScore() {
  if (window.__GPU_SCORE__ !== null) return; // 有缓存直接用
  
  // 首次：并行进行，不阻塞渲染，用默认中端配置
  const score = await JSBridge.getGPUBenchmark();
  localStorage.setItem('gpu_score', score);
  window.__GPU_SCORE__ = score;
  
  // 如果评分与默认配置不符，静默切换（用户感知不到，因为还在入场动画）
  if (needsDowngrade(score)) switchToLowEndMode();
}
```

**精确时机：** `DOMContentLoaded` 前的 inline script 执行阶段，此时 DOM 还未构建，React 还未挂载，是最早能执行 JS 的时机。

**缓存策略：** 评分 7 天有效期，活动期间不重新评估，避免每次进入页面都调用 JSBridge。

**Q8. 描述浏览器的合成层（Composite Layer）机制，什么情况下会触发层提升？如何利用它优化动画？**

**渲染流水线：** Layout → Paint → Composite（合成）

合成层由 GPU 独立处理，不影响主线程，动画只需 Composite 阶段，跳过 Layout 和 Paint，性能极高。

**触发层提升的条件：**
- `will-change: transform/opacity`（显式声明）
- `transform: translateZ(0)` 或 `translate3d(0,0,0)`（hack 方式）
- `opacity < 1` 且有动画
- `position: fixed`
- `<video>/<canvas>/<iframe>`
- CSS `filter`、`clip-path`（部分情况）

**优化动画的正确姿势：**
```css
/* ? 只用 transform 和 opacity 做动画，走合成层，不触发回流重绘 */
.card {
  will-change: transform; /* 提前告知浏览器，分配合成层 */
  transition: transform 0.3s ease;
}
.card:hover {
  transform: translateY(-4px); /* GPU 合成，60fps 流畅 */
}

/* ? 用 top/left 做动画，触发回流 */
.card:hover { top: -4px; }
```

**层爆炸（Layer Explosion）：** 过度使用 `will-change` 或 `transform3d` 会创建大量合成层，每层都需要 GPU 显存，反而导致内存暴涨、性能下降。

**五福 3D 粒子动画：** Mars 引擎的粒子系统本身运行在独立 Canvas 合成层，与 UI 层分离，互不影响。低端机通过减少粒子数量和降低 `devicePixelRatio` 来控制 GPU 负载。

**Q9. Service Worker 的工作原理是什么？如何实现离线缓存和资源预加载？**

**SW 生命周期：**
1. `install`：SW 首次安装，预缓存关键资源
2. `waiting`：新 SW 等待旧 SW 释放控制权
3. `activate`：清理旧缓存，接管页面
4. `fetch`：拦截所有网络请求

**缓存策略：**
```js
// Cache First（离线优先，适合静态资源）
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then(cached => 
      cached ?? fetch(event.request).then(response => {
        const clone = response.clone();
        caches.open('v1').then(cache => cache.put(event.request, clone));
        return response;
      })
    )
  );
});

// Network First（数据优先，适合 API）
// Stale While Revalidate（返回缓存同时后台更新）
```

**预缓存关键资源：**
```js
self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open('v1').then(cache => cache.addAll([
      '/', '/index.html', '/main.js', '/main.css', '/logo.png'
    ]))
  );
});
```

**与 CCDN 预缓存的对比：** CCDN 是 CDN 边缘节点的服务端缓存，SW 是客户端本地缓存。两者互补：CCDN 减少网络传输，SW 实现真正离线访问。

## 三、React 核心原理 & 状态管理

### 基础题

**Q1. React Fiber 架构解决了什么问题？与之前的 Stack Reconciler 有何不同？**

**Stack Reconciler 的问题：** 递归遍历 VDOM 树，一旦开始无法中断，大型组件树更新时会长时间占用主线程，导致页面卡顿（掉帧）。

**Fiber 架构的核心思想：** 将渲染工作拆分为可中断的小单元（Fiber 节点），利用浏览器空闲时间（`requestIdleCallback` 思想）分批执行，高优先级任务（用户交互）可以打断低优先级任务（数据更新）。

**Fiber 节点结构：**
```js
{
  type, stateNode,       // 组件类型和对应 DOM/实例
  return, child, sibling, // 树结构指针（链表）
  pendingProps, memoizedState, // props 和 hook 链表
  lanes, flags,          // 优先级和副作用标记
}
```

**两个阶段：**
- **Render 阶段（可中断）：** 构建 WorkInProgress Fiber 树，标记副作用
- **Commit 阶段（不可中断）：** 将副作用应用到真实 DOM

**核心区别：** Stack 同步递归不可中断；Fiber 异步可中断，支持优先级调度和并发特性。

---

**Q2. useEffect 和 useLayoutEffect 的区别？各自适用什么场景？**

| 维度 | useEffect | useLayoutEffect |
|------|-----------|-----------------|
| 执行时机 | 浏览器绘制后（异步） | DOM 更新后、浏览器绘制前（同步） |
| 是否阻塞绘制 | 否 | 是 |
| SSR | 支持 | 服务端会警告 |

**useLayoutEffect 典型场景：** 读取 DOM 尺寸后立即修改，避免用户看到中间状态（闪烁）。

```tsx
useLayoutEffect(() => {
  const { width } = ref.current.getBoundingClientRect();
  setWidth(width); // 在绘制前同步更新，用户看不到未调整的状态
}, []);
```

**useEffect 适用：** 数据请求、订阅事件、日志上报等大多数副作用。

---

**Q3. React 的 key 有什么作用？为什么不能用数组 index 作为 key？**

**key 的作用：** Diff 算法中识别列表元素身份，key 相同则复用，key 不同则销毁重建。

**index 的问题：** 删除列表头部元素后，后续元素的 index 全部变化，React 误认为所有元素都更新了，导致不必要的重渲染，且带输入框的列表会出现内容错位（key=0 的 DOM 被复用，显示了错误的输入内容）。

**正确做法：** 用稳定唯一的业务 ID（`user.id`、`item.uuid`）。只有静态纯展示列表才可以用 index。

---

**Q4. useMemo 和 useCallback 的区别？什么时候该用，什么时候过度优化？**

- `useMemo`：缓存计算结果（值）
- `useCallback`：缓存函数引用（本质是 `useMemo(() => fn, deps)`）

**该用的场景：**
- `useMemo`：计算耗时（> 1ms）且依赖变化频率低
- `useCallback`：函数传给 `React.memo` 包裹的子组件，或作为 `useEffect` 的依赖

**过度优化的信号：**
- 对简单计算（filter/map）用 useMemo，缓存开销 > 计算开销
- 子组件没有 `React.memo` 却用 useCallback（毫无意义）
- 没有 Profiler 数据支撑就盲目优化

**原则：** 先写正确代码，用 React DevTools Profiler 发现真实瓶颈后再优化。

**Q5. Redux 和 Zustand 的核心设计理念有什么不同？你在项目中是如何选型的？**

| 维度 | Redux | Zustand |
|------|-------|---------|
| 模板代码 | 多（action/reducer/selector） | 极少 |
| Provider | 需要 | 不需要 |
| 学习曲线 | 陡峭 | 平缓 |
| 适用规模 | 大型多人协作 | 中小型快速迭代 |

**选型决策：**
- **五福选 Zustand：** 活动页生命周期短，团队小，状态结构清晰（FSM），轻量无 Provider 完美契合
- **IOT 平台选 Redux Toolkit：** 多团队协作，状态复杂，需要严格数据流追踪和 DevTools 调试

### 高级题

**Q6. 你基于 Zustand 设计了 NFC 游戏的有限状态机，请画出状态流转图，并说明为什么选择 Zustand 而不是 XState 或 Redux？**

**状态流转：**
```
idle → detecting → guiding → gaming → colliding → querying → rewarding → idle
  ↓         ↓          ↓        ↓          ↓           ↓
error     error      error    error       error       error → idle
```

**Zustand 实现核心：**
```ts
const useGameStore = create<GameStore>()(immer((set, get) => ({
  state: 'idle' as GameState,
  transition: (to: GameState) => {
    const from = get().state;
    if (!VALID_TRANSITIONS[from]?.includes(to)) {
      throw new Error(`Invalid: ${from} → ${to}`);
    }
    set(d => { d.state = to; });
  },
})));
```

**为什么不用 XState：** 优势是可视化和严格语义，但包体积 ~20KB，学习成本高，五福状态数量少（8个），Zustand 手写 guard 完全够用，引入 XState 是过度工程。

**为什么不用 Redux：** 模板代码过多，活动页快速迭代中 Redux 的严格性是负担，Zustand + immer 同样保证不可变。

**Q7. React 的并发特性包括哪些？Suspense、useTransition、useDeferredValue 分别解决什么问题？**

**并发渲染核心：** 渲染可中断，高优先级更新（用户输入）可打断低优先级更新（数据加载）。

**Suspense：** 声明式异步等待，组件挂起时显示 fallback，与 `lazy`/数据获取结合。

**useTransition：** 将状态更新标记为低优先级，保持 UI 可交互：
```tsx
const [isPending, startTransition] = useTransition();
startTransition(() => setSearchQuery(value)); // 搜索结果更新不阻塞输入
```

**useDeferredValue：** 对高频值降频，类似防抖但基于优先级而非时间：
```tsx
const deferredQuery = useDeferredValue(query);
// query 频繁变化时，deferredQuery 滞后，避免每次击键都触发昂贵渲染
```

**画布场景应用：** 节点拖拽用 `useTransition` 包裹位置更新保证手势流畅；属性面板实时预览用 `useDeferredValue` 降频避免每次输入都触发画布重渲染。

**Q8. 在 AntV X6 画布中，你如何解决"大规模节点 React 组件嵌入 Canvas 渲染性能问题"？**

**根因：** X6 的 React Shape 为每个节点创建独立 React 树，1000 节点 = 1000 个 React 根，挂载/卸载开销巨大，帧率跌至 10fps。

**解决方案：**

1. **视口裁剪：** 监听 `translate/scale` 事件，只渲染视口内节点（类虚拟列表）
2. **节点复用：** 离屏节点不 unmount，用 CSS `visibility: hidden` 隐藏，保留 React 实例
3. **批量更新：** 多次节点更新合并到一个 `requestAnimationFrame` 中执行
4. **React DevTools Profiler + X6 内置 Profiler** 定位热点

**结果：** 10000 节点下帧率从 10fps 提升到 50fps+，内存占用降低 40%。

**Q9. 描述 React Context 的性能问题及解决方案，什么场景下应该避免使用 Context？**

**性能问题：** Context value 引用变化时，所有消费者重渲染，即使只用了 value 中的一个字段。

**解决方案：**
```tsx
// ? useMemo 稳定 value 引用
const value = useMemo(() => ({ user, setUser }), [user]);

// ? 拆分 Context，读写分离
<UserStateContext.Provider value={user}>
  <UserDispatchContext.Provider value={setUser}>
```

**应该避免 Context 的场景：** 高频更新状态（动画值、实时数据）、大型应用全局状态（用 Zustand/Jotai）、需要精确订阅某字段的场景。

**Context 适合：** 低频更新的配置（Theme、i18n、Auth）、组件树内依赖注入。

**Q10. React 的合成事件系统是什么？为什么要用事件委托？React 17 后有什么变化？**

**合成事件：** React 对原生事件的跨浏览器封装，统一 API，抹平差异。

**事件委托原因：** 不为每个 DOM 节点绑定事件，统一在根节点处理，减少监听器数量，动态节点自动享有事件处理。

**React 16 vs 17：**
- React 16：委托在 `document` 层
- React 17：委托移到 `root container`（解决微前端多 React 实例的 `stopPropagation` 冲突）

**陷阱：** 合成事件的 `stopPropagation` 只阻止合成事件冒泡，不阻止原生事件。混用时需注意执行顺序：原生事件（捕获）→ 合成事件 → 原生事件（冒泡）。

## 四、工程化：Webpack / Vite / 构建优化

### 基础题

**Q1. Webpack 的核心概念：Entry、Output、Loader、Plugin、Chunk 各是什么？**

- **Entry：** 构建入口，Webpack 从这里开始分析依赖图
- **Output：** 产物输出配置（路径、文件名、publicPath）
- **Loader：** 文件转换器，将非 JS 文件（CSS/图片/TS）转换为 JS 模块（`module.rules`）
- **Plugin：** 扩展 Webpack 能力，在构建生命周期钩子中执行（压缩、注入 HTML、环境变量）
- **Chunk：** 代码块，Webpack 将模块打包成 Chunk，一个 Entry 对应一个初始 Chunk，动态 import 产生额外 Chunk

**Loader vs Plugin 的本质区别：** Loader 是文件级别的转换（输入文件，输出 JS）；Plugin 是构建流程级别的扩展（监听 Webpack 生命周期事件，操作 compilation 对象）。

---

**Q2. Vite 为什么在开发环境下比 Webpack 快？它的 HMR 是如何实现的？**

**Vite 快的原因：**

1. **No Bundle 开发服务器：** 利用浏览器原生 ES Module，不打包，直接按需提供文件
2. **esbuild 预构建：** 用 Go 编写的 esbuild 将 CommonJS/UMD 依赖转为 ESM，比 Babel/Webpack 快 10-100 倍
3. **按需编译：** 只编译当前请求的文件，不像 Webpack 启动时全量编译

**HMR 实现：**
- Vite 通过 WebSocket 与浏览器保持连接
- 文件变化时，Vite 只重新编译变化的模块
- 通过 `import.meta.hot` API 通知浏览器更新
- 模块边界（HMR boundary）：React 组件通过 `react-refresh` 实现热更新，保留组件状态

**生产环境：** Vite 使用 Rollup 打包，Tree Shaking 更彻底，但不支持 Webpack 的部分高级特性（如 Module Federation）。

---

**Q3. 什么是 Tree Shaking？它依赖什么条件才能生效？**

**Tree Shaking：** 静态分析代码，移除未被引用的导出（dead code elimination）。

**生效条件：**
1. **ES Module 语法：** `import/export` 是静态的，编译时可分析；CommonJS 的 `require` 是动态的，无法静态分析
2. **无副作用：** `package.json` 中 `"sideEffects": false` 告知打包工具该包无副作用，可安全移除未用代码
3. **生产模式：** Webpack 的 Tree Shaking 在 `mode: 'production'` 下自动开启

**常见失效场景：**
- 引入了有副作用的模块（如 CSS-in-JS、polyfill）
- 使用了 `export default` 导出对象（整个对象被引入）
- Babel 将 ESM 转为 CommonJS（需配置 `@babel/preset-env` 的 `modules: false`）

**Q4. Code Splitting 有哪几种方式？Dynamic Import 和 SplitChunksPlugin 各解决什么问题？**

**三种方式：**
1. **Entry Points：** 多入口，每个入口独立打包（适合 MPA）
2. **Dynamic Import：** `import('./module')` 运行时按需加载，产生异步 Chunk
3. **SplitChunksPlugin：** 自动提取公共模块，避免重复打包

**Dynamic Import 解决：** 路由级/功能级懒加载，减少首屏 JS 体积
```js

```

**SplitChunksPlugin 解决：** 多个 Chunk 共用的模块（如 React、lodash）被重复打包的问题，自动提取为公共 Chunk
```js
optimization: {
  splitChunks: {
    chunks: 'all',
    cacheGroups: {
      vendor: { test: /node_modules/, name: 'vendors' },
    }
  }
}
```

**Q8. 什么是 Module Federation？它如何解决微前端场景下的依赖共享问题？与 qiankun 方案有何本质区别？**

**Module Federation（MF）：** Webpack 5 的特性，允许多个独立构建的应用在运行时共享模块，实现真正的代码级共享。

```js
// 主应用（Host）
new ModuleFederationPlugin({
  remotes: { 'app-device': 'appDevice@http://device.example.com/remoteEntry.js' },
  shared: { react: { singleton: true, requiredVersion: '^18.0.0' } },
})

// 子应用（Remote）
new ModuleFederationPlugin({
  name: 'appDevice',
  filename: 'remoteEntry.js',
  exposes: { './DeviceList': './src/DeviceList' },
  shared: { react: { singleton: true } },
})
```

**依赖共享机制：** `shared` 配置声明共享依赖，运行时协商版本，满足条件则复用已加载的实例，避免 React 等大库被多次加载。

**与 qiankun 的本质区别：**

| 维度 | Module Federation | qiankun |
|------|------------------|---------|
| 隔离粒度 | 模块级 | 应用级 |
| 沙箱 | 无（共享作用域） | JS 沙箱（Proxy） |
| 依赖共享 | 构建时声明，运行时协商 | externals 或重复加载 |
| 与构建工具 | 强绑定（Webpack 5） | 无关 |
| 适用场景 | 细粒度模块共享 | 完整应用隔离 |

**两者结合：** qiankun 做应用级隔离和生命周期管理，MF 做公共依赖共享，各取所长。

## 五、微前端：qiankun 原理与实践

### 基础题

**Q1. 微前端解决了什么问题？主要的实现方案有哪些？**

**解决的问题：** 大型前端应用的团队协作问题——多团队并行开发、独立部署、技术栈无关、渐进式迁移遗留系统。

| 方案 | 隔离性 | 通信 | 性能 | 适用场景 |
|------|--------|------|------|---------|
| iframe | 最强 | 复杂（postMessage） | 差（独立进程） | 强隔离需求 |
| qiankun | 强（JS沙箱+CSS隔离） | 简单 | 中 | 主流选择 |
| Module Federation | 弱（共享作用域） | 直接调用 | 好 | 细粒度共享 |
| Web Components | 中（Shadow DOM） | 自定义事件 | 中 | 组件级复用 |

**Q2. qiankun 是如何加载子应用的？子应用需要做哪些改造？**

**加载流程：**
1. 主应用调用 `registerMicroApps` 注册子应用配置
2. 路由匹配时，`import-html-entry` 加载子应用 HTML
3. 解析 HTML，提取 JS/CSS，在沙箱中执行 JS
4. 调用子应用的 `bootstrap → mount` 生命周期

**子应用改造：**
```js
// 导出生命周期函数
export async function bootstrap() {}
export async function mount(props) {
  ReactDOM.render(<App />, props.container.querySelector('#root'));
}
export async function unmount(props) {
  ReactDOM.unmountComponentAtNode(props.container.querySelector('#root'));
}

// webpack 配置：输出 UMD 格式
output: {
  library: 'appName',
  libraryTarget: 'umd',
  publicPath: '//cdn.example.com/app/',
}
```

**Q3. qiankun 的 JS 沙箱有哪几种实现方式？**

1. **SnapshotSandbox（快照沙箱）：** 激活时记录 window 快照，卸载时恢复。不支持多实例并行，适合不支持 Proxy 的环境。

2. **LegacySandbox（单例代理沙箱）：** 用 Proxy 拦截 window 读写，记录新增/修改的属性，卸载时还原。只支持单实例。

3. **ProxySandbox（多实例代理沙箱）：** 每个子应用有独立的 `fakeWindow`，Proxy 拦截读写操作到 fakeWindow，多个子应用可同时运行互不干扰。**这是 qiankun 默认使用的沙箱。**

---

**Q4. qiankun 的 CSS 隔离是如何实现的？有什么局限性？**

**两种方式：**

1. **strictStyleIsolation（Shadow DOM）：** 将子应用挂载到 Shadow DOM 中，CSS 完全隔离。局限：部分第三方组件（Modal/Tooltip 挂载到 body）样式失效，`document.querySelector` 无法穿透 Shadow DOM。

2. **experimentalStyleIsolation（Scoped CSS）：** 给子应用所有 CSS 选择器加前缀（类似 Vue Scoped），如 `.button` → `div[data-qiankun-app-name] .button`。局限：动态插入的样式（CSS-in-JS）无法处理，性能有一定开销。

**实践建议：** 优先用 CSS Module 或 BEM 命名规范从源头避免冲突，而非依赖 qiankun 的 CSS 隔离。

---

**Q5. 主子应用之间如何通信？qiankun 提供了哪些通信方式？**

1. **props 传递：** 主应用在 `mount` 时通过 props 传递数据和回调，适合初始化配置
2. **initGlobalState：** qiankun 提供的全局状态管理，发布订阅模式
```js
// 主应用
const actions = initGlobalState({ user: null });
actions.onGlobalStateChange((state) => console.log(state));

// 子应用（通过 props 接收 actions）
props.onGlobalStateChange((state) => setUser(state.user));
props.setGlobalState({ user: { id: 1 } });
```
3. **自定义事件（CustomEvent）：** 通过 `window.dispatchEvent` 跨应用通信，适合松耦合场景
4. **共享 Store：** 主应用暴露 Redux/Zustand store 实例，子应用直接订阅

**Q7. qiankun 的 Proxy 沙箱（ProxySandbox）是如何工作的？它能解决哪些问题，又有哪些场景无法覆盖？**

**工作原理：**
```js
class ProxySandbox {
  fakeWindow = Object.create(null);
  proxy = new Proxy(this.fakeWindow, {
    get(target, key) {
      // 优先从 fakeWindow 读，没有则从真实 window 读
      return key in target ? target[key] : window[key];
    },
    set(target, key, value) {
      target[key] = value; // 写入 fakeWindow，不污染真实 window
      return true;
    }
  });
}
```

**能解决的问题：**
- 多个子应用同时运行，各自的全局变量互不干扰
- 子应用卸载时，fakeWindow 随之销毁，不污染主应用

**无法覆盖的场景：**
- 直接操作 `document`（如 `document.title = 'xxx'`）
- 全局 CSS 变量（`:root { --color: red }`）
- 第三方 SDK 直接挂载 DOM（如百度地图、微信 SDK）
- `setTimeout/setInterval` 的内存清理（需要子应用在 unmount 时手动清理）
- `window.addEventListener` 的事件监听（需手动 removeEventListener）

**Q8. 微前端场景下，子应用的性能优化有哪些策略？如何避免子应用加载带来的白屏？**

**公共依赖抽取：**

```js
// 子应用 webpack 配置 externals，不重复打包 React/AntD
```

**白屏优化：**

**Q10. 如果让你从零设计一个微前端框架，你会如何考虑沙箱、通信、路由、性能这四个核心维度？**

**沙箱设计（分层）：**
- JS 沙箱：Proxy 拦截 window 读写（支持多实例），降级到快照沙箱（不支持 Proxy 的环境）
- CSS 沙箱：Shadow DOM（强隔离）或 Scoped CSS（兼容性好），可配置
- 副作用清理：自动追踪 setTimeout/addEventListener，卸载时自动清理

**通信设计（松耦合）：**
- 发布订阅总线：`EventEmitter` 实现，主子应用通过事件名通信
- 共享 Store：可选，适合需要响应式状态同步的场景
- 避免直接调用：子应用不应直接引用主应用的模块

**路由设计：**
- 主应用路由控制子应用生命周期（路由匹配 → mount，路由离开 → unmount）
- 支持 history 和 hash 两种模式
- 子应用路由前缀隔离，避免冲突

**性能设计：**
- 按需加载：路由匹配时才加载子应用资源
- 预加载：空闲时预加载下一个可能访问的子应用
- 公共依赖提升：通过 externals 或 MF 避免重复加载
- 生命周期标准：`bootstrap/mount/unmount/update`，bootstrap 只执行一次（缓存初始化结果）

## 六、跨端开发：H5 / WebView / JSBridge / 小程序

### 基础题

**Q1. JSBridge 的通信原理是什么？Native 调用 JS、JS 调用 Native 分别怎么实现？**

**JS 调用 Native（两种方式）：**
1. **URL Scheme 拦截：** JS 修改 `location.href` 或创建 iframe，Native 拦截特定 scheme（如 `jsbridge://method?params=xxx`）
2. **注入 API：** Native 在 WebView 初始化时注入全局对象（iOS `WKScriptMessageHandler`，Android `addJavascriptInterface`），JS 直接调用

**Native 调用 JS：**
- iOS：`WKWebView.evaluateJavaScript("window.callback(data)")`
- Android：`webView.evaluateJavascript("window.callback(data)", null)`

**完整双向通信流程：**
```js
// JS 侧
const bridge = {
  callbackMap: new Map(),
  call(method, params) {
    return new Promise((resolve, reject) => {
      const callbackId = `cb_${Date.now()}_${Math.random()}`;
      this.callbackMap.set(callbackId, { resolve, reject });
      // 通过注入 API 调用 Native
      window.NativeBridge.call(JSON.stringify({ callbackId, method, params }));
    });
  },
  // Native 回调时调用此方法
  onCallback(callbackId, result, error) {
    const { resolve, reject } = this.callbackMap.get(callbackId);
    this.callbackMap.delete(callbackId);
    error ? reject(error) : resolve(result);
  }
};
```

**Q2. WebView 白屏的常见原因有哪些？如何检测和兜底？**

**常见原因：**
- JS 运行时错误导致渲染中断（未捕获异常）
- 网络请求失败（接口超时、CDN 故障）
- WebView 内存不足（OOM）
- 页面加载超时（弱网环境）
- JSBridge 初始化失败（Native 未就绪就调用）

**检测方案：**
```js
// 心跳检测：定时检查 DOM 节点数
function detectWhiteScreen() {
  const timer = setInterval(() => {
    const nodeCount = document.querySelectorAll('body *').length;
    if (nodeCount < 5) { // 阈值根据页面结构调整
      reportWhiteScreen();
      showFallback();
    }
  }, 3000);
  
  // 页面正常渲染后停止检测
  window.addEventListener('app-ready', () => clearInterval(timer));
}
```

**兜底方案：**
- 显示"加载失败，点击重试"的降级 UI
- Native 截图对比（客户端定时截图，检测是否全白）
- 超时自动刷新（30s 无响应则 reload）
- 降级到 Native 原生页面

**Q4. 支付宝小程序的 JSAPI 和 H5 的 Web API 有什么核心区别？**

- **运行环境：** H5 运行在 WebView，可访问完整 Web API；小程序逻辑层运行在独立 JS 引擎（无 DOM/BOM），渲染层是 WebView

- **权限模型：** 小程序权限在 IDE 配置文件中声明，H5 通过 JSBridge 动态申请
- **网络请求：** 小程序用 `my.request`（不受同源策略限制），H5 用 `fetch/XHR`（受 CORS 限制）
- **存储：** 小程序用 `my.setStorage`（独立存储空间），H5 用 `localStorage`（与域名绑定）

**Q5. 什么是 WebView 的离线包方案？它如何提升加载速度？**

**离线包方案：** 将 H5 的静态资源（HTML/JS/CSS/图片）预置到 App 安装包或通过增量更新下载到本地，WebView 加载时拦截网络请求，直接从本地文件系统读取资源，绕过网络传输。

**实现流程：**
1. 构建时生成资源清单（manifest.json，包含文件 hash）
2. App 启动时检查更新，增量下载变化的文件
3. WebView 拦截请求（iOS `WKURLSchemeHandler`，Android `shouldInterceptRequest`）
4. 命中本地缓存则直接返回，否则走网络

**性能收益：** 网络请求时间从 500ms-2s → 0ms（本地读取），首屏加载从 3s → 1.3s（招银云创项目实测）。

### 高级题

**Q6. 你在招银云创设计了一套 JSBridge 通信规范，请描述你的协议设计。**

**消息格式标准化：**
```ts
interface BridgeMessage {
  callbackId: string;   // 唯一标识，用于匹配回调
  method: string;       // 调用的 Native 方法名
  params: unknown;      // 参数
  version: string;      // 协议版本，用于兼容性处理
}

interface BridgeResponse {
  callbackId: string;
  code: number;         // 0=成功，非0=错误
  data: unknown;
  message: string;      // 错误描述
}
```

**回调管理（防内存泄漏）：**
```ts
class BridgeManager {
  private callbacks = new Map<string, {
    resolve: Function;
    reject: Function;
    timer: ReturnType<typeof setTimeout>;
  }>();

  call<T>(method: string, params: unknown, timeout = 5000): Promise<T> {
    return new Promise((resolve, reject) => {
      const callbackId = `${method}_${Date.now()}`;
      const timer = setTimeout(() => {
        this.callbacks.delete(callbackId);
        reject(new BridgeError('TIMEOUT', `${method} timeout after ${timeout}ms`));
      }, timeout);
      
      this.callbacks.set(callbackId, { resolve, reject, timer });
      window.NativeBridge.call(JSON.stringify({ callbackId, method, params, version: '1.0' }));
    });
  }

  onResponse(response: BridgeResponse) {
    const cb = this.callbacks.get(response.callbackId);
    if (!cb) return;
    clearTimeout(cb.timer);
    this.callbacks.delete(response.callbackId);
    response.code === 0 ? cb.resolve(response.data) : cb.reject(new BridgeError(response.code, response.message));
  }
}
```

**错误码体系：**
- `1xxx`：Native 系统错误（权限拒绝、功能不支持）
- `2xxx`：业务错误（用户取消、数据格式错误）
- `3xxx`：网络错误（超时、连接失败）
- `9999`：未知错误

**能力检测（canIUse）：**
```ts
const canUseNFC = await bridge.call('canIUse', { api: 'nfc' });
if (!canUseNFC) showManualInputFallback();
```

**Q7. 你将首屏加载从 3s 优化到 1.3s，Crash 率降低 20%，请分别说明这两个指标的优化思路。**

**首屏加载优化（3s → 1.3s）：**

1. **离线包预置（-0.8s）：** 核心 JS/CSS 预置到 App，WebView 拦截请求走本地，消除网络传输时间
2. **DNS 预解析（-0.2s）：** `<link rel="dns-prefetch">` 提前解析接口域名
3. **关键资源内联（-0.3s）：** 首屏关键 CSS 内联到 HTML，消除 CSS 阻塞渲染
4. **接口并行（-0.4s）：** 页面初始化时并行发起所有必要接口，而非串行

**Crash 率降低 20%：**

1. **WebView OOM 优化：**
   - 图片懒加载 + 压缩（WebP 格式，减少 60% 内存）
   - 大列表虚拟化（只渲染视口内 DOM）
   - 及时销毁不可见组件（路由切换时 unmount）

2. **JS 运行时异常：**
   - React ErrorBoundary 捕获渲染异常，显示降级 UI 而非白屏
   - 全局 `window.onerror` + `unhandledrejection` 兜底

3. **白屏检测 + 降级：**
   - 心跳检测 DOM 节点数，异常时自动 reload
   - 关键接口失败时显示静态降级页面

4. **灰度验证：** 先 1% 流量发版，监控 Crash 率稳定后再全量，避免大规模影响。

**Q8. 五福项目覆盖 iOS / Android / 鸿蒙三端，NFC 权限 API 在三端的行为不一致，你是如何抹平差异的？**

**三端差异：**
- **iOS（CoreNFC）：** 不能静默检测 NFC 状态，必须用户主动点击触发，且只有 iPhone 7+ 支持
- **Android：** `NfcAdapter.isEnabled()` 可直接检测，支持后台感应
- **鸿蒙（HarmonyOS）：** 独立的 JSAPI 权限模型，`@ohos.nfc.controller`，权限申请流程不同

**抽象层设计：**
```ts
// 统一接口，屏蔽三端差异
interface NFCAdapter {
  checkAvailable(): Promise<{ available: boolean; reason?: string }>;
  startScan(options: ScanOptions): Promise<NFCTag>;
  stopScan(): void;
}

// 各端实现
class IOSNFCAdapter implements NFCAdapter {
  async checkAvailable() {
    // iOS 无法静默检测，返回"需要用户触发"
    return { available: true, reason: 'user-trigger-required' };
  }
  async startScan() {
    return bridge.call('startNFCScan'); // 触发 CoreNFC 系统弹窗
  }
}

class AndroidNFCAdapter implements NFCAdapter {
  async checkAvailable() {
    const enabled = await bridge.call('isNFCEnabled');
    return { available: enabled, reason: enabled ? undefined : 'nfc-disabled' };
  }
}

// 工厂函数：能力检测优先于 UA 判断
function createNFCAdapter(): NFCAdapter {
  if (await bridge.call('canIUse', { api: 'harmonyNFC' })) return new HarmonyNFCAdapter();
  if (await bridge.call('canIUse', { api: 'androidNFC' })) return new AndroidNFCAdapter();
  return new IOSNFCAdapter();
}
```

**降级策略：** NFC 不可用时（设备不支持、权限拒绝、NFC 未开启），引导用户手动输入对方的碰一碰码，保证核心流程可用。

## 七、低代码 & Formily

### 基础题

**Q1. Formily 的核心设计理念是什么？它解决了传统表单开发的哪些痛点？**

**核心理念：** MVVM 模式下的表单解决方案，将表单逻辑（校验、联动、布局）与 UI 渲染解耦，通过响应式内核驱动表单状态。

**解决的痛点：**
- **联动复杂：** 传统方案用 `onChange` + `setState` 手写联动，代码散乱难维护；Formily 用 `reactions` 声明式描述依赖关系
- **性能问题：** 传统方案任意字段变化导致整个表单重渲染；Formily 精确订阅，只更新依赖变化的字段
- **Schema 驱动：** 支持 JSON Schema 描述表单结构，实现低代码配置
- **校验体系：** 内置异步校验、联动校验、自定义校验规则，统一管理
- **布局与逻辑分离：** 表单逻辑在 Core 层，UI 渲染在 React/Vue 适配层，可跨框架复用

---

**Q2. Formily 中 Schema 驱动和 JSX 驱动各有什么优缺点？**

**Schema 驱动：**
```json
{
  "type": "object",
  "properties": {
    "username": {
      "type": "string",
      "title": "用户名",
      "x-component": "Input",
      "x-validator": [{ "required": true }],
      "x-reactions": { "dependencies": ["role"], "fulfill": { "state": { "visible": "{{$deps[0] === 'admin'}}" } } }
    }
  }
}
```
- **优点：** 可序列化存储（数据库/CDN），支持低代码配置，运行时动态生成表单
- **缺点：** 复杂逻辑表达能力有限，调试困难，TypeScript 类型支持弱

**JSX 驱动：**
```tsx
<SchemaField>
  <SchemaField.String name="username" title="用户名" x-component="Input" />
</SchemaField>
```
- **优点：** 完整 TypeScript 支持，IDE 提示好，复杂逻辑可直接写 JS
- **缺点：** 无法序列化，不支持低代码配置

**实践选择：** 低代码平台用 Schema 驱动（需要序列化存储）；业务开发用 JSX 驱动（开发体验好）。

---

**Q3. Formily 的响应式内核（@formily/reactive）与 MobX 有什么关系？**

`@formily/reactive` 是 Formily 团队参考 MobX 思想自研的响应式库，核心概念相同：

- **observable：** 将对象变为可观察对象，属性读写被追踪
- **computed：** 派生值，依赖变化时自动重新计算（有缓存）
- **reaction/autorun：** 副作用，依赖变化时自动执行

**与 MobX 的区别：**
- 体积更小（~10KB vs MobX ~50KB）
- 专为 Formily 表单场景优化，不是通用状态管理库
- API 略有差异，但核心思想一致

**在 Formily 中的应用：** 每个字段的 `value/visible/disabled/errors` 都是 observable，`reactions` 中的依赖追踪基于 computed，字段变化时只触发依赖该字段的其他字段更新，实现精确渲染。

### 高级题

**Q4. 你设计的"字段联动响应式依赖模型"是如何工作的？请举一个复杂的跨字段联动场景说明实现细节。**

**场景：** 企业认证表单，`企业类型` 决定 `营业执照` 字段的显隐和必填规则，`所在地区` 变化时异步加载 `城市` 选项，`城市` 变化时清空 `详细地址`。

```tsx
const schema = {
  type: 'object',
  properties: {
    companyType: {
      type: 'string',
      title: '企业类型',
      enum: ['个体户', '有限公司', '股份公司'],
    },
    businessLicense: {
      type: 'string',
      title: '营业执照',
      'x-reactions': {
        dependencies: ['companyType'],
        fulfill: {
          state: {
            // 个体户不需要营业执照
            visible: "{{$deps[0] !== '个体户'}}",
            required: "{{$deps[0] !== '个体户'}}",
          }
        }
      }
    },
    province: { type: 'string', title: '省份' },
    city: {
      type: 'string',
      title: '城市',
      'x-reactions': [
        {
          dependencies: ['province'],
          fulfill: {
            run: `$self.loading = true; $self.dataSource = await fetchCities($deps[0]); $self.loading = false;`
          }
        }
      ]
    },
    address: {
      type: 'string',
      title: '详细地址',
      'x-reactions': {
        dependencies: ['city'],
        fulfill: { state: { value: '' } } // city 变化时清空地址
      }
    }
  }
};
```

**避免循环依赖：** Formily 内部维护依赖图，检测到循环依赖时抛出警告。设计时遵循单向数据流原则，A 依赖 B，B 不能依赖 A。

**异步联动处理：** `x-reactions` 的 `run` 支持 async 函数，Formily 自动处理 loading 状态，防止并发请求（新请求发出时取消旧请求）。

**Q7. Formily 的性能边界在哪里？当表单字段超过 100 个且存在大量联动时如何优化？**

**性能瓶颈分析：**
- 100+ 字段时，初始化 observable 对象的开销增大
- 大量 `reactions` 形成复杂依赖图，每次字段变化需要遍历依赖图
- React 渲染层：即使 Formily 精确订阅，100+ 个 Observer 组件的协调也有开销

**优化策略：**

1. **字段精确订阅：** 确保每个字段只订阅自己真正依赖的字段，避免过度依赖
```ts
// ? 订阅整个 form 的变化
reactions: (field) => { field.visible = form.values.type === 'A'; }

// ? 只订阅 type 字段
reactions: { dependencies: ['type'], fulfill: { state: { visible: "{{$deps[0] === 'A'}}" } } }
```

2. **虚拟滚动：** 超长表单（100+ 字段）分页显示或按需渲染，只渲染视口内字段

3. **懒计算联动：** 非可见字段的联动延迟计算（字段变为可见时才触发）

4. **Formily DevTools：** 分析哪些字段触发了不必要的重渲染，针对性优化

5. **批量更新：** 多个字段同时初始化时，用 `batch(() => { ... })` 合并更新，减少渲染次数

**Q2. Canvas 的脏区渲染（Dirty Rectangle）是什么？如何避免全量重绘？**

**脏区渲染：** 只重绘发生变化的区域（脏区），而非整个 Canvas，减少绘制开销。

```js
class DirtyRectRenderer {
  dirtyRects: DOMRect[] = [];

  markDirty(x: number, y: number, width: number, height: number) {
    this.dirtyRects.push(new DOMRect(x, y, width, height));
  }

  render() {
    if (this.dirtyRects.length === 0) return;
    
    // 合并重叠的脏区
    const merged = mergeDirtyRects(this.dirtyRects);
    
    merged.forEach(rect => {
      ctx.save();
      ctx.beginPath();
      ctx.rect(rect.x, rect.y, rect.width, rect.height);
      ctx.clip(); // 裁剪到脏区
      
      // 只重绘与脏区相交的元素
      this.elements
        .filter(el => el.intersects(rect))
        .forEach(el => el.draw(ctx));
      
      ctx.restore();
    });
    
    this.dirtyRects = [];
  }
}
```

**避免全量重绘的策略：**
- 静态背景层与动态元素层分离（多 Canvas 叠加）
- 只在元素状态变化时标记脏区
- 使用 `requestAnimationFrame` 合并多次变化到一帧

**Q3. AntV X6 的核心概念：Graph、Node、Edge、Port 分别是什么？**

- **Graph：** 画布容器，管理所有元素，提供渲染、交互、事件系统
- **Node：** 节点，图中的顶点，可以是矩形、圆形或自定义 React 组件
- **Edge：** 边，连接两个节点的连线，可以有箭头、标签、弯折点
- **Port：** 连接桩，节点上的连接点，Edge 从 Port 出发连接到另一个 Port

**在 IOT 流程画布中的应用：** Node 代表设备操作步骤（发送指令/等待响应/条件判断），Edge 代表流程走向，Port 定义每个步骤的输入/输出连接点，Graph 管理整个流程的序列化和反序列化。

### 高级题

**Q4. 你解决了"大规模节点下 React 嵌入 Canvas 渲染性能问题"，请详细说明问题的根因和解决方案。**

**根因分析：**
X6 的 React Shape 通过 `ReactDOM.createRoot` 为每个节点创建独立 React 树，渲染到 SVG 的 `<foreignObject>` 中。1000 个节点 = 1000 个独立 React 根，问题在于：
- 每次画布平移/缩放，所有节点的 React 组件都可能触发重渲染
- 节点进出视口时的 mount/unmount 开销巨大（React 树的创建和销毁）
- 1000 个 MutationObserver 和事件监听器的内存开销

**解决方案（分层优化）：**

```ts
// 1. 视口裁剪：只渲染视口内节点
const visibleNodes = new Set<string>();

graph.on('translate', () => updateVisibility());
graph.on('scale', () => updateVisibility());

function updateVisibility() {
  const viewportBBox = graph.getGraphArea();
  graph.getNodes().forEach(node => {
    const bbox = node.getBBox();
    const isVisible = viewportBBox.isIntersectWithRect(bbox);
    const wasVisible = visibleNodes.has(node.id);
    
    if (isVisible && !wasVisible) {
      visibleNodes.add(node.id);
      node.show(); // 触发 React 组件 mount
    } else if (!isVisible && wasVisible) {
      visibleNodes.delete(node.id);
      // 不 unmount，用 CSS 隐藏（保留 React 实例）
      node.attr('body/visibility', 'hidden');
    }
  });
}

// 2. 批量更新：合并到 rAF
let pendingRender = false;
function scheduleRender() {
  if (pendingRender) return;
  pendingRender = true;
  requestAnimationFrame(() => {
    ReactDOM.unstable_batchedUpdates(() => updateVisibility());
    pendingRender = false;
  });
}

// 3. 节点数据变化时批量更新
graph.on('node:change:data', scheduleRender);
```

**性能数据：** 10000 节点，优化前 10fps，优化后 50fps+；内存从 800MB 降至 480MB。

**Q5. "复杂分支结构的序列化持久化设计"是如何实现的？如何保证多层级画布配置的完整还原？**

**数据结构设计：**
```ts
interface FlowSchema {
  version: string;           // Schema 版本号，用于迁移
  nodes: NodeSchema[];
  edges: EdgeSchema[];
  subflows?: Record<string, FlowSchema>; // 嵌套子流程
}

interface NodeSchema {
  id: string;
  type: string;              // 节点类型（action/condition/loop）
  position: { x: number; y: number };
  data: Record<string, unknown>; // 业务数据
  ports?: PortSchema[];
}

interface EdgeSchema {
  id: string;
  source: { nodeId: string; portId: string };
  target: { nodeId: string; portId: string };
  condition?: string;        // 条件分支的判断表达式
}
```

**版本迁移机制：**
```ts
const migrations: Record<string, (schema: FlowSchema) => FlowSchema> = {
  '1.0→2.0': (schema) => ({
    ...schema,
    version: '2.0',
    nodes: schema.nodes.map(n => ({ ...n, ports: generateDefaultPorts(n.type) }))
  }),
};

function migrateSchema(schema: FlowSchema, targetVersion: string): FlowSchema {
  let current = schema;
  while (current.version !== targetVersion) {
    const key = `${current.version}→${nextVersion(current.version)}`;
    current = migrations[key](current);
  }
  return current;
}
```

**循环检测：** 有向图 DFS，检测是否存在环路，防止无限循环配置：
```ts
function hasCycle(nodes: string[], edges: EdgeSchema[]): boolean {
  const visited = new Set<string>();
  const inStack = new Set<string>();
  
  function dfs(nodeId: string): boolean {
    visited.add(nodeId);
    inStack.add(nodeId);
    const outEdges = edges.filter(e => e.source.nodeId === nodeId);
    for (const edge of outEdges) {
      if (!visited.has(edge.target.nodeId) && dfs(edge.target.nodeId)) return true;
      if (inStack.has(edge.target.nodeId)) return true;
    }
    inStack.delete(nodeId);
    return false;
  }
  
  return nodes.some(n => !visited.has(n) && dfs(n));
}
```

**Q6. 如果画布需要支持 10 万节点的流畅交互，你会如何设计渲染架构？**

**分层渲染架构：**

1. **LOD（Level of Detail）：** 根据缩放级别切换渲染精度
   - 缩放 < 20%：只渲染节点轮廓（矩形/圆形），不渲染内部 React 组件
   - 缩放 20-60%：渲染简化版节点（只显示标题）
   - 缩放 > 60%：渲染完整 React 组件

2. **四叉树空间索引：** 快速查询视口内节点
```ts
const quadTree = new QuadTree({ x: 0, y: 0, width: 100000, height: 100000 });
nodes.forEach(n => quadTree.insert(n));

function getVisibleNodes(viewport: BBox): Node[] {
  return quadTree.query(viewport); // O(log n) 而非 O(n)
}
```

3. **WebGL 渲染（极端场景）：** 10 万节点时 Canvas 2D 也会卡顿，用 WebGL 批量渲染几何图形，GPU 并行处理

4. **分层 Canvas：**
   - 背景层（网格线）：静态，只在缩放时重绘
   - 节点层：动态，视口变化时重绘
   - 交互层（选中/hover 高亮）：独立层，频繁更新不影响其他层

5. **Web Worker 布局计算：** 自动布局（力导向/层次布局）计算量大，移到 Worker 线程，不阻塞主线程交互

## 九、动画性能 & GPU 渲染

### 基础题

**Q1. CSS 动画和 JS 动画各有什么优缺点？什么是 FLIP 动画技术？**

| 维度 | CSS 动画 | JS 动画 |
|------|---------|---------|
| 性能 | 可走合成层，无 JS 开销 | 需要 JS 执行，可能阻塞主线程 |
| 控制精度 | 有限（关键帧） | 完全可控（逐帧） |
| 交互性 | 弱（难以动态修改） | 强（可响应用户输入） |
| 复杂动画 | 难以实现 | 灵活 |
| 适用场景 | 简单过渡、循环动画 | 游戏、物理动画、复杂交互 |

**FLIP 动画技术：**
- **F（First）：** 记录元素初始状态（位置/尺寸）
- **L（Last）：** 将元素移动到最终状态，记录最终状态
- **I（Invert）：** 用 `transform` 将元素"反转"回初始视觉位置
- **P（Play）：** 移除 transform，触发过渡动画

```js
// FLIP 实现列表重排动画
const first = el.getBoundingClientRect();
// 执行 DOM 变化（重排）
list.insertBefore(el, list.firstChild);
const last = el.getBoundingClientRect();

// Invert：用 transform 抵消位移
const deltaX = first.left - last.left;
const deltaY = first.top - last.top;
el.style.transform = `translate(${deltaX}px, ${deltaY}px)`;

// Play：移除 transform，触发 CSS 过渡
requestAnimationFrame(() => {
  el.style.transition = 'transform 300ms ease';
  el.style.transform = '';
});
```

**FLIP 的优势：** 将昂贵的布局计算（Layout）转换为廉价的合成层动画（Composite），实现流畅的列表重排动画。

**Q2. requestAnimationFrame 相比 setTimeout 有什么优势？**

1. **与屏幕刷新率同步：** rAF 在浏览器下一次重绘前执行，通常 60fps（16.7ms/帧），setTimeout 的时间不精确（受事件循环影响）
2. **页面不可见时暂停：** 标签页切换到后台时，rAF 自动暂停，节省 CPU/GPU 资源；setTimeout 仍然执行
3. **避免过度绘制：** 多次 rAF 调用在同一帧内只执行一次，setTimeout 可能在一帧内执行多次导致丢帧
4. **与浏览器渲染流水线协调：** rAF 在 Layout 和 Paint 之前执行，确保动画更新在正确时机

```js
// ? setTimeout 动画：时间不精确，可能丢帧
function animate() {
  update();
  setTimeout(animate, 16); // 不精确，可能 16ms 或 20ms
}

// ? rAF 动画：与屏幕刷新同步
function animate(timestamp) {
  const delta = timestamp - lastTime;
  update(delta); // 基于时间差更新，帧率无关
  lastTime = timestamp;
  requestAnimationFrame(animate);
}
```

**Q3. 什么是 will-change？它有什么副作用？**

**will-change：** 提前告知浏览器元素将要发生的变化，让浏览器提前优化（通常是提升为合成层）。

```css
.animated-element {
  will-change: transform, opacity; /* 提前分配合成层 */
}
```

**副作用：**
1. **内存占用：** 每个合成层都需要 GPU 显存，过度使用导致内存暴涨
2. **层爆炸：** 大量元素设置 will-change，创建过多合成层，反而降低性能
3. **字体渲染变化：** 合成层中的文字渲染方式可能与普通层不同（抗锯齿差异）
4. **z-index 行为变化：** 创建新的层叠上下文，影响 z-index 的表现

**正确使用姿势：**
```css
/* ? 动画开始前设置，结束后移除 */
.card { transition: transform 0.3s; }
.card:hover { will-change: transform; } /* hover 时才提升 */

/* ? 不要对所有元素设置 */
* { will-change: transform; } /* 灾难性的内存占用 */
```

**Q2. 流式输出（Streaming）在前端如何消费？fetch 的 ReadableStream 如何使用？**

```ts
async function streamChat(prompt: string, onChunk: (text: string) => void) {
  const response = await fetch('/api/chat', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', 'Authorization': `Bearer ${token}` },
    body: JSON.stringify({ prompt }),
  });

  const reader = response.body!.getReader();
  const decoder = new TextDecoder();
  let buffer = '';

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    
    buffer += decoder.decode(value, { stream: true });
    
    // 按行解析 SSE 格式
    const lines = buffer.split('\n');
    buffer = lines.pop() ?? ''; // 保留不完整的行
    
    for (const line of lines) {
      if (line.startsWith('data: ')) {
        const data = line.slice(6);
        if (data === '[DONE]') return;
        const { content } = JSON.parse(data);
        onChunk(content);
      }
    }
  }
}
```

**fetch vs EventSource 的选择：** EventSource 只支持 GET 请求，无法自定义 Header（无法传 Authorization），AI 接口通常需要 POST + Bearer Token，所以用 `fetch + ReadableStream`。

**Q3. 什么是 AI Agent？它与普通的 LLM API 调用有什么不同？**

- **记忆（Memory）：** 维护对话历史和工作状态
- **反思（Reflection）：** 评估执行结果，调整策略

**典型 Agent 循环：**


### 高级题

**Q4. 你设计了"SSE/stream 流式输出的前端处理方案"，请描述完整技术方案。**

**完整实现：**

```ts
class StreamProcessor {
  private abortController: AbortController | null = null;
  private buffer = '';

  async startStream(
    url: string,
    payload: unknown,
    callbacks: {
      onToken: (token: string) => void;
      onToolCall: (toolCall: ToolCall) => void;
      onDone: () => void;
      onError: (err: Error) => void;
    }
  ) {
    this.abortController = new AbortController();
    
    try {
      const response = await fetch(url, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json', 'Authorization': `Bearer ${getToken()}` },
        body: JSON.stringify(payload),
        signal: this.abortController.signal,
      });

      if (!response.ok) throw new Error(`HTTP ${response.status}`);

      const reader = response.body!.getReader();
      const decoder = new TextDecoder();
      
      // 批量渲染：积累 token，每帧最多渲染一次
      let pendingTokens = '';
      let rafId: number | null = null;
      
      const flushTokens = () => {
        if (pendingTokens) {
          callbacks.onToken(pendingTokens);
          pendingTokens = '';
        }
        rafId = null;
      };

      while (true) {
        const { done, value } = await reader.read();
        if (done) break;
        
        this.buffer += decoder.decode(value, { stream: true });
        const lines = this.buffer.split('\n');
        this.buffer = lines.pop() ?? '';
        
        for (const line of lines) {
          if (!line.startsWith('data: ')) continue;
          const data = line.slice(6).trim();
          if (data === '[DONE]') { callbacks.onDone(); return; }
          
          const chunk = JSON.parse(data);
          
          if (chunk.type === 'content_block_delta') {
            pendingTokens += chunk.delta.text;
            // 用 rAF 批量更新，避免每 token 触发重渲染
            if (!rafId) rafId = requestAnimationFrame(flushTokens);
          } else if (chunk.type === 'tool_use') {
            callbacks.onToolCall(chunk);
          }
        }
      }
    } catch (err) {
      if ((err as Error).name === 'AbortError') return; // 用户主动取消
      callbacks.onError(err as Error);
    }
  }

  abort() {
    this.abortController?.abort();
    this.buffer = '';
  }
}
```

**断线重连：**
```ts
async function streamWithRetry(url: string, payload: unknown, maxRetries = 3) {
  for (let i = 0; i < maxRetries; i++) {
    try {
      await streamProcessor.startStream(url, payload, callbacks);
      return;
    } catch (err) {
      if (i === maxRetries - 1) throw err;
      await sleep(1000 * Math.pow(2, i)); // 指数退避
    }
  }
}
```

**Q5. 你构建了"多轮对话上下文隔离机制"，请说明隔离的边界是什么？**

**隔离边界：** `sessionId` 是隔离的最小单元，每个会话有独立的消息历史、流式状态和 AbortController。

```ts
interface Session {
  id: string;
  messages: Message[];
  streamProcessor: StreamProcessor | null;
  status: 'idle' | 'streaming' | 'error';
}

class ConversationManager {
  private sessions = new Map<string, Session>();
  private activeSessionId: string | null = null;

  switchSession(sessionId: string) {
    // 切换会话时，暂停当前流式输出
    const current = this.sessions.get(this.activeSessionId!);
    current?.streamProcessor?.abort();
    
    this.activeSessionId = sessionId;
  }

  async sendMessage(sessionId: string, content: string) {
    const session = this.sessions.get(sessionId)!;
    
    // 并发场景：同一会话的新请求取消旧请求
    session.streamProcessor?.abort();
    session.streamProcessor = new StreamProcessor();
    
    // 构建上下文：保留最近 20 轮 + system prompt
    const context = [
      { role: 'system', content: SYSTEM_PROMPT },
      ...session.messages.slice(-40), // 最近 20 轮（每轮 2 条）
      { role: 'user', content },
    ];
    
    await session.streamProcessor.startStream('/api/chat', { messages: context }, {
      onToken: (token) => {
        session.messages[session.messages.length - 1].content += token;
      },
      // ...
    });
  }
}
```

**内存管理：** 长对话的消息裁剪策略——保留 system prompt + 最近 N 轮对话，超出部分用摘要替代（调用 LLM 对历史对话做摘要，压缩 token 数量）。
