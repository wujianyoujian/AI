## 工程化兼容性问题
一、CSS 兼容性

核心问题： 不同浏览器对 CSS 属性支持程度不同，以及盒模型差异。

解决方案：

- Autoprefixer：构建时自动添加 -webkit-、-moz- 等厂商前缀，配合 browserslist 配置目标浏览器范围
- PostCSS：CSS 转换管道，Autoprefixer 是其插件之一，还可以做 CSS 降级（如 color: oklch() 降级为 hex）
- CSS Reset / Normalize.css：消除浏览器默认样式差异，Normalize 保留有用默认值，Reset 全部清零
- 盒模型统一：全局设置 box-sizing: border-box，避免 IE 遗留问题
- Can I Use：查询属性支持情况，决定是否需要 polyfill 或降级方案

---
二、JavaScript 兼容性

核心问题： 新语法（ES6+）和新 API 在旧浏览器不支持。

解决方案：

- Babel：将 ES6+ 语法转译为 ES5，配合 @babel/preset-env + browserslist 按需转译，避免过度编译
- Core-js / Polyfill：补充运行时 API，如 Promise、Array.prototype.includes、Object.assign 等。useBuiltIns: 'usage' 模式按需引入，减小包体积
- 区分语法转译和 API polyfill：Babel 只处理语法，API 需要 polyfill，这是面试常考的区分点

---
三、HTML 兼容性

- 语义化标签降级：<article>、<section> 等 HTML5 标签在 IE8 不识别，用 html5shiv 解决（现在基本不需要了）
- <meta charset="UTF-8">：防止编码问题
- DOCTYPE 声明：缺少会触发 IE 怪异模式（Quirks Mode），导致盒模型异常

---
四、浏览器差异（行为层面）

- 事件模型：IE 用 attachEvent，标准用 addEventListener，现代项目不需要处理，但要知道历史原因
- fetch vs XHR：IE 不支持 fetch，需要 polyfill 或用 axios（内部用 XHR）
- requestAnimationFrame：旧版需要前缀，现代浏览器已统一

---
五、工程化落地（4~5 年经验的重点）

这是区分初级和中高级的关键，要能说出如何在项目中系统性配置：

browserslist（统一目标浏览器）
    ↓
Babel + @babel/preset-env（JS 语法转译）
    ↓
core-js（API polyfill，按需引入）
    ↓
PostCSS + Autoprefixer（CSS 前缀）
    ↓
构建产物分析（bundle-analyzer 检查是否有冗余 polyfill）

browserslist 配置示例：
> 1%
last 2 versions
not dead
not IE 11

这个配置会被 Babel、Autoprefixer、ESLint 等工具共享，是兼容性配置的核心。

---
六、现代项目的取舍

4~5 年经验还需要有判断力，不是所有兼容都要做：

- 明确业务目标浏览器，不为 IE 做无谓兼容（大多数 ToC 产品已放弃 IE11）
- 用 <script type="module"> + <script nomodule> 做差异化加载：现代浏览器加载 ES Module 包，旧浏览器加载 ES5 包，减少现代用户的包体积
- 移动端重点关注 iOS Safari 的兼容（如 position: sticky、100vh 问题、-webkit-overflow-scrolling）

---
面试回答结构建议

▎ "前端兼容性我会从 CSS、JS、工程化三个层面来说。CSS 层面用 PostCSS + Autoprefixer 自动处理前缀，配合 Normalize.css 统一基线样式；JS 层面用 Babel 做语法转译，core-js 按需 polyfill API，两者通过 browserslist 统一目标浏览器；工程化层面，browserslist 是核心，所有工具共享这份配置。现代项目我们已经放弃 IE，重点转向 iOS Safari 的兼容，同时用 module/nomodule 差异化加载来优化现代浏览器的性能。"

这个回答覆盖了原理、工具链、工程实践和业务判断，符合 4~5 年经验的预期深度。

## 混合APP 的兼容性问题
一、WebView 本身的差异

混合 App 的核心是 WebView，但不同平台的 WebView 内核不同：

┌────────────────┬────────────────────────────────────────┐
│      平台      │              WebView 内核              │
├────────────────┼────────────────────────────────────────┤
│ Android 5+     │ Chromium（系统 WebView，版本跟随系统） │
├────────────────┼────────────────────────────────────────┤
│ Android 4.x    │ 老版本 WebKit，问题最多                │
├────────────────┼────────────────────────────────────────┤
│ iOS            │ WKWebView（iOS 8+），UIWebView 已废弃  │
├────────────────┼────────────────────────────────────────┤
│ 微信内置浏览器 │ X5 内核（腾讯基于 Blink 定制）         │
└────────────────┴────────────────────────────────────────┘

关键问题：Android 系统 Weboid 的 WebView 不支持新CSS/JS 特性，需要 Babel + Polyfill 兜底，同时要在真机上测试而不只是 Chrome DevTools。

---
二、JSBridge 通信兼容性

JSBridge 是混合 App 兼容性问题最集中的地方。

通信原理

JS 调用原生（两种方式）：

1. URL Scheme 拦截：JS 发起假请求 myapp://action?params=xxx，原生拦截 URL 执行对应逻辑
  - 兼容性最好，iOS/Android 都支持
  - 缺点：有长度限制，异步
2. 注入 JS 对象：
  - Android：addJavascriptInterface() 注入 Java 对象到 window
  - iOS WKWebView：WKScriptMessageHandler 注入，JS 用 window.webkit.messageHandlers.xxx.postMessage()
  - 两端 API 不一样，需要封装统一调用层

原生调用 JS：
- Android：webView.evaluateJavascript("javascript:callback()", null)
- iOS：webView.evaluateJavaScript("callback()")
- 两端基本一致，但要注意时机问题（页面未加载完时调用会失效）

---
三、具体踩坑点

1. iOS WKWebView 的限制

- 本地文件跨域：WKWebView  下 Ajax 请求会被 CORS拦截，需要原生配置或改用 http://localhost 方式加载
- -webkit-overflow-scrolling: touch：老项目常见，控制滚动惯性，但会导致 position: fixed 失效，需要用其他方案替代
- 输入框被键盘遮挡：iOS 弹出键盘不会触发 resize，需要监听 focusin 事件手动滚动页面
- 100vh 问题：同前面说的，iOS Safari 地址栏占用空间，用 dvh 或 JS 动态设置

2. Android WebView 问题

- 字体缩放：用户在系统设置内字体也会跟着变，导致布局错乱。解决：textSize 固定，或 CSS 用 px 而非 em/rem
- 白屏问题：WebView 初始化慢，常见优化是预加载 WebView 实例（WebView 池）
- 视频自动播放：Android低版本需要用户手势触发，不能自动播放，需要原生协助或降级处理
- position: fixed + 软键盘：Android 弹出键盘会 resize WebView，导致 fixed 元素位置错乱，需要监听 resize 重新定位

3. 通用问题

- Bridge 初始化时序：页面 JS 执行时原生 Bridge 可能还没注入完成，需要用 document.addEventListener('deviceready', ...) 或轮询等待
- Cookie/Storage 隔离：不可能不共享，登录态需要原生统一管理后注入
- HTTPS 证书：Android WebView
对自签名证书默认拒绝，开发 生产不能这样做）

---
四、调试手段

- Android：Chrome DevTools 远程调试，chrome://inspect，连接 USB 后可以直接调试 WebView
- iOS：Safari 开发者工具，开启"Web 检查器"后连接真机调试
- vConsole / Eruda：在页面内嵌入移动端调试面板，不需要连电脑，适合测试阶段

---
五、面试回答结构

▎ "混合 App 的兼容性主要集中在三块：WebView 差异、JSBridge 通信、以及平台特有 bug。
▎
▎ WebView 层面，Android 的w 版本跟随 Android版本，低版本设备需要 Babel + Polyfill 兜底，必须真机测试。
▎
▎ JSBridge 层面，iOS 和 Android 的注入方式不一样，iOS 用 messageHandlers，Android 用 addJavascriptInterface，我们会封装一个统一的 Bridge 层屏蔽差异，同时处理 Bridge 未就绪时的时序问
▎
▎ 具体 bug 层面，iOS 最常 效、WKWebView本地文件跨域；Android 最常见的是字体缩放导致布局错乱、position: fixed 被键盘顶飞。调试用 Chrome DevTools 远程调试 Android，Safari 调试 iOS，测试阶段用 vConsole 内嵌调试面板。"

## h5 app 通信方式
JS 调用原生（H5 → App）

1. URL Scheme 拦截

// JS 发起假请求
location.href = 'myapp://getLocation?callbackId=cb_123'
// 或用 iframe
const iframe = document.createElement('iframe')
iframe.src = 'myapp://getLocation?callbackId=cb_123'
document.body.appendChild(iframe)
原生拦截这个 URL，解析 scheme 和参数执行对应逻辑。

- 兼容性最好，iOS/Android 都支持
- 参数有长度限制（URL 长度限制）
- iframe 方式比 location.href 更稳定，不会打断页面导航

2. 注入全局对象

原生向 window 注入一个对象，JS 直接调用其方法：

// Android：addJavascriptInterface 注入
window.NativeBridge.getLocation(JSON.stringify({ callbackId: 'cb_123' }))

// iOS：messageHandlers 注入
window.webkit.messageHandlers.getLocation.postMessage({ callbackId: 'cb_123' })

- 调用更直接，没有长度限制
- iOS 和 Android API 不一样，需要封装统一层

3. 拦截 prompt / alert / confirm（了解即可）

早期方案，原生重写 WebView 的 window.prompt，JS 调用 prompt('myapp://xxx') 传递消息，原生拦截返回值。现在基本不用，但面试偶尔会问。

---
原生调用 JS（App → H5）

evaluateJavaScript

两端都支持，原生主动执行一段 JS 字符串：

// iOS
webView.evaluateJavaScript("window.onNativeEvent({ type: 'locationResult', data: {...} })")

// Android
webView.evaluateJavascript("window.onNativeEvent(...)", null)

H5 侧提前在 window 上挂好回调函数等待调用。

---
异步回调的处理

通信本质是单向的，要实现"调用 → 等待结果"的异步模式，需要用 callbackId 对应：

const bridge = {
  callbacks: {},
  call(method, params, callback) {
    const id = `cb_${Date.now()}`
    this.callbacks[id] = callback
    // 发消息给原生，带上 id
    nativeCall(method, { params, callbackId: id })
  },
  // 原生回调时触发
  onNativeCallback(id, result) {
    this.callbacks[id]?.(result)
    delete this.callbacks[id]
  }
}

原生执行完后调用 evaluateJavaScript("bridge.onNativeCallback('cb_123', result)") 触发回调。

---
总结对比

┌────────────────────┬───────────┬──────────────┬──────────────────────┐
│        方式        │   方向    │     优点     │         缺点         │
├────────────────────┼───────────┼──────────────┼──────────────────────┤
│ URL Scheme         │ JS → 原生 │ 兼容性好     │ 有长度限制           │
├────────────────────┼───────────┼──────────────┼──────────────────────┤
│ 注入全局对象       │ JS → 原生 │ 直接、无限制 │ iOS/Android API 不同 │
├────────────────────┼───────────┼──────────────┼──────────────────────┤
│ evaluateJavaScript │ 原生 → JS │ 两端统一     │ 需要 H5 提前挂好函数 │
├────────────────────┼───────────┼──────────────┼──────────────────────┤
│ prompt 拦截        │ JS → 原生 │ 同步返回值   │ 已过时，不推荐       │
└────────────────────┴───────────┴──────────────┴──────────────────────┘

实际项目中，注入全局对象 + evaluateJavaScript 是主流组合，封装一个统一 Bridge 层屏蔽平台差异。


## monorepo 等相关回答，以及如何技术选型

Monorepo 是什么

一个仓库管理多个包/项目，相对的是 Multirepo（每个项目独立仓库）。

适用场景： 组件库 + 业务项目、微前端子应用、共享工具函数的多个服务。

---
主流工具对比

1. pnpm Workspace（最常用）

# pnpm-workspace.yaml
packages:
  - 'packages/*'
  - 'apps/*'

- 原生支持 workspace，依赖提升 + 硬链接，磁盘占用最小
- 配合 Turborepo 做任务编排
- 适合： 大多数前端 Monorepo 场景，首选

2. Turborepo

不是包管理器，是任务编排工具，解决的是"多包之间构建顺序和缓存"问题：

// turbo.json
{
  "pipeline": {
    "build": {
      "dependsOn": ["^build"],  // 先构建依赖包
      "outputs": ["dist/**"]
    },
    "test": {
      "dependsOn": ["build"]
    }
  }
}

- 增量构建缓存，没改动的包跳过构建
- 并行执行独立任务
- 适合： 配合 pnpm workspace 使用，CI 提速明显

3. Nx

功能最重，内置代码生成器、 动影响的测试）：

nx affected --target=test  # 只测试受影响的包
nx graph

- 学习成本高，配置复杂
- 适合： 大型团队、多语言 Monorepo（前端 + Node.js 后端）

4. Lerna（了解即可）

老牌工具，现在基本被 pnpm workspace + Turborepo 替代，但很多老项目还在用。主要功能是版本管理和发布。

---
技术选型判断

┌───────────────────────────┬─────────────────────────────────────────┐
│           场景            │                推荐方案                 │
├───────────────────────────┼─────────────────────────────────────────┤
│ 中小团队，前端项目        │ pnpm workspace + Turborepo              │
├───────────────────────────┼─────────────────────────────────────────┤
│ 需要发布 npm 包（组件库） │ pnpm workspace + Changesets（版本管理） │
├───────────────────────────┼─────────────────────────────────────────┤
│ 大型团队，多语言          │ Nx                                      │
├────────────────────────────────────────┤
│ 老项目迁移                │ 保留 Lerna，逐步迁移到 pnpm workspace   │
└───────────────────────────┴─────────────────────────────────────────┘

---
Monorepo 的核心优势

- 代码共享：packages/utils 直接被所有 app 引用，不需要发 npm 包
- 原子提交：一个 PR 同时改组件库和使用方，不会出现版本不同步
- 统一工具链：ESLint、Type

---
Monorepo 的问题和解法

1. 构建慢
- Turborepo / Nx 的增量缓存解决，没改动的包直接用缓存

2. 依赖版本冲突
- pnpm 的 catalog 功能（pnpm 9+）统一管理依赖版本：
# pnpm-workspace.yaml
catalog:
  react: ^18.3.0
  typescript: ^5.4.0
各包用 catalog: 引用，版本统一管理

3. 权限管理
- 大仓库所有人都能看到所有代码，敏感项目需要额外的访问控制
- GitHub 的 CODEOWNERS 文件可以限制特定目录的 PR 审批人

4. Git 历史噪音
- 一个 commit 可能涉及多个包，用 Conventional Commits 规范 + scope 区分：feat(ui): add Button component

---
包之间的引用方式

// apps/web/package.json
{
  "dependencies": {
    "@myorg/ui": "workspace:*",    // 引用本地包
    "@myorg/utils": "workspace:*"                                    }
}

workspace:* 表示用本地版本，pnpm 会创建软链接，改了 packages/ui 立即生效，不需要重新发包。

---
面试回答结构

▎ "Monorepo 我们用 pnpm workspace + Turborepo 的组合。pnpm workspace 管理包之间的依赖关系，用orepo做任务编排，配置构建依赖顺序和增量缓存，CI 里没改动的包直接跳过，构建时间从 10 分钟降到 2 分钟左右。
▎
▎ 选型上，中小团队首选这个组合，上手快、够用；如果是大型团队或者需要多语言支持，才考虑 Nx，但学习成本明显更高。组件库发版用 Changesets 管理版本号和 changelog，避免手动维护。
▎
▎ 主要踩过的坑是依赖版本不act，用 pnpm 的 catalog功能统一锁定解决。
